## 2. 现状诊断

### 2.1 一句话

**领域模型（`Role` 模板 + `Supplier` 延迟实例化 + `RoleInstance` 聚合根 + `*Aware` 能力接口）是对的，不需要推倒；要修的是三件事：① 组件起的任务没人管（会伤害到已清除角色的玩家）；② 组件与框架之间没有契约面（拿到的是 73 个 public 方法的上帝对象）；③ 施放判定与热键栏渲染各有 4–6 份拷贝。**

### 3.3 核心契约（**目标形态**，阶段 4 落地）

> ⚠️ **组件层（L2）的定义不在本节，已全部迁至 `docs/组件系统设计-Unity风格.md`**（最终形态：构造期注入 `ComponentServices` + 回调只传信号 `CastSignal`/`AttackSignal` + `RoleComponent` 基类 default 钩子 + 端口必须是独立适配器）。原来的 `ComponentContext` / `CastContext` / 四个 `*Aware` 接口草案**已删除**，不再保留两套说法。
> 本节只保留仍然有效的 **L1 平台层**契约（`Task` / `Scheduler` / `KeyFactory` / `FactionLookup`，注 ①、注 ② 继续适用）。
>
> **注 ①（对架构文档 §7.2 的修正）**：本版 API **没有** `org.bukkit.scheduler.Cancellable`（`jar tf` 只找到 `org/bukkit/event/Cancellable.class`），`BukkitTask` 与 `io.papermc.paper.threadedregions.scheduler.ScheduledTask` 无共同父类型，且 `ScheduledTask.cancel()` 返回 `CancelledState` 而非 `void`。因此**必须自建 `Task` 句柄**，不要照抄 `Cancellable`。
>
> **注 ②**：不要现在实现 Folia 适配器。当前唯一运行环境是普通 Paper（`paper-1.21.11-132.jar`），Folia 分支无法验证。抽 `Scheduler` 的价值在于**去耦合 + 可测**，不在于 Folia。

### 3.4 施放/攻击管道（含**行为等价性论证**）

```
handleCast(trigger):                        // listener 只负责把事件翻译成 trigger
  id  = 该 trigger 对应的热键栏物品 id
  item = hotbarItems.get(id)；null → 返回
  precheck(item) == fail:                   // 只读声明字段，无副作用
      ① 冷却中            → 反馈"冷却中"（热键栏已是该状态，无需额外消息）
      ② 技能且被沉默/眩晕  → 反馈
      ③ 主武器且被眩晕     → 反馈
      ④ 能量 < energyCost → **不拦截**，仅让热键栏显示"能量不足"
      → markHotbarDirty(); return
  result = ((HotbarActionable) item).onCast(new CastSignal(trigger))   // 组件跑全部复杂判定
  switch (result):                       // CastResult 四常量，定义见设计文档 §10
      CAST           → cooldown.start(id, item.getCooldownTicks())
      NO_COOLDOWN    → 组件已自行处理
      REJECTED_*     → 反馈（文本由框架持有；不设自定义消息通道）
  markHotbarDirty()

handleAttack(victim):                       // 由 EntityDamageByEntityEvent 进入
  ① **先** event.setCancelled(true)         // ← 现状就是先取消再判冷却，必须保持
  ② 取手持主武器；非主武器/无角色/无该武器 → return
  ③ precheck（冷却仅看主武器；受眩晕限制，**不受沉默限制**）
  ④ result = ((CombatHook) weapon).onAttack(new AttackSignal(victim))   // 组件内部自行按能量档位分支
```

- `<noun>` = `"Skill"` / `"MainWeapon"`（`ItemKind` 提供）；随后统一追加 `"===================="` 与 `description`，并写入 PDC（`Skill.Utils.SKILL_KEY` / `MainWeapon.Utils.MAIN_WEAPON_KEY`）。

#### 3.5.1 自动刷新契约（**触发时机**，与状态判定同等重要）

"图标随状态自动变化"这件事**今天就是自动的**，新设计必须覆盖它全部的触发源，否则会出现"状态变了但图标不动"。

**今天的触发源（实测 7 类）**：

| # | 触发源 | 位置 | 动作 |
|---|---|---|---|
| ① | 每 tick ticker | `RoleInstance.java:94-99` → `triggerUpdate:727-733` | 按 ②③ 的谓词决定是否刷新 |
| ② | 冷却到点 | `shouldUpdateHotbar:757-765` | 全量重建 |
| ③ | 冷却倒计时 | `shouldUpdateItemMeta:767-774` | 仅重写 `displayName` |
| ④ | 施放/攻击后 1t | 8 处 `runTaskLater(..., this::updateHotbar, 1L)`（`:171,205,223,241,266,295,310,325`） | 延迟全量重建 |
| ⑤ | 能量变化 | `setCurrentEnergy:489` | **立即**全量重建 |
| ⑥ | buff 变化 | `BuffManager.java:109` | 立即全量重建 |
| ⑦ | 冷却启动 | `:167,179,262,273` 等 | 立即全量重建 |

> ⚠️ **②的谓词其实是"永久为真"**（O-21：两张冷却表的条目永不清除，唯一的 `remove` 在零调用死方法里）—— 也就是说今天等价于**每 tick 无脑重建**。这解释了两件事：
> 1. O-21/O-21b/O-23 这三个性能问题的共同根源；
> 2. **今天的可靠性来自"无条件轮询"，不是"状态变化通知"**。因此新渲染器**不能只依赖组件 `markDirty()`** —— "冷却到点"这类事件**没有任何组件会去通知**，必须由框架 poll。**只做 push 一定会漏刷新。**

**新设计：push + poll + 帧末 flush**

| 类别 | 触发者 | 覆盖事件 | 对应今天 |
|---|---|---|---|
| **push** | 框架自己（不需要组件配合） | 施放结果分派后、冷却 `start`、能量变化、buff 变化、上角色首次渲染 | ④⑤⑥⑦ + 初始渲染 |
| **push** | **端口适配器内部**（框架侧） | 任何经端口发生的状态写入（`energy.tryConsume` / `buffs.add` / `cooldowns.start`） | 覆盖⑤⑥⑦中的组件触发部分 |
| **poll** | ticker 每 tick 检查三个便宜谓词 | ① 最早冷却到期 tick ≤ now；② 是否有条目处于冷却中（倒计时文本需刷）；③ buff 到期 | ①②③ |
| **flush** | 帧末一次 | 一 tick 内多次 `markDirty` 只重建一次 | 顺带修掉 O-21b / O-23 |

> **组件不参与渲染**：`markDirty()` 是框架内部 API，**不进 `ComponentServices`** —— 渲染器读的全部状态都来自框架可见的数据（冷却/buff/能量端口 + `final` 的声明数据），组件既不需要也不应该控制渲染时机（设计文档 §5 有完整论证）。

**两条写路径都必须保留**（这是今天行为的一部分，不能合并）：
- **状态变化** → 整体替换 `ItemStack`；
- **只有倒计时文本变化** → 只 `setItemMeta`（即今天 ③ 的路径）—— 避免每 tick 替换物品对象带来的持有/选中态风险。

**渲染器的数据来源**：直接读端口（`buffs().canCastSkill()` / `energy().current()` / `cooldowns().isReady()`），**不接收组件上报的状态** —— 否则渲染逻辑又回到组件里，那正是 6 份拷贝的成因。

**组件侧只有一件事**：提供声明数据（设计文档 §4.3）。**不造 `ItemStack`、也不请求刷新**（I-12：`createIconItem` 全仓只允许出现 1 处）。

**验收方式**：在"施放 → 冷却中（含秒数倒计时）→ 冷却到点 → 能量不足 → 被眩晕禁用 → 恢复就绪"这条完整链路上逐帧比对图标（材质 + displayName + lore），且**在没有任何状态变化的空闲 tick 上不得发生物品替换**（可用 `ItemStack` 引用相等性检查，或统计 `setItem` 调用次数为 0）。

### 3.6 生命周期与资源托管契约

```
RoleInstance 构造:
  buildServices(player)（此时组件查找尚不可用）
  → 按模板工厂创建全部组件（构造期拿到 svc，顺序 = 注册顺序）
  → components.freeze()（之后 getComponent() 才合法）
  → awake 全部 → start 全部 → 启动**唯一** ticker → 首次渲染

RoleInstance.clear():
  stop 全部（逆序：武器/被动/技能）
  → 每个组件：取消它通过 svc.timers() 登记的全部任务（框架兜底，按组件分组）
  → 未取消的 ticker 兜底取消
  → clearHotbar / 移除本系统施加的属性修饰符 / 移除本系统施加的药水效果（记账，见 D6）
  → buffManager.clearAll() / 清冷却 / 清组件引用（组件缓存的 `getComponent` 结果在各自 stop 里置空）
```

**硬性要求**：`stop` 返回后，框架必须**自动**回收该组件通过 `svc.timers()`（`run` / `runLater` / `runRepeating` / `track`）登记的一切资源。这样 `MeiqiheziEquipmentsPassive` 那种空 `stop` 造成的装备残留（O-1/O-2）与 `DefaultSanTEZeroPunishment` 的 `taskId` 覆盖（O-6）都在机制层面消失，而不是靠人记得写。

**分派与异常策略**（完整定义见设计文档 §7/§8）：
- **存储合并、分派分组**：主动组件（技能 + 主武器）存一张 `LinkedHashMap`（I-12），但分派仍按今天的三组 `SKILL → PASSIVE → MAIN_WEAPON`，`stop` 整体逆序 —— 存储合并不改变分派顺序。
- 组内顺序 = **注册顺序**（今天依赖 `HashMap` 迭代序 = 未定义，属申报的有意修正）。
- 异常：`awake`/`start` **fail-fast**（装配错误开局就响）；`update` 与事件广播**逐组件隔离**（泛化今天的 `runComponentUpdate`）。

## 4. 语义裁决（把上一轮遗留的开放问题**定死**）

> 上一轮 `架构重构意见.md` §6.7 留了 3 个开放问题，另有两个隐藏分歧（攻击/左键语义、能量档位）。以下是**最终裁决**，后续不要重新讨论；若要推翻，必须给出与本节同级的证据。

**D1 · 不做能力原子化。** 不把技能拆成 `onCast`/`onAttack`/`onDrop` 等原子能力；按**语义域**抽 `HotbarActionable` / `CombatHook`。依据：`onAttack` 仅 2 个实现、`onLeftClick` 仅 1 个实现；写作单位是"一技能一文件"。`onAttack` **独立**保留（触发源、上下文 `victim`、门槛都不同）。

**D1-补 · 技能与主武器合并（修正本文早期版本与设计文档 §4.2 草稿）。** 二者合并到 `ActiveComponent`，用 `kind()` + `CombatHook` 区分；`PassiveSkill` 保持独立（不实现 `HotbarItem`）。依据：二者写同一个 `slotMap`、`updateHotbar` 对它们做同一件事、两张冷却表与 7 个同形 handler 纯冗余、**`RoleAPI` 对外早已是通用 id 查询**、两个 PDC key 对下游零引用。**装配 API（`addSkill`/`addMainWeapon`）与 `Skill`/`MainWeapon` 两个薄子类保留**，因此 10 个组件文件与 `RoleRegistry` 无需改动。完整等价清单见设计文档 §4.2。

**D2 · 框架只做「检查与反馈」，不替组件决策。** precheck 只读声明字段、无副作用；组件保留全部决策权；框架提供 `tryConsume` / `cooldown().start(ticks)` / `NO_COOLDOWN` 三个显式原语。

**D3 · 冷却 = 默认统一 + 两个逃生舱；不引入 `Channeled` 接口。**
- 默认：`CastResult.CAST` → 框架按 `getCooldownTicks()` 启动。
- 逃生舱①：`CastResult.NO_COOLDOWN`（覆盖 `MeiqiheziJuejueMainWeapon` 的"不进冷却"路径）。
- 逃生舱②：组件直接 `svc.cooldowns().start(ticks)`（覆盖 `RedDeeplySorrowSkill.java:46` 的引导期刷新）。
- **不引入 `Channeled`**：只有 1 个引导型技能，属投机抽象；引导所需的一切（起任务、刷新冷却、结束条件）用 `svc.timers().runRepeating(...)` + 逃生舱②即可表达。

**D4 · 沉默**不**打断引导（保持现状），并把它显式化。** `RedDeeplySorrowSkill` 的 `onRightClick`(`:28`) 挡了沉默，但 `update`(`:36-49`) 不再检查 —— 这是**有意保留**的既有语义，本次重构不改（改它属于游戏行为变更）。组件若要"被沉默即打断"，写法是显式三行：在 `update` 里 `if(!svc.buffs().canCastSkill()){ running=false; svc.cooldowns().start(cooldownTicks()); return; }`。

**D5 · 能量档位留在组件里。** `MeiqiheziJuejueMainWeapon` 的 `20` / `5` **不**提升为 `Map<Integer, Effect>` 之类的档位模型（无第二个使用者）；只要求把它们提成类顶部的 `private static final` 命名常量，**数值不变**。

**D6 · 死亡语义与资源所有权。**
- 死亡时立即 `clearRole` 是**现状**（`PlayerListener.java:21-27`），本次**不改**；但与 `SHDFGamePlugin` 的"断线/死亡保护 + 复活点"假设不一致这件事，必须在 `docs/` 里写成一条明文的跨插件语义约定，并在阶段 0 与下游确认一次。
- `RoleInstance.clear()` 的药水清理必须改成**记账式**：只移除本系统（`BuffManager` / 装备被动 / 技能）通过本系统施加的效果；**不得**再无条件清空玩家所有药水效果（O-7）。

**D7 · 组件间通信 = `getComponent` 直接调公开方法（作者裁决，取代早期的"类型化接口"方案）。**

    **方向与唯一不变量**：集合差必须**正序**（`-Anchor` = **改动前**日志、`-Current` = 本次日志），报告须**显式打印方向**；**唯一不变量是 `C) OTHER = 0`**（或逐行解释）。⚠️ **"`A) oshi` = 0"不可写死** —— A 是否为 0 取决于**所选锚点那次起服是否恰好也打了 oshi 行**（实测：正序 `9/13 → t2 22:01` 得 `A=3 / B=0 / C=0`；反向时同样 3 行会落在 `REMOVED` 侧）。
  - **锚点不可自证（防循环论证）**：某阶段的"改动前"锚点**必须早于该阶段的改动**。反例：t2 的起服（22:01:08–22:01:19）发生在其两个装备被动改动（21:55–21:58）**之后** → 它**不能**用作 t2 自己的"无新增 ERROR"对照（等于拿改造后的日志证明改造没引入新错误）；它作为**阶段 1 及以后**的"改动前锚点"才是正确用法。t2 自身若需对照，只能用 **09-13 那份**，并声明其代码时点早于 A/B 两流改动（A/B 引入的问题不计入本阶段新增）。

  按此口径，"3 条 oshi WARN 不属新增 ERROR"是**规则自动得出**的，不需要每个阶段靠人解释；也避免了"按全量行数比对时任何一条新 INFO 都会让总数漂移"。每个阶段的交付小结与验证报告都按这两门给数。

**机器人优先（举证责任前移）**：需要客户端行为的项，**先试机器人**（能读服务端→客户端数据包：属性、药水、物品栏）。尝试必须留痕：**脚本/命令路径 + 连接或断言的关键输出 + 时间点**；**仅写"机器人不可用"= 视同未尝试 → high finding**。机器人**不能**读客户端视觉呈现（显示名渲染等）。

**探针判定必须三态 + 证据强度单列**：
- **测得值（三态）**：`true`（测得为真）/ `false`（**测得为否，按缺陷处理**）/ `null`（**未测到，不得计为通过**）。三者不得混成一个 `false` —— "仪器没测到"与"实现是坏的"是两件事。
- **证据强度是独立字段**：`E_evidenceStrength ∈ {strong, vacuous}`。"vacuous"= 断言测得为真但**空转**（例：掉线前根本没有药水存在 → "无残留药水"为真却什么都没证明）。**强度不得污染测得值**：测得值仍按实际测量给 `true/false/null`。
- **退出码必须同时编码两者**：`0` = 全真且无 vacuous；**`4` = 全真但存在 vacuous**（**证明力不足，不得当强证据**）；`2` = 有 false；`3` = 有 null。**优先级：`false > null > vacuous`，即 `2 > 3 > 4 > 0`** —— 任何"**既有 vacuous 又有 false**"的混合情形**必然出 `2`**、"既 vacuous 又有 null"必然出 `3`，**`4` 不与 2/3 并存**（评审 T10 的精确订正）。该语义已由仪器自检**逐一断言四条分支**（`exit_allTrue_strong_is_0` / `exit_allTrue_vacuous_is_4` / `exit_anyFalse_is_2` / `exit_anyNull_is_3` / `exit_falseBeatsVacuous_is_2` / `exit_nullBeatsVacuous_is_3`）→ **不是文档声明，而是被证明可达**。
- 交付小结中每项按**三件套**定档：**测得值 + 强度 + 依据**（例：`E_effectsCleared = true / vacuous / primedBeforeQuit=false`）。
- 凡"只写在注释或报告文本里、不进判定路径"的状态，等于**没有约束**（见下条），**必须**由退出码或 verdict 字段承载。

**断言必须逐项覆盖验收判据的每一项读数（P-1 的教训）**：若验收写"两个读数"（如"最大血回到 20"**与**"无残留药水"），探针的 verdict 就必须有**对应两条断言**。本轮曾出现：判据要求"无残留药水"，而 `snapshot()` 已采集 `effects`、verdict 里却**没有一条断言它** → 跑完会输出"全部断言为真 → 运行实测通过"，用**一个通过的表态覆盖一个从未被测量的项**（与"以代码形态倒推"同构）。交付前须做一次**判据 ↔ 断言**逐项对照。

**注释里的告示不算约束**：若某个状态（如 vacuous / "证据为空转" / "未测到"）只写在注释或说明文字里、而**不进 verdict 与退出码**，就等于**没有约束** —— 必须落到**判定路径**上。本轮实例：`E_effectsCleared` 的 `unmeasured` 分支是**死代码**（上游恒为数组），且 `primedBeforeQuit` 未被 verdict 读取 → 未测到时仍会打印"全部为真"。**加注释 ≠ 修判定路径。**

**自检 / 单测的 stub 数据必须来自「实测报文」，不得沿用被测代码的字段假设**（F-3 的教训，2026-09-16）：
- **实例**：探针的属性修饰符检测谓词只读 `m.key || m.name`，而 **mineflayer 把修饰符标识放在 `uuid` 字段**（**报文实证**：`{"uuid":"shadowhunterrolesplugin:role_health_modifier","amount":20,"operation":0}`）→ 谓词**恒为 false** → `C_persistence_modifierGone` **无条件为 true** → I-16 的"持久化"半边变成**"未测而判通过"的假阳性**。
- **为什么自检没抓到**：**旧版自检的 stub 恰好用 `key`/`name` 形状 —— 与错代码同源**，于是 14 项断言"通过"只是把 bug **认证**了一遍（测试镜像了 bug）。**结构性核验（三态可达、退出码、接线）不能替代对「报文事实 / 字段名」的独立核对。**
- **规则**：① stub 的**字段形状与取值必须来自真实报文或真实运行观测**；② 仪器每次改动后**先在排练环境跑一次**再交付（本轮正是排练抓到的 F-3）；③ 涉及具体数据结构的判据，必须由**第二个独立路径**交叉核对（如 t7 对 C 槽另用日志/属性两路）。
**期望字符串必须取自被测命令的实际分支**：本轮已发生一次真实教训 —— 探针曾用 `You have no role yet`（只在 `RoleCommand.handleClear:189/:192`）去匹配 `/role energy get` 的回执，而该路径实际发 `<名> has no role!`（`:112`），导致**判据恒 false、正确实现被判成未通过（假阴性）**。仪器错 → 结论错，且比不测更危险。

**文件证据必须锚定版本（本轮两次预检空转的教训）**：凡报告"某文件有问题"或引用某文件的内容，**必须带上该文件的版本标识**。同一路径在两小时内可能有多个版本（本轮探针脚本 21:58:49 / 9 235 B → 22:01:48 / 11 971 B → 22:03:03 / 12 185 B），不带版本标识的复检会**核到旧版并空转一轮**，甚至据此下错结论。这条同时适用于实现者、验证者与评审者。

**版本一律以「字节数 + mtime + SHA256」认定（**默认指"文件内容的 SHA256"**；若引用 git blob 哈希等其它算法，必须注明是哪一个 —— 两者不同且都自洽）；另注意**行尾**：git 对部分文件报 `LF will be replaced by CRLF`，**跨检出副本的原始字节可能不同** → 比对副本时先固定行尾，或统一采用 git blob 哈希。**根因（2026-09-16 实测）：本仓库 `core.autocrlf=true`** —— `git worktree`/`checkout` 检出时会把 **LF 转成 CRLF（字节 +5）**：实测 `gradle.properties` 在**主树 = 116 B/LF**、在 **worktree = 121 B/CRLF**（⇒ 哈希不同）。**教训：用 worktree 做"纯净树"验证时，凡要把字节/哈希与主树或快照比对，必须先归一化行尾、或统一改用 git blob 哈希；否则会得到"疑似漂移"的假象**（本轮评审即遇到一次并自行查明，未误报为缺陷）**，行号与"行数"都不可作为版本标识**：同一份 11 971 B 的文件，两个工具分别数出 **215 行**与 **165 行** —— 成因是 `Get-Content | Measure-Object -Line` **不计空行**（同一个坑也造成了本指南早期"4 811 / 4 825 行"的分歧：全行口径 = 4 825，不计空行口径 = 3 831）。因此**引用行号时必须同时给出该行的内容片段**，否则复检方无法判断你指的是哪一版。

**引用"正在被编辑的文件"时：给「当场取值 + 复现命令」，不要手抄哈希**（本轮空转 3 次的止损经验）：同一脚本 10 分钟内出现 8 个版本，任何手抄的哈希都可能在你发出消息时就已经过期。正确做法：① 写"**当场取值**"（执行命令得到的输出）；② **附可复现命令**（如 `Select-String -Pattern "effSrc"` 命中的行、或 `node <script> --selftest`），让对方**自己取当前值**；③ 需要固定版本时，只认**结果文件自带的身份**（见上条）。**"我声明改好了"不是证据，"你能自己跑出同样的值"才是。**

**双边举证（判"不符"的一方也要自证）**：任何"未修 / 与磁盘不符 / 版本错位"的结论，**必须附判定方当场实测的 `(bytes, mtime, SHA256)`**，否则不予采纳。理由：本轮 4 次版本错位中，有多次是**复检方读到的是旧版**而声称"未修"——单边举证无法区分"对方没改"与"我读旧了"。**举证责任是双向的。**
**引用粒度要按对象选（本轮实证）**：① **数值身份（bytes/mtime/SHA256）**用于**锁定交付物与仪器**；② 对**会持续演进的文档**，改用**叙述式引用（章节号 + 内容片段）** —— 实例：`阶段0-1-评审报告.md` 对 t7 报告的引用**全是章节号**（§4/§5.1/§6/§7.1），因此对 t7 报告的**三次身份变更完全免疫**（grep 历史哈希 = 0 命中）；而同期**消息里的哈希引用四次落空**。→ **"锁死器物用哈希，指向论证用章节"。**
**计数类结论必须先测量、并把命令与输出留案（本轮最强教训）**：行数 / 项数 / 命中数 / 字节数一律"**先跑命令，再写进消息**"。本轮实证：一处 "§6.1 = 11 项 / 10 行" 的计数由**肉眼读表**得出，被下游（评审 → 队长 → 收口记录）一路转写，最终由**两方独立复算**推翻 —— 正确值是 **12 行 / 14 个 O 编号**（**行与编号是两个口径，引用必须写明是哪一个**；同理见"字符串侧 4 行 / 代码区 6 行"）。**"我没跑就说了"会复发，唯一防法是留下命令与输出。** 该条同时适用于队长与评审 —— 本轮双方各失守一次。（若必须写数值身份，请写明"以现算为准"。）

**仪器身份必须钉死 —— 机制是「结果自绑定」，且**取消事前公告**（eng-验证 实测论证）**：
- **"改完先公布哈希"这个流程本身有竞态，必然失败**：本轮同一个探针脚本累计出现 **6 个版本**（9 235 → 11 971 → 12 185 → 12 881 → 15 621 → 15 962 B），其中 **3 次"冻结/最终"公告在发出时即已过期** —— 公告里的 SHA256 **在磁盘上根本不存在**，结果因此无法归属。**这不是某个人的疏忽，是流程缺陷。**
- **规则：不要事前公告哈希。** "**最终版**"的定义 = **产出该结果文件的那一版**。
- **推荐流程（一次成型）**：改 → **跑一次** → 直接贴结果文件自带的 `meta.scriptIdentity`（`{bytes, mtime, sha256}`）+ `meta.probedAt`。**因为身份来自"实际跑过的那一版"，所以不存在"公告的身份在磁盘上不存在"这种失败模式。**
- **可靠机制**：仪器**运行时读自身字节算哈希**（如 `fs.readFileSync(__filename)` + `crypto`），把身份与运行时刻写进**结果文件**。**只有"实际跑过的那一版"的身份才算数。**
- **验证流程固定为**：读结果文件里的身份 → 对**当时磁盘上的仪器文件**复算比对 → 不一致即判「结果与仪器版本不符」并出 finding。
- **时区提醒**：`mtime.toISOString()` 是 **UTC**，而人工写消息多用本地 `+08:00` —— 同一时刻的两种写法，**不要据此判"不一致"**，一律换算到同一时区再比。
- 交付/引用实测证据仍须写明：**仪器身份（取自结果文件）+ 运行时刻 + 环境身份**（jar SHA256 / 起服时刻 / `run\plugins` 清单 / 日志路径）。
- **被引用的仪器版本必须可复原（本轮新增教训）**：`.scratch\bot\` **不在版本控制下** —— 被覆盖即**永久丢失**。本轮实例：被公告为"最终冻结版"的 `15 621 B / 29B421B9…` 已不可复原，导致"只对该版复检一次"的指令**根本无法执行**（复检方只能改对"现存唯一版本"复检）。
  → **规则：凡要作为证据引用的仪器版本，引用前先复制出带哈希的副本**（放入仓库内或其它受管位置），或把它纳入版本控制。**"身份可核"不等于"产物可复原"，两者都要。**

## 8. 新组件写作模板（阶段 4 之后生效）

**新增一个技能 = 1 个新文件 + 1 行注册**（角色装配在 `RoleLoader` 里）。

```java
package com.shadowHunterRolesPlugin.roleComponent.red;

/** 目标形态（阶段 4 后）。数值必须与设计表逐字一致。 */
public final class RedExampleSkill extends Skill {   // Skill extends RoleComponent implements HotbarItem, HotbarActionable

    private static final int COOLDOWN_TICKS = 120;
    private static final int ENERGY_COST    = 0;
    private static final double RADIUS      = 5;

    public RedExampleSkill(ComponentServices svc) {          // ← 构造期注入，不是回调参数
        super(svc, "red_example_skill", Component.text("示例技能"),
              Component.text("对5格内敌人造成3秒致盲"), COOLDOWN_TICKS, ENERGY_COST, Material.REDSTONE);
    }

    @Override
    public CastResult onCast(CastSignal signal) {            // ← 只收本次调用特有的信号
        // 1) 组件自己的复杂判定（框架不替你做）
        if (!svc.buffs().canCastSkill()) return CastResult.REJECTED_DISABLED;

        // 2) 提交原语（检查+扣减合一；失败自己决定怎么办）
        if (ENERGY_COST > 0 && !svc.energy().tryConsume(ENERGY_COST)) {
            return CastResult.REJECTED_NO_ENERGY;
        }

        Player self = svc.self().player();
        for (Player victim : self.getLocation().getNearbyPlayers(RADIUS)) {
            if (!svc.factions().isHostile(victim)) continue;
            victim.addPotionEffect(PotionEffectType.BLINDNESS.createEffect(61, 1));
        }
        self.getWorld().playSound(self.getLocation(), Sound.ENTITY_WITCH_CELEBRATE, 1, 1);

        return CastResult.CAST;      // 框架按 COOLDOWN_TICKS 启动冷却
    }
}
```

**必须遵守**：
1. 不 `import` 插件主类、不 `RoleManager.getInstance()`、不 `Bukkit.getScheduler()`（`getContext` 系列已整体删除，见 D7）。
2. 起任务一律 `svc.timers()`（`runLater`/`runRepeating`/`track`），**不要**裸 `new BukkitRunnable()`；`stop` 后框架会兜底取消（I-4）。
3. 有 `start` 就必须有对称的 `stop`；跨组件引用用 `getComponent(X.class)` 在 `awake` 里解析并缓存到字段、在 `stop` 里置空；声明式依赖写进 `RequiresComponents`（可选）。
4. 组件间通信 = `getComponent(具体类.class)` 直接调公开方法，**并判空**；**只允许同角色包内**的具体类耦合。
5. `Player` 不得存进长生命周期字段或长期任务闭包（只能存 UUID 或每次实时取）。
6. 数值提成类顶部命名常量；不要在方法体里留裸数字（除非是几何/特效参数，如 `0.5` 偏移）。
7. 组件不碰热键栏：不造 `ItemStack`、也不请求刷新（`markDirty()` 是框架内部 API，置脏点在端口适配器与 ticker poll 里）。

> 完整模板与纪律清单见 `docs/组件系统设计-Unity风格.md` §12。

| 事实 | 结论 |

## 附录 B-补 · 宿主环境坑位与证据文件纪律（实测积累，全队复用）

**PowerShell / 文件编码**
1. `.ps1` **不能**用 `& .\x.ps1` 直接跑（执行策略）→ 用 `powershell -NoProfile -ExecutionPolicy Bypass -File <脚本>`。
2. **PS 5.1 把无 BOM 的 `.ps1` 当 ANSI 读** → 脚本里含中文会破坏解析（实测报 `Unexpected token '}'`）→ **`.ps1` 一律 ASCII-only**，路径用 `$PSScriptRoot` 派生。
3. **BOM 陷阱（PS 5.1 与 PS 7+ 语义相反，务必看清）**：PS 5.1 下 `Out-File -Encoding UTF8` **写 BOM**（首字节 `FF FE` 或 `EF BB BF`），而被其它工具解析的产物（如 JSON）会**直接解析失败**：实测 `runserver-identity.json` 曾被写成带 BOM → Node `JSON.parse` 报错；同族还有 `javac 非法字符: '\ufeff'`。**另：PS 5.1 的 `>` 重定向同样写 UTF-16LE（带 BOM）** —— `node … --selftest > st.txt` 之后再 `JSON.parse` 会报 `Unexpected token`；**取 JSON 输出不要用 `>` 落盘再解析**。**正确写法**：
   - 文本日志：`[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($false)))`；
   - 仅 PS 7+ 才有 `-Encoding utf8NoBOM`（**5.1 没有**；5.1 的 `utf8` = 带 BOM）。
   → **凡落盘产物（日志 / JSON / 清单）一律无 BOM**；交付前用首 3 字节或 `JSON.parse` 自检一次。已踩过：`docs\t2-build-x.txt` 等 4 个 UTF-16LE 文件（1611/2570 个 NUL）。
4. JDK 工具 `jps/jcmd/jstack/javap` **不在 PATH**（只有 `java` 经 Oracle `javapath` 在 PATH）→ 需用全路径 `C:\Program Files\Java\jdk-21\bin\`。

**构建新鲜度**
5. **`build\classes` 目录 mtime 不是信号**（实测目录停在 `2026-08-08`，其中 `.class` 是 `2026-09-16 21:59:12`）→ 判据取**目录下最新 `.class` 文件**的 mtime。

**证据文件命名与留存**
6. **证据文件用 `阶段N-` 前缀**，不要用裸 `tN-`：本轮出现过**同名碰撞** —— 上一轮会话（A 流）的产物叫 `docs\t2-*.txt`，而本次重构的 t2 也是同名任务，两者易被当成同批证据。

**脚本调用**
9. **调用"会写产出文件"的脚本时，绝不可截断 stdout**：`| Select-Object -First N`（或任何提前关闭管道的写法）会让脚本**后半段不执行** → **静默丢失产物文件**，且退出码会变成异常值。实测：本轮用 `| Select-Object -First 14` 调 `log-delta.ps1` → 报告文件**未写出**、`exit = -1`；去掉截断即正常。**适用于 t7 要跑的四个脚本（`log-delta` / `numeric-multiset` / `collect-runserver-identity` / 探针）。**
10. **`.ps1` 一律 ASCII-only，且要自检**：实测有脚本第 7 行含非 ASCII（`(eng-验证)`）—— 本次侥幸跑通，但"PS 5.1 把无 BOM `.ps1` 当 ANSI 读"的坑正是靠这条规则规避的（同类脚本首版就报过 `Unexpected token`）。**非 ASCII 自检应作为准入检查**（t7 已按此执行），标识用 `eng-verifier` 之类纯 ASCII 写法。**本项目已因此踩两次**（另一次是给采集脚本加中文注释 → `Unexpected token` + **JSON 静默保留旧值**）；自检命令：`(Get-Content x.ps1 -Raw) -match '[^\x00-\x7F]'` 必须为 `False`。
