# 0001 · 允许组件覆写识别键与状态文案

- **状态**：已采纳（当前有效）
- **对象**：热键栏物品的**识别键**（`skill_id` / `main_weapon_id`）与**六条状态文案**的产出权

## 背景

热键栏物品的产出权已经交给组件（组件通过 `buildItem()` 产出完整物品）。识别键与状态文案原本是框架独占的输出面：识别键决定物品点击后走哪条处理链、清除角色时扫不扫得到；状态文案表达四态（冷却 / 禁用 / 能量不足 / 就绪）的可见结果。

产出权交出去之后，这两类东西是否也允许组件覆写，是一个必须回答的问题——默认画法在组件基类里已经会写它们，但"框架是否在最后一步强制覆盖"是另一个决定。

## 决策

**允许组件覆写**这两类：组件在 `buildItem()` 里可以自己写识别键、自己决定状态文案；框架**不再**在最后一步强制写键，也不再强制状态文案的字面内容。

## 被放弃的替代方案

**替代方案（不开放覆写）**：框架在装饰序列的**最后一步**写识别键，六条状态文案固定由框架产出；组件只能改材质、显示名与描述行。

放弃它的理由：那会让"自定义物品识别"与"自定义状态文案"必须改框架本身——一旦有角色需要不同的识别方式（例如想让自己的物品多带一个标记），或者需要不同的文案（本地化、风格化），唯一出路是动框架代码。

## 后果（含代价）

**放弃的保障**：

- 「**第三方改不坏外观**」不再由框架保证 —— 它退化为**组件基类的默认约定**：不覆写就跟框架一致，覆写就自己负责。
- 与之连带：外观的**跨版本逐字对拍**只在"没有第三方覆写"的前提下成立；一旦有组件覆写，同一段代码在不同安装上可以呈现不同外观。

**两条具体的玩家可见代价**：

1. **识别键写错 ⇒ 点击物品没有任何反应。** 物品点击的处理链在入口处按识别键判断"这是不是本插件的物品"，判定失败就直接返回；玩家看到的是"技能按了没反应"，而不是任何报错。
2. **识别键缺失 ⇒ 清除角色时物品残留。** 清除角色时按识别键清扫快捷栏槽位；扫不到的物品会**留在玩家背包/快捷栏里**，并可以继续被拿在手上。

**其余代价**：默认画法里的写键步骤因此不是"收口点"，阅读代码时不能假定它一定生效。

## 门槛自证

- **难以回退**：把"允许覆写"收回成"框架强制写"，等于宣布所有已经依赖自定义识别键/文案的组件失效——要迁移它们的物品识别方式与文案，并重新验证点击与清除两条链路。
- **缺上下文会令人困惑**：默认画法里明明写了识别键、状态文案也写死在基类里，读者会问"既然写了，为什么还允许别人改掉它"——不解释就会误以为框架在保证外观一致。
- **是真实取舍**：确实评估过"框架最后一步强制写"这条路（它换来"第三方改不坏外观"），是因为自定义能力才选了开放。
