## 1. 新增一个技能（Skill）

### 1.1 文件放哪里
`src/main/java/com/shadowHunterRolesPlugin/roleComponent/<角色包>/skill/<名字>Skill.java`
（例：`roleComponent/meiqiHezi/skill/`、`roleComponent/red/`；**同角色包内**才允许互相 `getComponent`，跨角色引用是设计错误 —— `debug-logs/组件系统设计-Unity风格.md` §4.4 纪律 4）

### 1.2 骨架（**当前唯一形态**：`onCast` + 端口）

> **阶段 4 收尾后只有一条派发路径**：组件实现 `onCast(CastSignal)` 并返回 `CastResult`；**冷却由组件自己启动**（在施放成功处 `svc().cooldowns().start(getCooldownTicks())` —— 框架**不再**代启动，详见 架构文档 §4.2）。**没有** `markMigrated()`/`isMigrated()` 标记，也**没有**旧回调（`onRightClick/onLeftClick/onDrop(RoleInstance)` 已删除）。

```java
package com.shadowHunterRolesPlugin.roleComponent.meiqiHezi.skill;

import com.shadowHunterRolesPlugin.core.Skill;
import com.shadowHunterRolesPlugin.core.dispatch.CastResult;
import com.shadowHunterRolesPlugin.core.dispatch.CastSignal;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import net.kyori.adventure.text.Component;
import org.bukkit.Material;
import org.bukkit.entity.Player;

/** 示例技能：3 格内敌人吃 6 点物理伤害，自己回 2 点生命。 */
public class MeiqiheziSampleSkill extends Skill {

    private static final int COOLDOWN_TICKS = 100;   // 5 秒；必须与构造器实参一致（组件据此自启冷却）
    private static final int ENERGY_COST = 10;
    private static final double RADIUS = 3;
    private static final double DAMAGE = 6;
    private static final double HEAL = 2;

    /** 由容器经 `ComponentFactory.create(id, services)` 调用；**id 在装配处声明**（见 §4），组件不再自带常量。 */
    public MeiqiheziSampleSkill(String id, ComponentServices services) {
        super(id, services,
              Component.text("示例技能"),                  // 显示名
              Component.text("3 格内敌人受伤，自身回血"),   // 描述
              COOLDOWN_TICKS, ENERGY_COST, Material.PAPER);
    }

    @Override
    public CastResult onCast(CastSignal signal) {
        if (!svc().buffs().canCastSkill()) return CastResult.NO_COOLDOWN;        // 沉默/眩晕：不启冷却
        if (!svc().energy().tryConsume(ENERGY_COST)) return CastResult.REJECTED_NO_ENERGY;

        Player caster = svc().self().player();                                   // 每次现取，不存字段
        for (Player victim : caster.getLocation().getNearbyPlayers(RADIUS)) {
            if (!svc().factions().isHostile(victim)) continue;                   // 未选角色的玩家也算敌人
            svc().damage().physicalDamage(victim, caster, DAMAGE);               // 真伤用 trueDamage(...)
        }
        svc().vitals().heal(HEAL);
        svc().cooldowns().start(getCooldownTicks());                            // 冷却由组件自启（框架不再代启动）
        return CastResult.SUCCEED;                                              // 仅表示"施放成功"
    }
}
```

- 端口白名单见 `docs/插件文档/架构与组件模型.md` §2；**一个端口方法都不许多用**（含 R-1 的 `applyPotionEffect` 方法族）。
- **冷却由组件自管理**（框架不再代启动）：在施放成功处 `svc().cooldowns().start(getCooldownTicks())`。`start(int)` 是**重启语义**（按调用时刻重算、覆盖旧值、不叠加）；**`boolean end()`** 可**主动结束冷却**（在冷却中 ⇒ 清条目 + 回调 `ENDED_BY_COMPONENT` + 一次刷新 + **返回 `true`**；否则 **返回 `false`**、无副作用）（**签名变更属已批准变更：`bd726cf`，用户 D-list 裁定**）；**到期由框架每 tick 扫描移除**并回调 `EXPIRED`（O-21 已关闭）。想收尾自己的状态就覆写 `onCooldownEnd(CooldownEndReason reason)`（`ActiveComponent` 上的默认空实现，枚举值 `EXPIRED / ENDED_BY_COMPONENT / RESTARTED`）。完整契约见 `架构与组件模型.md` §4.2。
- **没有"迁移标记"**：`markMigrated()`/`isMigrated()` 已随 T-2 ① 删除；新组件**不需要**任何注册/标记代码，写出来也编译不过。
- **没有旧回调**：`onRightClick/onLeftClick/onDrop(RoleInstance)` 已随 T-1 ④ 删除；照老资料写这些方法不会被调用（父类亦无这些方法）。
- 装配在 `registry/RoleLoader`（见 §4）：`.addSkill(ID_XXX, MeiqiheziSampleSkill::new, slot)` —— **id 常量在装配处声明**，组件构造器只负责接收。

### 1.3 （原"骨架 B：新管道写法"已并入 §1.2）

> **历史说明**：迁移期曾并存"旧回调骨架（A）/新管道骨架（B）"两套写法，并用 `markMigrated()` 决定走哪条路径。阶段 4 收尾后只剩一套（= §1.2）；老资料里的骨架 A（`instance.decreaseEnergy(...)` / `instance.startSkillCooldown(...)`）属**迁移期**写法，**现在照抄不会生效**。

### 1.4 需要"延时/周期任务"的技能

- 用 **`svc().timers()`**：`run(Runnable)` / `runLater(delayTicks, Runnable)` / `runRepeating(initialDelay, period, Runnable)` —— 任务**创建即登记**进本组件资源表（`core/ports/TimerPort.java`）。
- 取消：在**新无参 `stop()`** 里 `task.cancel()`（样板：`MeiqiheziCircleSlashSkill.java` 的 `castTask` + 新 `stop()`）。**框架还会兜底取消**资源表（`stop()` 返回后 `cancelAllAndClear()`）⇒ "忘了取消"也不会泄漏，但**仍应显式取消**（重复取消幂等）。
- **实例失效守卫**：旧写法 `instance.isValid(){task.cancel();return;}` 已随迁移消失 —— 实例失效 = 角色被清除 = 你的 `stop()` 已被调用 + 资源表被兜底取消；任务体内只需保留**与玩家状态相关**的守卫（如 `caster.isDead() || !caster.isOnline()`）。
- **不要**直接 `Bukkit.getScheduler()`（全仓唯一允许点是 `platform/BukkitSchedulerAdapter.java`）；组件侧也**不要**再用 `rolesContext()`（组件侧已归零，用端口）。

### 1.5 不要覆写渲染
组件的 `createIconItem(RoleInstance)` / `getDisplayName(RoleInstance)` 是**旧渲染**（设计 §4.3 已把它们移出 `ActiveComponent`）：**组件侧覆写已全部删除**（现算 `roleComponent/**` 内 = 0）；仅**基类 4 个方法**仍活（`core/Skill.java` 2 个 + `core/MainWeapon.java` 2 个，属 T ⑦ 未收口部分）。新组件**不要**再写这两处覆写；统一渲染器的接管清单见 `debug-logs/阶段4-4.4渲染器接管预案.md`。

```java
    public void stop() {

    }

    @Override
    public void update() {

```

要点：
- 基类是 `PassiveSkill extends RoleComponent`，**被动不实现** `HotbarItem`/`HotbarActionable` ⇒ 它天然不能被施放（`core/PassiveSkill.java` 的注释）。
- 生命周期钩子是**基类 default 方法**（`awake()` / `start()` / `stop()` / `update()`），按需覆写即可 —— **不需要**再 `implements LifecycleAware/UpdateAware`：那四类 `*Aware` 接口**已随 T 块删除**（`core/RoleComponentAware/` 目录不存在），照抄旧写法会编译不过。
- `awake()` 需要"解析跨组件依赖并缓存"时才覆写（`getComponent(X.class)`）；它必须**幂等**、不得改动任何玩家可见状态。
- 想在 SanTE 归零时做点什么：覆写 **`onSanTEChange(int pre, int now)`**（基类钩子，无 `Player`/`RoleInstance` 参数；用 `svc().self().player()`）—— 样板 `roleComponent/DefaultSanTEZeroPunishment.java`。
  - **派发口径（现状）**：容器在 `setCurrentSanTE` **发布事件之后直接派发**（不经 Bukkit 事件总线）；**`pre == now` 不派发**；**不要再**通过监听 `SanTEChangeEvent` 或 `RoleEventListener` 接收组件通知（该转发已删除；事件的对外发布保留，仅作第三方挂点）。
  - **重入护栏**：在钩子内直接改写 SanTE 是允许的 —— 派发期间的重入写入会被**合并**，本次派发返回后按**末次值补发一次**（不递归、也不漏）。
- **有 `start` 必有对称 `stop`** —— 本工程已经因为"只发不收"踩过坑（装备被动 stop 回收是阶段 0 的收口项，见 `debug-logs/阶段0-交付小结.md`）。

## 3. 新增一个主武器（MainWeapon）

文件：`roleComponent/<角色包>/mainWeapon/<名字>MainWeapon.java`。

```java
package com.shadowHunterRolesPlugin.roleComponent.red;

import com.shadowHunterRolesPlugin.core.MainWeapon;
import com.shadowHunterRolesPlugin.core.dispatch.AttackSignal;
import com.shadowHunterRolesPlugin.core.dispatch.CastResult;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import net.kyori.adventure.text.Component;
import org.bukkit.Material;
import org.bukkit.entity.Player;

/** 示例主武器：攻击造成 8 点物理伤害并击退 1。 */
public class RedSampleMainWeapon extends MainWeapon {

    private static final int COOLDOWN_TICKS = 100;   // 5 秒
    private static final double DAMAGE = 8;
    private static final double KNOCKBACK = 1;

    /** 由容器经 `ComponentFactory.create(id, services)` 调用（id 在装配处声明，见 §4）。 */
    public RedSampleMainWeapon(String id, ComponentServices services) {
        // 注意参数顺序：icon 在 cooldown 之前（与 Skill 相反，且这个顺序被冻结）；energyCost 恒传 0
        super(id, services, Component.text("示例之刃"),
              Component.text("攻击造成物理伤害"), Material.IRON_SWORD, COOLDOWN_TICKS);
    }

    @Override
    public CastResult onAttack(AttackSignal signal) {
        Player attacker = svc().self().player();                       // 攻击者永远是自己
        Player victim = signal.victim();
        svc().damage().physicalDamage(victim, attacker, DAMAGE, KNOCKBACK);   // 4 参 = 物理伤 + 击退
        return CastResult.SUCCEED;                                     // 框架按 getCooldownTicks() 启冷却
    }
}
```

要点：
- 主武器**只受眩晕限制**（不受沉默）：`svc().buffs().canUseMainWeapon()` / `canCastSkill()` 的差异由框架的闸门语义决定。
- 攻击路径：`listener/MainWeaponListener.onAttackPlayer` → `RoleInstance.handleAttack`（`core/RoleInstance.java:191`）→ `CombatHook.onAttack(new AttackSignal(victim))`（`:199/:201`）⇒ 组件只需实现 `onAttack(AttackSignal)` 并返回 `CastResult`（**不要**自己启冷却）。
- 左键/右键/`Q` 三个入口由 `MainWeaponListener` 转发到 `RoleInstance` 的对应入口，最终同样走 `onCast(CastSignal)`（**与技能同一条管道**）。
- 主武器**没有 `energyCost`**：`MainWeapon` 构造器恒把 energyCost 传 `0`（`core/MainWeapon.java`），这样武器图标不会多出一个今天不存在的 `ENERGY LACK` 状态。

### 4.3 硬规则（违反会在装配期抛异常、该角色**不会被注册**）
| 规则 | 事实 | 出处 |
|---|---|---|
| 组件 id **跨类型唯一** | 技能/被动/武器共用一个命名空间，重复即抛 `IllegalArgumentException(type + " already registered: " + id)` | `core/Role.java:232-237`（O-10 修复） |
| 槽位只能是 `0..8`，且不可冲突 | 非法槽位/冲突都抛异常，**不再"告警 + 覆盖"** | `core/Role.java:240-247`（O-12 / 裁决 1） |
| 角色 id 非空 | `new Role.Builder(id)` 里校验 | `core/Role.java:118-123` |
| 数值必须合法 | maxHP > 0、baseATK/maxEnergy/maxSanTE ≥ 0 | `core/Role.java:141-171` |
| 装配失败按角色隔离 | 某个角色装配抛异常 → 记 `SEVERE`、**跳过该角色**，其余照常注册；不让异常冒泡成 `ExceptionInInitializerError` | `registry/RoleLoader.java:68-88` |
| 装配顺序 = 注册顺序 | 同一类型内部按 `add*()` 的调用顺序（`LinkedHashMap`） | `core/Role.java:111-114`、设计 `debug-logs/组件系统设计-Unity风格.md` §7 分派顺序 |

### 4.4 一个容易踩的坑：**组件构造器会被执行多次**
`Role.Builder.addSkill/addPassive/addMainWeapon` **不再实例化组件**（阶段 4 收尾后装配条目是 `(id, ComponentFactory)`）：id 由**注册处**声明、组件由 `ComponentFactory.create(id, services)` 在角色实例化时才创建 ⇒ **不存在"构造器被执行两次"的问题**，构造器里做初始化也不会被提前触发。**校验**（id 非空/跨类型唯一、槽位 0..8 且不冲突）仍在 `Role.Builder` 内按**声明的 id** 完成（`core/Role.java:188-254`）。
⇒ **组件构造器必须是纯的**：不要在构造器里改玩家状态、发起任务、写静态状态。要"开始生效"请写在 `start`。

## 5. 注册与自检

### 5.1 组件不需要注册到别处
组件由角色模板的工厂方法创建：`RoleInstance.initComponents()` → `Role.createSkill/createPassive/createMainWeapon(id, services)` → **`ComponentFactory.create(id, services)`**（构造期注入）→ `componentRegistry.register(...)`。**没有**"组件清单文件"要改，也**没有** `bind` 这一步（已删除）。

### 5.2 新增角色/组件后的自检清单

| # | 检查 | 怎么做 |
|---|---|---|
| 1 | 编译 | `.\gradlew build -x copyPluginJar --console=plain`；看 `BUILD SUCCESSFUL` + 最新 `.class` mtime |
| 2 | 装配无异常 | 起服看控制台；若出现 `Role 'xxx' failed assembly validation and was NOT registered` 就是 §4.3 的校验拦下了（`RoleLoader.java:82-84`） |
| 3 | 改装配代码没把别的角色带崩 | 起服应看到 `ShadowHunter Character System enabled.`（`ShadowHunterRolesPlugin.java:87`） |
| 4 | 角色可选 | 进游戏 `/role set <id>`；回显 `Your role has been set: <id>` |
| 5 | 热键栏正确 | 0 号位主武器、1–3 号位技能；图标为角色 `.icon(...)` 或组件图标（`RoleInstance.updateHotbar`） |
| 6 | 施放正确 | 左/右/`Q` 各试一次；冷却是否按声明值启动（技能名带 `x.xs` 说明用的是 `getCooldownTicks()`） |

## 7. 禁忌清单（照抄设计 §12 的纪律，逐条可 grep）

1. **不 import 插件主类、不调 `ShadowHunterRolesPlugin.getInstance()`**（设计 `debug-logs/组件系统设计-Unity风格.md` §12 组件纪律清单）。当前 `getInstance()` 已**零调用**（`docs/插件文档/架构与组件模型.md` §6.3）。

6. **组件不碰热键栏**：不造 `ItemStack`、不请求刷新（`markDirty()` 是框架内部 API，设计 `debug-logs/组件系统设计-Unity风格.md` §12 组件纪律清单（第 6 条））。
7. **不要**再想"迁移判据"这件事：`markMigrated()`/`isMigrated()`/`USE_COMPONENT_PIPELINE` **都已删除**（阶段 4 收尾 T-2 ①③），**全部组件无条件走新管道** —— 新组件不存在"要不要标记"的问题。
8. **不要"顺手改正" id 里的拼写**：`meiqihezi_equippments_passive`、`red_equippments_passive`、`autoRecoverSanTEPassive` 都是**索引键**，改名等于换一个组件。
9. **不要改 `RoleAPI` 既有方法的签名/返回类型**：只增不改；破坏性变更只允许在**阶段 6.4** 且必须与 `SHDFGamePlugin` **同步发布**（`debug-logs/最终重构指南.md` §6.4 跨插件契约）。
10. **`ComponentServices` 成员数固定为 10**：要加端口成员必须走裁决（`core/ports/ComponentServices.java:3-9`）。
