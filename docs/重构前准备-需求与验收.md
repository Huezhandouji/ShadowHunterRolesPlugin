## 2. A 流需求：生命周期三方法 `awake` / `start` / `stop`

### 2.1 命名（**权威来源：用户直接指令**）

`onSet`/`onClear` 重命名为 **`awake` / `start` / `stop`，三个方法名一律不得带 `on` 前缀**。

理由：与既有 `UpdateAware` / `EnergyChangeAware` / `SanTEChangeAware` 的命名风格统一。

> ⚠️ 文档 `架构重构意见.md` 中部分段落仍写 `onStart/onStop`，属**过期措辞**；team description 亦然。**一律以本文件为准。**

### 2.2 目标接口形态

```java
public interface LifecycleAware {
    default void awake(Player player, RoleInstance instance) {}  // 新增阶段：只做跨组件依赖解析
    void start(Player player, RoleInstance instance);            // 原 onSet：开始生效
    void stop(Player player, RoleInstance instance);             // 原 onClear：对称拆卸
}
```

- 参数**暂保持 `(Player, RoleInstance)`**，**不**新造窄上下文类型（属后续架构阶段）。
- `awake` 用 `default` 空实现（多数组件不需要）。

### 2.3 语义映射

| 旧 | 新 | 语义 |
|---|---|---|
| `onSet` | `start` | 「开始生效」语义**整体**迁移过来：初始化数据、发放装备、注册 tick |
| `onClear` | `stop` | 与 `start` 严格对称的拆卸 |
| —— | `awake` | **仅**解析跨组件依赖并缓存引用 |

### 2.4 `awake` 契约（验收必查）

1. **幂等** —— 重复调用不产生叠加效果。
2. **不得改动任何玩家可见状态** —— 此时 `stop` 尚未调用，重入会叠加效果（如重复发装备、重复上 buff）。
3. **时序**：全部组件创建完成 → `awake` 全部 → `start` 全部 → **启动 ticker** → 渲染热键栏。

### 2.5 必须一并调整的 `RoleInstance` 构造时序

现状（`RoleInstance.java:75-101`）：

```
initComponents()(75) → new BuffManager(77) → 设生命(80-88) → updateHotbar(90)
→ 起 ticker(93-98) → triggerLifecycleOnSet()(100)
```

**问题**：ticker 在生命周期回调**之前**就启动了，而 `awake` 阶段的语义是"在 1-tick 任务尚未挂上调度器时解析依赖"。

**要求改为**：

```
initComponents → new BuffManager → 设生命 → awake 全部 → start 全部 → 起 ticker → updateHotbar
```

**必须在报告中论证**：该顺序调整对当前行为无影响（主线程同步构造，原先 ticker 启动到回调之间无任何 tick 有机会执行）。

### 2.6 配套重命名

- `triggerLifecycleOnSet()`（`:586`）→ 拆为 **awake 遍历**与 **start 遍历**两个方法。
- `triggerLifecycleOnClear()`（`:609`）→ **`triggerLifecycleStop()`**。
- 现有 3 段 `instanceof` 分支（技能/被动/武器）可保留同样结构，或改为一次遍历分派；**若改结构，必须保证调用集合与顺序不变**。
- `stop` 遍历顺序建议与 `start` 相反（逆序拆卸），并在报告中说明是否采用。

### 2.7 调试字符串裁决（**连字符串一起改**）

`TestSendSanTEAndEnergyChangeMsgPassive.java:21`/`:26` 把方法名写死成了玩家可见文案（`"onSet() triggered!"` / `"onClear() triggered!"`）。

**裁决：改为新方法名**（`"start() triggered!"` / `"stop() triggered!"`）。理由：

1. 本文件的验收标准含「全仓 grep 证明契约上再无 `onSet/onClear` 残留」，若字符串保留旧名就会出现在 grep 结果里，**留下一个需要额外解释的例外**，比改字符串本身更糟。
2. 真正要保护的"行为不变"是**游戏行为语义**（能量/伤害/冷却/层数、装备发放与回收、事件响应）。一个测试桩的调试文案不属该类；且该桩**即将被移出生产注册**（B-5），可见性趋近于零。
3. 二者取一，选"不留矛盾"的那个。

**同时硬性要求**：只改字符串内容，**不得**顺带删除这段调试输出 —— 解除该测试桩注册属 B 流（B-5），A 流删掉会与 B 流互相覆盖。
