## 1. 四条子指令 · 参数位 · 现状 / 改后

`/role` 主指令先把 `args[0]` 当子指令名剥掉，`subArgs[i] == args[i+1]`
（`command/RoleCommand.java:86-95`）。下表**「参数位」一律指剥离子指令名之后的 `subArgs` 下标**。

| 子指令 | 参数位 | 现状怎么写（file:line 证据） | 改后怎么写 |
|---|---|---|---|
| `/role set <roleId> [playerName]` | **`subArgs[1]`**（第 2 段） | `args.length == 1` ⇒ `targetName = null`；`== 2` ⇒ `args[1]`（`SetRoleCommand.java:45-52`）；解析 = `Bukkit.getPlayer(targetName)` + `isOnline()` 双查（`:75-79`） | `subArgs[1]` **接受裸名或选择器**，经 §3 统一解析为 `Player`。`args.length` 判定分支**逐字不动** |
| `/role clear [playerName]` | **`subArgs[0]`**（第 1 段） | `args.length == 0` ⇒ `null`；`== 1` ⇒ `args[0]`（`ClearRoleCommand.java:36-43`）；解析 = `Bukkit.getPlayer` + `isOnline`（`:55-59`） | `subArgs[0]` 接受裸名或选择器；长度分支逐字不动 |
| `/role energy get [playerName]` | **`subArgs[1]`**（第 2 段） | `args[0]=="get"` 且 `args.length==1` ⇒ `null`；`==2` ⇒ `args[1]`（`EnergyCommand.java:50-58`）；解析在 `:86` | `subArgs[1]` 接受裸名或选择器 |
| `/role energy set <value> [playerName]` | **`subArgs[2]`**（第 3 段） | `args[0]=="set"` 且 `args.length==2` ⇒ `null`；`==3` ⇒ `args[2]`（`EnergyCommand.java:61-69`）；解析在 `:102` | `subArgs[2]` 接受裸名或选择器。注意 `subArgs[1]` 恒为 `value`，**永不当目标** |
| `/role operation <query\|modify> [player\|@s] <componentId[#index]> [payload…]` | **`subArgs[1]`**（第 2 段，**条件性**） | `isTargetToken(args[1])` 为真才当目标（`ComponentOperationCommand.java:90-102`）；判据 = `@s`（**大小写不敏感**）或在**在线玩家名**（`:146-152`）；解析在 `ComponentOperationDispatcher.resolveTarget`：`@s`/空 ⇒ 执行者，否则 `Bukkit.getPlayerExact`（`:250-255`） | `subArgs[1]` 的判据放宽（§6），解析走 §3 同一入口 |

**「四条」的分界（防歧义）**：`command/` 包内**只有** `set` / `clear` / `energy` / `operation` 这四条子指令带玩家目标参数。
`debug` 与 `debug cooldown` / `debug sched` **只作用于执行者自己**，不接受玩家目标
（`DebugCooldownCommand.java:61-62` 把 `args[1]` 当组件 id、`:136-140` 只在执行者自己的实例上查 `#slot`/`componentId`）；
`help` 无参数。⇒ **本特性不触碰 `debug`**，`plugin.yml` 也无需改（§10）。

两条独立的证法（都可复现，见 §9 的 V1 / V2）：

1. **目录清点**：`io/papermc/paper/entity/` 下 13 条里**没有** `selector/` 子目录，逐条列出如上。
2. **负向探针**：`javap -classpath <paper-api.jar> io.papermc.paper.entity.selector.EntitySelector`

   Brigadier 解析器，**不是** `…entity.selector.EntitySelector`（本卡面的定向条件问的就是后者，答案是「不存在」）。

### 2.3 事实三：本工程的指令面拿不到 `CommandSourceStack`

- `plugin.yml` 只有一条 `commands: role:`（`src/main/resources/plugin.yml:9-19`），注册走 `setExecutor`/`setTabCompleter`
  （`RoleCommand.java:41` 实现 `CommandExecutor, TabCompleter`；`SubCommand.java:15-16` 明写「**不迁移到 Brigadier**」）；
- `CommandExecutor.onCommand(CommandSender, Command, String, String[])` 的入参里**没有** `CommandSourceStack`；
- 要拿到 `CommandSourceStack` 就得把 `/role` 迁到 Brigadier（改注册面、改类层级）—— 那是**另一个**改动面，
  本特性明确不做（§10）。

## 3. ★ 「只能选 1 名」的判定与解析口径（定案）

### 3.1 解析入口（新增一个**包私有** helper；形状由 §10 的约束决定）

```java
/**
 * 目标解析：裸玩家名 / 选择器 / "@s" ⇒ Player；任何失败/歧义 ⇒ null。
 * 唯一的拒绝判据 = 「解析结果恰好 1 名**在线**玩家」。
 */
final class PlayerTargets {                                   // 包私有 ⇒ 不扩公共面（§10）
    private PlayerTargets() {}

    static Player resolve(CommandSender sender, String raw) {
        if (raw == null || raw.isBlank()) {
            return sender instanceof Player player ? player : null;   // 省略目标 = 执行者自己
        }
        if ("@s".equals(raw)) {                                 // 大小写敏感：逐字对齐 dispatcher 既有口径
            return sender instanceof Player player ? player : null;
        }
        List<Entity> selected = null;
        if (raw.startsWith("@")) {
            try {
                selected = Bukkit.selectEntities(sender, raw);  // 契约 C1：非法 ⇒ IAE
            } catch (IllegalArgumentException malformed) {
                return null;                                    // ↑ 捕获后与"选不到"同一路径
            }
        }
        if (selected == null) {
            Player exact = Bukkit.getPlayerExact(raw);          // 与 dispatcher 既有口径逐字等价
            if (exact == null) {
                Player legacy = Bukkit.getPlayer(raw);           // 保留 getPlayer 的宽松匹配
                if (legacy == null || !legacy.isOnline()) {
                    return null;
                }
                return legacy;
            }
            return exact.isOnline() ? exact : null;
        }
        if (selected.size() != 1) {
            return null;                                        // size==0 与 size>1 同一出口
        }
        Entity only = selected.get(0);
        if (!(only instanceof Player player) || !player.isOnline()) {
            return null;                                        // @e 之类非玩家（或离线玩家）落这里
        }
        return player;
    }
}
```

**逐条理由（实现卡直接照抄即可）**：

1. **不按 token 内容分流**：`@a` / `@e` / `@p` / `@r` / `@s[tag=x]` / `@e[type=player,limit=1]` 全部走**同一把尺**
   （恰好 1 名在线玩家）。凡靠「选择器白名单」判定的写法都被 C4（只保证与原版同形）否掉。
2. **`@s` 走**字面**快路径**（`"@s".equals(raw)`）：与 `ComponentOperationDispatcher.resolveTarget`（`:251`）**已有的
   `equalsIgnoreCase` 口径**在**合法输入**上等价（`@s` 只有这一种合法写法），且**不依赖** `Bukkit.selectEntities`
   对纯 Bukkit `CommandSender` 的转换行为 ⇒ 少一处运行期假设。
   大写 `@S` **不走**快路径（它是非法选择器）⇒ 落到 `catch (IllegalArgumentException)` ⇒ 与「选不到」同一出口；
   这与今天的结局（三处 `getPlayer("@S")` 必然不中 ⇒ 同一句失败文案）**措辞相同**，见 §5 第 5 条。
3. **裸名保留双查**：`getPlayerExact` 不中再 `getPlayer` —— 这样 `:55`/`:75`/`:86`/`:102` 处
   按名解析的**宽松匹配与大小写不敏感**逐字不变（`Bukkit.getPlayer` 不中时不会抛异常，安全）。
4. **`selected == null` 表示「没走选择器」**：所以裸名分支与选择器分支**互斥**，不存在「选择器失败后再退化成裸名」的歧义。
5. **`instanceof Player` 之前先判 `size()`**：`@e` 在正常世界里 `size() ≥ 2`（执行者自己也是一个实体）⇒ 在 `size` 这一关就被拒，
   消息与 `size == 0` **完全同一句**（这正是卡面要求的「非玩家选择器与 size == 0 走同一路径」，见 §4）。
6. **★ 回显名（`targetName`）不做规范化**：`handleSet/handleClear` 收到的 `targetName` 仍是**原始 token**，
   只有「省略目标」时它是 `null`。这样 `Cannot find the player you provided: <原样 token>` 与
   「`The role of player [ <原样 token>] has been set:`」里的**回显与今天逐字节相同**（包括用户敲的小写形式），
   而传给 `roleManager.selectRole/clearRole` 的是**解析出的 `Player`**。**不新增任何分支**即可同时满足两件事。

（省略目标 ⇒ 同一实例 ⇒ 走「自己」那两版；显式 `@s` ⇒ 也走「自己」那两版 —— 而今天 `/role clear @s` 是**失败**，
所以这是**新增**行为，不是既有行为的改动）。


### 3.2 判定表（这是实现卡与 t22 的验收尺）

| 输入 | 与 sender 的关系 | 判定 | 结果 |
|---|---|---|---|
| 省略目标段 | — | 不解析 | 目标 = 执行者自己（`sender == target`） |
| `@s` | 执行者 | 快路径 | 目标 = 执行者自己 |
| 裸名 `Steve`，在线 | 他人 | `getPlayerExact` 命中且在线 | 目标 = Steve |
| 裸名 `Steve`，已离线 | 他人 | `getPlayerExact` 不中 → `getPlayer` 不中 | **拒绝** ⇒ `Cannot find the player you provided: Steve` |
| 裸名，不存在 | — | 两查皆空 | **拒绝**，同上 |
| `@p` | 最近玩家（在无参数场景即执行者） | `selectEntities` ⇒ 1 名在线玩家 | 目标 = 该玩家 |
| `@a` | 全体在线 | `size > 1`（单人服务器 `size == 1`！） | 两人及以上 ⇒ **拒绝**；**单人服务器会命中**（见下方「如实申报」） |
| `@e` | 全体实体 | 通常 `size > 1`；`@e[type=player]` 等价 `@a` | ⇒ **拒绝**（与 `size == 0` 同一句） |
| `@a[name=Steve]` | 指向 1 人 | `size == 1` | 目标 = Steve ✓ |
| `@e[type=player,limit=1]` | 指向 1 人 | `size == 1` | 目标 = 该玩家 ✓ |
| `@nonsense` / `@a[garbage]` | — | `IllegalArgumentException` ⇒ 捕获 ⇒ 同 `size == 0` | **拒绝**，同上 |
| `@z`（无此选择器） | — | 同上 | **拒绝**，同上 |

**如实申报（不得粉饰）**：`@a` 的语义就是「**全部在线玩家**」，所以**单人服务器**上 `/role set X @a` 会**成功**。
这不是漏洞，而是「恰好 1 名」这把尺的必然结果，也是卡面「只允许 1 名」的字面口径。
若产品上要求「`@a` 永远拒绝」，就必须引入第二套「选择器白名单」判定 —— 与 C4 冲突，**本卡明确不采用**；
改为在手册 §3.2（§8）里写清「`@a`/`@e` 在多人在线时一律被拒；单人服务器上 `@a` 等价于 `@p`」，由产品侧决定是否再开卡。

## 4. ★ 回绝措辞（全部写定，逐字供实现卡照抄）

**口径（队长 round 裁定，取代原「零新增句子」方案）：按真实原因分三句，各自描述**发生了什么**。**
判据：**报告失效现象时必须给真实原因**，不得用一句「找不到那个玩家」去叙述「找到了不止一个」——
那属叙述与事实不符，与本项目的注释判据（只叙述机制事实）同源。新增句子仅限下表第 2～4 句，
且**只出现在选择器失败路径**（今天不存在该路径 ⇒ 不推翻任何既有断言）。

| 情形 | 判据 | 逐字文案 |
|---|---|---|
| 目标段**显式给出**、且**不是选择器**（裸名 / UUID），解析失败 | 非 `@` 开头且 `getPlayerExact`/`getPlayer` 不中 | `Cannot find the player you provided: <原始 token>`（**逐字不变**） |
| **选择器**解析失败（语法非法 / `IllegalArgumentException`） | `@` 开头且 API 抛异常 | `Cannot parse the target selector you provided: <原始 token>` |
| **选择器**命中 **0 个玩家** | `size == 0` | `No online player matched the target selector you provided: <原始 token>` |
| **选择器**命中 **多于 1 个玩家** | `size > 1` | `The target selector you provided matched <N> players; it must match exactly one: <原始 token>` |
| `operation` 目标段**非选择器**解析失败 | 同上 | `No online player named '<原始 token>'. (Omit the player to target yourself.)`（**逐字不变**） |
| `operation` 目标段**选择器**失败 | 上述三句之一 | 同上三句（`operation` 不再单独复用旧句） |

- ★ **裸名路径的既有句子一字不改**：`Cannot find the player you provided: <原样 token>` 与
  `No online player named '<原样 token>'. (Omit the player to target yourself.)` 仍只服务**非选择器**输入
  ⇒ §5 保持清单里所有既有断言照旧成立，`size == 0` 不再与它共用一句。
- **非玩家选择器（如 `@e`）** ⇒ 解析结果里没有 `Player` ⇒ 归约为 `size == 0` ⇒ 走第 3 句。
- `<原始 token>` = 用户**原样**输入的那一段（含 `@` 符号）；**不**做归一化、**不**加引号。
- **语法非法的回显不得携带 API 的原始异常消息**（可能含内部实现细节）⇒ 第 2 句是固定文案，异常只记服务端日志。
- `operation` 那句话里的 `(Omit the player to target yourself.)` 保留是**有意**的：非选择器失败时它依然是正确的下一步提示。
- 目标段**省略** ⇒ 不解析、不报错，行为与今天完全一致（§5 第 3 条）。

### 4.0 回显名口径（与回绝措辞同一族，一并定案）

| 位置 | 用哪个名字 | 理由 |
|---|---|---|
| 回绝文案里的 `<原样 token>` | **原始 token**（`targetName`） | 玩家敲了什么就回什么；今天就是 `getPlayer` 的入参 |
| `set`「给他人装配成功」文案里的 `[ <…>]` | **原始 token** | `SetRoleCommand.java:85` 今天用的就是 `targetName`；规范化会改变小写输入的可见输出 |
| `clear`「他人成功 / 他人没有角色」文案里的 `[<…>]` | **原始 token** | `ClearRoleCommand.java:68`、`:80` 今天用的就是 `targetName`（`:81` 给**目标本人**发的是固定句） |
| `energy` 回显里的 `[<…>]` | **解析结果的 `getName()`** | `EnergyCommand.java:92`、`:95` 今天用的就是 `target.getName()`，**不动** |
| `operation` 审计行的 `target=` | **解析结果的 `getName()`** | 审计必须能定位到唯一对象；原始 `@a` 无法定位（§6.3、§7 第 6 条） |

⇒ 一句话纪律：**逐子指令沿用今天各自用的那个名字，一个都不换。** 唯一例外是 `operation` 的选择器路径（今天不存在该路径，故无「不变」可言）。

### 4.1 值得写下来的取舍与代价

- **原方案（已弃）**：`size > 1` 与 `size == 0` 共用「找不到那个玩家」一句，为的是零新增句子、避免
  `使用者手册.md:111 / :132`（§3.3 逐条回显文案表）、`docs/ai-generated/使用者手册.md:184`（消歧规则）
  与回归断言三处同时漂移。
- **弃用理由（队长裁定）**：该方案的代价是**语义不诚实** —— 玩家与排障者看到「找不到那个玩家」，
  而实情是「找到了不止一个」或「选择器语法错了」。这与本项目的注释判据同源（只叙述真实机制事实），
  不可为了「少改文档」而牺牲可诊断性。相比之下，多改两行手册是**可控成本**。
- **采纳方案**：按真实原因分三句（§4 表第 2～4 句），**裸名路径的既有句子一字不改** ⇒ 既有断言全部保持；
  新增只落在**今天不存在**的选择器失败路径上。
- ⇒ 新增的三句**必须**登记进手册（§8 第 3 条），并由 **t22 独立验证卡**逐句显式确认
  （语法非法 / `size == 0` / `size > 1` 三句各自的实际回显），不许由实现卡自证。
- 现状确认（逐字核对过）：`@s` 目前在四条子指令上**全部失败**，且失败文案就是上表第一句
  —— 手册里**只有** `@s` 用于 `/role operation` 的**成功**示例（`使用者手册.md:87` 用法列、`:184` 消歧说明、
  `:545` 与 `:696` 的 SanTE 实跑记录），**没有**任何一处断言「`/role energy get @s` 必须失败」。
  ⇒ 本特性把 `@s` 从「失败」改成「成功」**不推翻任何既有文档**，只新增支持。

## 6. ★ 消歧规则：`/role operation` 的第 2 段何时当目标、何时当 `componentId`

### 6.1 现状（逐字核对过）

`ComponentOperationCommand.java:146-152`：

```java
    /** 第 2 个参数是否**当目标**（`@s` 或在线玩家名 ✓）。 */
    private boolean isTargetToken(String token) {
        if (token == null || token.isBlank()) {
            return false;
        }
        return ComponentOperationDispatcher.SELF_TOKEN.equalsIgnoreCase(token)
                || Bukkit.getPlayerExact(token) != null;
    }
```

类 javadoc `:28-29` 的定案：

> **目标与 id 的消歧** ✓：第 2 个参数**当且仅当**它是 `@s` 或一个**在线**玩家名时才当作目标 ✓；
> 否则它本身就是 `componentId`（目标 = 自己）✓ —— 这样 `query energy current` 不会被误读成"目标 = energy" ✗。

⇒ 现状 = **两条件之一**（`@s` 大小写不敏感 **或** `Bukkit.getPlayerExact(token) != null`）；
不命中 ⇒ `targetToken = null`（`:99`）、`componentId = args[1]`、`payloadFrom = 2`。

### 6.2 放宽后的规则（定案）

> **凡以 `@` 开头的 token 一律按选择器解析。**
> 即第 2 段当目标 **⟺** ① `token` 非空白 **且**（② `token` 以 `@` 开头 **或** ③ `Bukkit.getPlayerExact(token) != null`）。

```java
    /** 第 2 个参数是否**当目标**：`@` 开头（选择器 / `@s`）或在线玩家名。 */
    private boolean isTargetToken(String token) {
        if (token == null || token.isBlank()) {
            return false;
        }
        return token.startsWith("@")
                || Bukkit.getPlayerExact(token) != null;
    }
```

- ② 覆盖了旧的 `SELF_TOKEN.equalsIgnoreCase(token)`（`@s` 以 `@` 开头）⇒ 旧条件被**包含**，旧判定**只增不改**：
  今天判为目标的 token，改后仍判为目标；今天不判为目标的**非 `@`** token，改后仍不判为目标。
- `@` 开头的 token **即便解析失败也仍当目标**（不能回落成 `componentId`）—— 否则 `@nonsense` 会被当成组件 id，
  玩家看到 `No component with id '@nonsense' …`，与 `@` 的直觉相反，且掩盖真正的错因。

### 6.3 解析与回绝落在哪一层（定案）

- **解析与回绝都在 `ComponentOperationCommand`**：目标段命中时先 `PlayerTargets.resolve(player, args[1])`，
  为空 ⇒ 打 §4 第 2 句并 `return true`（即**不进入** dispatcher）。
- **`ComponentOperationDispatcher.dispatch(...)` 的签名不动**（`ComponentOperationDispatcher.java:70`）：
  仍收 `String targetToken`，但传入的是**解析后玩家的 `getName()`**，不再传原始选择器串。
- **`ComponentOperationDispatcher.resolveTarget` 的 `Bukkit.getPlayerExact` 保留不动**（`:249-255`）：
  它现在只服务「省略目标」路径，且**离线单测面**（`ComponentOperationDispatcherTest`）以它为边界，
  改动它会同时动到测试面与 §5 第 1 条的既有口径。
- ⇒ **选择器解析只有一处实现**（`PlayerTargets`），不存在第二套判定；`dispatcher` 侧的 `@s`/空 ⇒ 自解析**也保留**，
  但在选择器路径上**不再被触发**（因为传进去的已是玩家名）。这是「职责不重复」的正常结果，不是死代码：
  省略目标那一路仍然走它。

### 6.4 消歧判定表（现算 vs 改后）

| `args[1]` | 现状 | 改后 | 说明 |
|---|---|---|---|
| `energy`（组件 id） | 不是目标 ⇒ `componentId=energy`，目标 = 自己 | **不变** | 卡面点名的「`query energy current` 不被误读」仍成立 |

| `@s` | 目标（大小写不敏感）⇒ 执行者 | 目标 ⇒ 执行者 | 只增（`@S` 的处置见 §5 第 5 条） |

| `Steve`（离线） | 不是目标 ⇒ `componentId=Steve` ⇒ `No component with id 'Steve' …` | **不变**（非 `@` 开头） | 既有「离线名不构成目标」的判定一字不改 |
| `@a` / `@e` / `@p` / `@r` | 不是目标 ⇒ 当 `componentId` ⇒ `No component with id '@a' …` | **是目标** ⇒ 走 §3 ⇒ `@a`/`@e` 通常被拒（§4 第 3/4 句）；`@p`/`@r` 采 1 名 | ★ 放宽点，正是本特性的目的 |
