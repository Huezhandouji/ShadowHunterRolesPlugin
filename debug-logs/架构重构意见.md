## 0. 一句话结论

这个插件的**领域模型设计得不错**（`Role` 模板 + `Supplier` 延迟实例化 + `RoleInstance` 作为每个玩家每局的聚合根 + `LifecycleAware`/`UpdateAware`/`EnergyChangeAware` 等能力接口），问题几乎全部集中在**「怎么把角色装进去」和「组件之间怎么说话」这两件事上**：

1. **注册是硬编码的**（`RoleRegistry` 静态块 + 具体类名），新增角色必须改核心类 → 违反开闭原则。
2. **组件之间通过 `RoleInstance` 这个"上帝对象"和 `Map<String,Object>` 字符串键上下文通信**，且 `RoleInstance` 把几乎所有内部状态都暴露成 public 方法 → 高耦合、无边界。
3. **插件类、单例、Bukkit 静态调用渗透进领域层**（`Role`/`Skill`/`MainWeapon`/`DamageUtil` 全都 `ShadowHunterRolesPlugin.getInstance()`）→ 领域层无法独立测试。
4. **组件生命周期只有"开始"没有"结束"的强约束**，且状态与组件实例终身绑定，跨角色/跨玩家复用不安全。

下面按设计原则分条列出，每条都给出**证据（文件:行）→ 为什么这是问题 → 建议方案**。第 3 节单列"读代码时发现的确定性/疑似缺陷"，因为它们正是上述架构问题的直接产物。

## 1. 开闭原则（OCP）问题

### P1-1（严重）角色注册硬编码在核心类里，新增角色必须修改核心

**证据**
- `registry/RoleRegistry.java:40-43`：静态初始化块里直接 `registerHunterMeiqihezi(); registerShadowRed();`
- `registry/RoleRegistry.java:6-11`：顶部逐个 import 具体角色组件类（`MeiqiheziJuejueMainWeapon`、`RedBleedPassive`…）
- `registry/RoleRegistry.java:50-113`：两个私有方法把角色数值、描述文案、技能/被动/武器、图标全部写死，每个角色的装配体量都在 30 行上下
- `registry/RoleRegistry.java:22,25,80-81,110-111`：`ROLES` / `BUILDERS` 两个 **static** Map，注册行为发生在类加载期，与插件生命周期无关

**为什么是问题**
新增一个角色要走三道改动：新增角色类 → import 进 `RoleRegistry` → 在静态块里加一个 `registerXxx()`。这就是 OCP 的教科书反例：**扩展需要修改已有代码**。同时 `Role` 的数值（maxHP/baseATK/图标/描述）本该是**数据**，现在被编译进了字节码——策划改一个数值需要重新构建发版。

**建议**
- 把 `RoleRegistry` 从"注册者"降级为"容器"：只保留 `register(Role)` / `get(id)` / `ids()` / `all()`，注册改成**插件启动时由一个 `RoleLoader` 显式驱动**（`onEnable` 阶段），不要放在 static 块里。这样也顺手消除 P3-1 的类加载期 NPE 风险，并让"注册失败"可以 fail-fast 报错而不是 `ExceptionInInitializerError`。
- 装配数据外置：`roles.yml`（或每角色一个 `roles/<id>.yml`）持有 id/名称/描述/数值/图标/技能槽位/被动列表，Java 侧只保留"技能实现类 → id"的注册表。这样新增角色 = 新增一个 yml + （若要新技能）新增一个类，**核心零改动**。
- 若暂不做数据驱动，至少引入 SPI：`ServiceLoader<RoleDefinition>` 或注解扫描（`@RoleComponent(id="red_evilShock_skill")`），让新增技能/角色类只靠"多一个类 + 多一个 META-INF/services 条目"完成接入。

### P1-2（中）阵营是封闭枚举，外部插件无法扩展

**证据**：`core/Faction.java:3-7` 只有 `SHADOW` / `HUNTER` / `UNKNOWN` 三个常量。
**为什么是问题**：`SHDFGamePlugin` 已经通过 `RoleAPI.setFaction(UUID, Faction)`（`api/RoleAPI.java:123`）改阵营来实现"无差别 PvP"，说明阵营**是需要被外部插件驱动的运行时概念**。可枚举只能表达 3 种，加第四方阵营就得改这个插件并重编译。
**建议**：把阵营改成 `record Faction(String id)` + `FactionRegistry`，内置 SHADOW/HUNTER/UNKNOWN 作为默认值；敌对关系从"不等即敌对"这种硬编码语义（`RoleInstance.java:562-565`）改为可配置的 `FactionRelation` 策略（见 P2-1）。

### P1-3（中）组件"能不能放技能/能不能用武器"的规则被写死在 BuffManager 里

**证据**：`manager/BuffManager.java:88-94`——`canCastSkill()` 写死为 `!STUN && !SILENCE`，`canUseMainWeapon()` 写死为 `!STUN`。
**为什么是问题**：新增一种"禁疗""禁跳跃""封禁普攻"的减益，就要改 `BuffManager`；`BuffType`（`core/BuffType.java:3-7`）同样是封闭枚举（`SILENCE/STUN/IMMUNE`）。
**建议**：把"减益 → 禁止的能力"做成数据表（`Map<BuffType, Set<Capability>>`，其中 `Capability` 是 `CAST_SKILL`/`USE_MAIN_WEAPON`/…），`BuffType` 改为可注册的 `record`/枚举 + 外部注册入口。`Immune` 与各减益的互斥（`BuffManager.java:39-44,67-81`）也应从 `if` 链改为声明式优先级规则。

### P1-4（轻）重复技能/武器图标逻辑靠 copy-paste"扩展"

**证据**：`core/Skill.java:58-125` 与 `core/MainWeapon.java:46-112` 是同一段逻辑的两份拷贝（冷却 → STRUCTURE_VOID、禁用 → BARRIER、就绪 → 图标，加 lore 与 PDC）；`roleComponent/meiqiHezi/skill/MeiqiheziBloodySlashSkill.java:79-159` 又把整段**再抄一遍**（只为多一个 `ENERGY LACK` 分支），`MeiqiheziCircleSlashSkill.java:86+` 同样。
**为什么是问题**：想统一给所有技能物品加一条 lore，要改 4 处以上；改漏一处就出现不一致。
**建议**：抽 `HotbarItemRenderer`（或 `IconSpec` + `IconRenderer`），默认渲染器 + "能量不足/被封禁/沉默"等**状态提供者列表**（`List<IconStateProvider>`），技能只声明自己要加哪些状态，不再重写渲染。

## 2. 低耦合 / 依赖方向问题

### P2-1（严重）组件之间通过"字符串键 + Map\<String,Object\>"通信

**证据**
- `core/RoleInstance.java:53`：`private final Map<String, Object> context`；:134-150 提供 `setContext/getContext(key, Class)/hasContext/removeContext`
- 生产者：`roleComponent/red/RedBleedPassive.java:24-26` 定义 `BLEED_RECORD_CONTEXT_KEY` / `BLEED_RESOLVE_REQUESTS_KEY` 静态字符串；:55-56 在 `onSet` 把自己的两个 `HashMap` 塞进上下文
- 消费者：`roleComponent/red/RedSanctifiedBladeMainWeapon.java:35`（主武器）与 `roleComponent/red/RedEvilShockSkill.java:33`（技能）各自 `getContext(..., Map.class)` 后强转
- `RedBleedPassive.java:66-67`：`requestBleedResolve` 是 **static** 方法，却要通过 `instance` 参数才能找到数据

**为什么是问题**
这是典型的"服务定位器 + 无类型字典"反模式：
- 类型安全靠 `@SuppressWarnings("unchecked")` 和调用方自律——`RedEvilShockSkill.java:33-34` 拿到 `resolveRequests` 后**直接 `.put()`，没有判空**，一旦该被动未注册就是 NPE（`RedSanctifiedBladeMainWeapon.java:36` 记得判空，说明作者自己也知道这契约不可靠）。
- 主武器（红）**编译期依赖**了被动（`RedBleedPassive.BLEED_RECORD_CONTEXT_KEY`）。主武器本该是独立的伤害实现，现在必须知道"红有一个流血被动"以及它的内部数据形状。
- 键冲突、生命周期全靠约定：上下文在 `clear()`（`RoleInstance.java:768`）里被整体清空，任何忘记重新注册的组件都会静默拿不到数据。

**建议**
- 把"角色内的组件协作"提升为**显式接口**：例如 `interface BleedLedger { void applyStacks(Player victim, int stacks); void requestResolve(Player victim, int stacks); }`，由 `RedBleedPassive` 实现。
- 组件之间的查询改为**类型化查找**：`RoleInstance.getComponent(Class<T>)`（内部按接口/类索引），而不是字符串键。
- 更彻底一点：让角色装配体显式声明组件依赖（构造注入或 `RoleContext.wire(...)`），由装配层把 `BleedLedger` 交给主武器，主武器只依赖接口，不依赖具体被动类。

### P2-2（严重）`RoleInstance` 是上帝对象，组件可随意改它的状态

**证据**：`core/RoleInstance.java` 771 行里，对外暴露了生命（:452-475）、能量（:477-504）、SanTE（:507-531）、阵营（:534-545）、冷却（:157-282）、热键栏（:359-433）、上下文（:134-150）、Buff（:127）、普攻/技能施放（:193-328）、生命周期触发（:586-676）、掉落标记（:41-43）……几乎所有状态都有 public getter/setter。任何组件都能 `instance.setCurrentEnergy(...)`、`instance.increaseSanTE(...)`（`RedBleedPassive.java:128,213`）、`instance.setIsInSanTEPunishmentState(...)`（`DefaultSanTEZeroPunishment.java:62,109,111`）。

**为什么是问题**
- 组件与聚合根**双向强耦合**，无法把某个组件单独拿出来测试或复用。
- 状态的**唯一权威**不清晰：`isInSanTEPunishment` 这类标志位由外部组件写，`RoleInstance` 只负责存。
- 组件可以绕过规则直接改数值。例如能量消耗的"够不够扣"判断分散在 `MeiqiheziBloodySlashSkill.java:36-38`、`MeiqiheziCircleSlashSkill.java:38-40` 等各技能里（`Skill.energyCost` 字段（`core/Skill.java:29`）有值却没人统一校验），**同一套规则被复制到 N 个技能里**。

**建议**
- `RoleInstance` 只保留**稳定公共查询**（getRole/getPlayer/getFaction/isHostileTo）与**窄接口的能力**（如 `EnergyPool`、`SanTEPool`、`CooldownRegistry`、`HotbarPresenter`），把这些能力接口传给组件，而不是传整个 `RoleInstance`。
- 能量/SanTE 的"检查 + 扣除"合并为单一原语：`boolean tryConsumeEnergy(int cost)`，技能的 `energyCost` 由框架统一校验，技能里只写业务效果。
- 生命周期触发（`RoleInstance.java:586-676` 五次几乎相同的 `instanceof` 三段循环）改为**一次遍历、按接口分派**：维护 `Map<Class<?>, List<Consumer>>` 或在注册时把组件归类，消除 5×3 的样板与遗漏风险。

### P2-3（严重）领域层反向依赖插件类与全局单例

**证据**
- `core/Role.java:234`：`ShadowHunterRolesPlugin.getInstance().getLogger()`（Builder 校验槽位冲突时）
- `core/RoleInstance.java:63-66,93-98,168-171,202-206,220-224,238-242,263-267,292-296,307-311,322-326,716,722`：到处 `ShadowHunterRolesPlugin.getInstance()`（构造 NamespacedKey、调度任务、打日志）
- `core/Skill.java:129-132,147-150`、`core/MainWeapon.java:119-122`、`core/DamageUtil.java:20-23`：静态 `NamespacedKey` 在**类初始化时**就调用 `getInstance()`
- `core/RoleInstance.java:558,569-570,578-579`：领域对象直接 `RoleManager.getInstance()` 查别的玩家，而 `RoleInstance.isHostileTo(Player)` 本该只依赖"阵营查询"这一个抽象
- `roleComponent/SkillUtil.java:22`：工具类直接 `RoleManager.getInstance()`
- 单例本身：`manager/RoleManager.java:14-21`（双重检查但**非线程安全**的懒加载单例）、`ShadowHunterRolesPlugin.java:16,56-58` 静态 `instance`

**为什么是问题**
- **无法单元测试**：`new RoleInstance(...)` 需要 Bukkit 已启动 + 插件已加载 → 只能起服务器测。
- **循环依赖**：core ↔ plugin ↔ registry ↔ manager 互相引用，编译单元无法独立演进。
- **静态状态跨测试/跨重载泄漏**：单例 + static Map 在 `/reload` 或 PluginClassLoader 重建后可能与新实例不一致。

**建议**
- 引入一个极薄的**服务上下文**（`RolesContext`）持有 `Plugin`、`Logger`、`Scheduler`、`RoleManager`、`NamespacedKeyFactory`，通过构造注入到 `Role`/`RoleInstance`/组件；领域层只依赖这个上下文接口，不 import 插件主类。
- `NamespacedKey` 统一由 `KeyFactory`（持 `Plugin` 实例）提供，去掉 `Skill.Utils`/`MainWeapon.Utils`/`DamageUtil`/`BuffManager` 四处各自 `new NamespacedKey(getInstance(), ...)`。
- 去掉 core 里的 `RoleManager.getInstance()`：`isHostileTo` 改为接收 `Faction` 或一个 `FactionLookup` 抽象（接口，主插件注入实现），把"查别的玩家"这个职责移出领域对象。
- 单例改为显式生命周期对象（在 `onEnable` 构造、在 `onDisable` 释放），不要静态懒加载；`plugin.yml` 的 `paper-plugin-loader` 已经就位，`LifecycleEventManager` 也可用于注册类资源。

### P2-4（严重）与 `SHDFGamePlugin` 的跨插件契约过窄，逼出"绕过 API"

**证据**
- `RoleAPI`（`api/RoleAPI.java`）有 `isValidRoleId/getRoleDisplayName/getRoleDescription/getRoleIcon`，但**没有**"列出全部角色 id / 按阵营列出角色"的查询。
- 结果：`SHDFGamePlugin` 的角色池只能写在配置里（`config.yml` 的 `maps`、`maps.yml` 的 `roles.attacker/defender`），由 `RoleSelectionGui.java:84-88` 逐个 `isValidRoleId` **静默过滤无效角色**——写错角色 id 不报错，只是按钮消失。
- 另一处**已经存在的越界**：`SHDFGamePlugin/src/main/java/com/sHDFGamePlugin/phase/RoleSelectingPhase.java:30` 直接 `import com.shadowHunterRolesPlugin.registry.RoleRegistry`。该 import 目前是未使用的死 import（全类无引用，因为取角色信息已改走 `RoleBridge`→`RoleAPI`），但它标志着"调用方曾经/可能伸手进你的内部注册表"；因为 `build.gradle.kts:15` 是 `compileOnly` 依赖整个 jar，这种越界在编译期**不会被拦住**。
- 契约类型问题：`api/RoleAPI.java:135` 用 `-78` 作"查不到"的哨兵值（字段能量/SanTE 全是这个约定），`getRoleIcon` 用 `Material.AIR` 表示缺失（`RoleSelectionGui.java:106-110` 需要专门注释说明）。

**为什么是问题**：公共 API 表达力不足 + 用哨兵值表达"无"，调用方只能靠约定和死值兜底；同时**内部注册表对调用方是可达的**，边界形同虚设。这直接违反"依赖稳定抽象、不依赖实现细节"。

**建议**
- `RoleAPI` 补齐只读查询：`Set<String> getAllRoleIds()`、`List<RoleInfo> getRoles()`（含 id/显示名/描述/图标/阵营）。让主插件**不再需要配置角色池**，并能对配置里的未知角色 id 报错而不是静默过滤。
- 返回值改用 `Optional`/`OptionalInt`（`getPlayerRoleId`、`getPlayerEnergy`…），去掉 `-78` 和 `Material.AIR` 哨兵语义；`getRoleIcon` 返回 `Optional<Material>` 或 `ItemStack`。
- 明确 API 边界：新增 `api` 包下的接口 + `docs/API.md`，在 `plugin.yml` 或文档里声明"`registry`/`core`/`roleComponent` 不是公共 API，随时可变"；若确实希望外部只依赖接口，可考虑拆成 `ShadowHunterRoles-API`（只含接口 + 数据 record，无 Paper 依赖）与实现两个 artifact（`build.gradle.kts:18-27` 已有 `maven-publish` 与 `mavenLocal()`，`SHDFGamePlugin` 正是消费 `mavenLocal` 的 jar）。
- `@Deprecated` 的 Player 重载（`api/RoleAPI.java:25-131`，约 20 个）应给定**移除版本**并分批删除，否则 API 会永久膨胀。

### P2-5（中）命令层没有跟上工程的 Paper 形态

**证据**：`command/RoleCommand.java` 是 `CommandExecutor`（:17），靠 `switch(args[0])`（:38-90）；`plugin.yml:9-13` 只声明了命令，没有权限；`ShadowHunterRolesPlugin.java:28` 直接 `getCommand("role").setExecutor(...)`（**没有判空**，也没有 `setTabCompleter`）。
**为什么是问题**：Paper 侧推荐 Brigadier；而且 `plugin.yml commands:` 与 Brigadier 同注册会冲突，现在把命令注册写死在主类里，将来迁移需要同时改描述符与主类。更现实的问题是**它现在就会崩**（见 P3-3）。
**建议**：改用 `LifecycleEvents.COMMANDS`（Paper 的 `LifecycleEventManager`）注册 Brigadier 命令树，参数用 `ArgumentTypes.playerProfiles()/integer()`，权限用 `.requires(...)`，补全由参数类型自动获得；同时把 `plugin.yml` 的 `commands:` 段删掉，避免重复注册。

## 4. 性能与运行时（架构导致，非微优化）

### P4-1 每个在线玩家固定跑 2 个 1-tick 任务，且热键栏被反复重写
**证据**
- `RoleInstance.java:93-98`：每 tick `triggerUpdate()`
- `manager/BuffManager.java:137-144`：每个 `RoleInstance` 再起一个 1-tick 任务（`BuffManager` 由 `RoleInstance` 构造，`RoleInstance.java:77`）
- `RoleInstance.java:700-706` → `shouldUpdateHotbar()/shouldUpdateItemMeta()`（:730-747）
- `RoleInstance.java:488`：`setCurrentEnergy` 每次都 `updateHotbar()`

**问题**：16 个玩家 = 32 个 1-tick 任务；一次能量变化会触发"立刻 `updateHotbar` + 本 tick 轮询再 `updateHotbar` + 1 tick 后 `runTaskLater` 再 `updateHotbar`"（`RoleInstance.java:162-174,202-206`），**同一帧内同一槽位可能被写 2-3 次**（每次 `createIconItem` 都会新建 `ItemStack` + `ItemMeta` + `lore`）。`updateSkillItemMeta` 逐个技能重建组件（:390-415），`updateAllSkillItemMeta` 又是 N 次调用。

**建议**：合并为**单一 ticker**（每玩家一个 `RoleTicker`，统一分派 update + buff tick），热键栏改为**脏标记 + 帧末一次 flush**（`markHotbarDirty()` → 本 tick 结束统一渲染），冷却结束改为事件驱动而不是 `runTaskLater` 堆积。

### P4-2 Folia/调度器用法不一致
**证据**：绝大多数是 `Bukkit.getScheduler()`（`RoleInstance.java:93,168,202,220,238,263,292,307,322`、`BuffManager.java:138`、`SkillListener.java:139`、`MainWeaponListener.java:134`、`DefaultSanTEZeroPunishment.java:114`、`MeiqiheziBloodySlashSkill.java:74`、`MeiqiheziCircleSlashSkill.java:81`），唯独 `roleComponent/red/RedSolitaryArroganceSkill.java:32-81` 用 `getGlobalRegionScheduler().runAtFixedRate(...)`。
**问题**：混用两套 API，既不 Folia-safe 也不统一（`BukkitScheduler` 在 Folia 不可用；`GlobalRegionScheduler` 用在玩家身上又是错的粒度——应该用 `EntityScheduler`）。
**建议**：抽一个 `Scheduler` 抽象（`runOnEntity(Player, Runnable)` / `runLaterTicks` / `runRepeating`），实现层按服务端能力分派，组件一律不直接碰 `Bukkit.getScheduler()`。这样也顺手把"任务句柄必须被持有并在 clear 时取消"变成框架责任。

### P4-3 施法前置校验与"技能是否可用"逻辑在多处重复
**证据**：`SkillListener.java:64,106,144`（冷却判断）、`MainWeaponListener.java:49,85,109,141`（冷却判断）、`RoleInstance.castSkillXxx/castMainWeaponXxx`（:193-328，同样再判一次 null）、技能内部又判 `canCastSkill()`（`RedEvilShockSkill.java:26`、`RedSolitaryArroganceSkill.java:31`、`MeiqiheziBloodySlashSkill.java:37`…）。
**问题**：同一条"能不能放"的规则散落在 listener / RoleInstance / 技能三层，任何一层改动都可能让另外两层失效（例如新增"沉默也禁止普攻"要改 4 个文件）。
**建议**：把"能否施放"收敛为 `CastGate`（冷却 ∩ Buff ∩ 能量 ∩ 阵营），listener 只负责翻译事件，技能只负责效果。

## 5. 组件能力接口（`RoleComponentAware`）的问题

**证据**：`core/RoleComponentAware/` 下 4 个接口，签名高度重复：`LifecycleAware.onSet/onClear(Player, RoleInstance)`、`UpdateAware.update(Player, RoleInstance)`、`EnergyChangeAware.onEnergyChange(Player, RoleInstance, int, int)`、`SanTEChangeAware.onSanTEChange(Player, RoleInstance, int, int)`——每个都把 `(Player, RoleInstance)` 作为前两个参数重复传递，而 `RoleInstance` 已经持有 `Player`。

**问题**
1. **参数冗余**：`instance.getPlayer()` 已有（`RoleInstance.java:446`），`Player` 参数是重复真值来源，可能出现 `player != instance.getPlayer()` 的不一致调用（`RedBleedPassive.update(Player player, ...)` 里既用传入的 `player` 又用 `instance`，见 :124-128）。
2. **能力接口无生命周期约束**：`PassiveSkill.trigger()`（`core/PassiveSkill.java:19`）定义了但**全项目零调用**，与 `UpdateAware` 形成两套并存机制——新写被动的人不知道该实现哪个。
3. **"必须清理"只是注释**（`LifecycleAware.java:12`），没有强制手段，于是 B-5 那种空 `onClear` 必然出现。
4. `RoleInstance.java:586-676` 为每个能力接口各写一遍"技能/被动/武器"三段循环 → 加第 5 个能力接口要再抄 3 段。

**建议**
- 统一为 `RoleComponent` 基类/接口 + 可选能力接口，回调签名去掉重复的 `Player`（v3 修正为 `onSet(ComponentContext ctx)`，见 §6.4/§6.5）。
- 删除 `PassiveSkill.trigger()`，或让它成为唯一的默认入口，二选一，不要并存。
- 提供 `ComponentContext`（含 `Logger`/`Scheduler`/`KeyFactory`/注册的任务句柄集合），`onClear` 由框架调用后**自动取消该组件注册的所有任务与资源**，把"必须清理"从注释变成机制。
- 能力分派改为注册表驱动（见 P2-2 建议），消除 5×3 样板。

## 6. 组件模型设计决策（决策记录）

> 本节回答三个在评审中反复出现的问题，结论均有实测数据支撑。
> **先给结论**：不做"完全能力拆解"；判定留在组件里，框架只负责**检查与反馈**；回调参数不再传 `RoleInstance`，改传窄上下文。

### 6.1 问题：技能与主武器是否应完全拆解成 `onCast`/`onAttack` 等原子能力？

**决策：不拆。** 理由是这个方向会把"分解轴"切错。

#### 判据一：触发面几乎完全重合

实测全部 `roleComponent` 下的钩子覆写情况：

| 钩子 | 实现者 | 覆写数量 |
|---|---|---|
| `onRightClick` | 6 个技能 + `TestSetSanTEToZeroSkill` | **7** |
| `onLeftClick` | 仅 `MeiqiheziJuejueMainWeapon` | **1** |
| `onDrop` | 仅基类空实现（`Skill.java:46` / `MainWeapon.java:43`） | **0** |
| `onAttack` | `MeiqiheziJuejueMainWeapon`、`RedSanctifiedBladeMainWeapon` | **2** |
| `canRightClick` | 仅基类 `return false`（`MainWeapon.java:39`） | **0**（死扩展点） |

技能与主武器**响应同一组事件**（左键/右键/丢弃）。因此"能响应什么事件"**不是**两者的差异点——沿这条缝拆解，只会把 6 个方法（其中 4 个常年空实现）保留下来，却解决不了真正的重复。

#### 判据二：两者的真实差异在"门槛"和"展示"，不在"事件"

| 差异 | 技能 | 主武器 | 证据 |
|---|---|---|---|
| 沉默是否禁止 | 禁止（`canCastSkill`） | 不禁（`canUseMainWeapon`） | `BuffManager.java:88-94` |
| 能量字段 | 有 `energyCost` | 无 | `Skill.java:29` vs `MainWeapon` 全类 |
| 装配位置 | 槽 1–8 | 槽 0 | `RoleRegistry.java:66-73,100-103` |
| 图标冷却秒数 | 显示 `Xs` | 不显示 | `Skill.java:78` vs `MainWeapon.java:66` |

这些是**装配属性**，应该被建模成数据（`HotbarItem` 的声明），而不是类层次。

#### 判据三：目前零复用点，属于投机抽象

`onAttack` 仅 2 个实现、`onLeftClick` 仅 1 个实现。**没有任何一个能力被两个组件共享过。** 在没有第二个复用点之前，把行为切成原子能力只会增加间接层。

#### 判据四：写作单位不应被破坏

团队的写作单位是"一个技能一个文件"（`roleComponent/red/RedEvilShockSkill.java` 44 行读完即知全貌）。拆成 capability 集合后，一个技能散落在 3 个文件里，代码与策划表失去 1:1 对应。

#### 但要按"语义域"抽接口，而不是按回调抽接口

| 语义域 | 内容 | 参与方 |
|---|---|---|
| `HotbarActionable` | `onCast(CastContext)` | 技能 + 主武器（都是热键栏物品） |
| `CombatHook` | `onAttack(victim, CastContext)` | 目前仅主武器；技能将来可能需要 |
| `Channeled` | `onChannelTick(CastContext)` | 引导型技能（见 §6.7） |

`onAttack` **必须保持独立**：触发源（`EntityDamageByEntityEvent`）、上下文（有 `victim`）、门槛（不受沉默限制，且 `MainWeaponListener.java:46-58` 会 `setCancelled(true)` 接管原版伤害）都不同。拍平进 `onCast` 只会让签名背上一个恒为 `null` 的 `victim`。

#### 同时合并冗余的单触发方法

`onLeftClick` + `onRightClick` + `onDrop` 合并为：

```java
void onCast(CastContext ctx);        // ctx.trigger() ∈ { LEFT, RIGHT, DROP }
```

7 个技能里 7 个只关心 RIGHT，单方法 + 枚举比三个空方法更省、更难写错。

### 6.2 问题：判定（能量/冷却/沉默）该由框架统一做，还是留在组件里？

**决策：框架不替组件做决策。框架只做「检查与反馈」，组件保留全部决策权；框架提供「提交」原语供组件显式调用。**

> 作者提出的前提是"之后会有大量技能做各种复杂的判定"，这个前提**成立**，而且现有代码里已经出现了，所以方案必须建立在它之上，而不是与它对抗。

#### 证据 A：能量门槛是声明式的（可以统一，且统一不等于替组件判定）

`Skill.java:29` 已有 `private final int energyCost`，而 5 个技能的构造函数都写了值：

| 技能 | 声明的 energyCost | 施放前是否又手写一遍判断 |
|---|---|---|
| `MeiqiheziCircleSlashSkill` | `15`（:31） | ✅ `:38` |
| `MeiqiheziBloodySlashSkill` | `8`（:28） | ✅ `:36` |
| `MeiqiheziUnconcernSkill` | `0`（:22） | ❌（cost=0，`canCastSkill` 守卫在 :29） |
| `RedSolitaryArroganceSkill` | `0`（:26） | ❌（cost=0，守卫在 :31） |
| `RedEvilShockSkill` | `0`（:21） | ❌（cost=0，守卫在 :26） |
| `RedDeeplySorrowSkill` | `0`（:23） | ❌（cost=0，守卫在 :28） |
| `TestSetSanTEToZeroSkill` | `0`（:17） | ❌（cost=0，守卫在 :24） |

结论：**cost > 0 的技能都在重复声明同一份事实**；cost = 0 的技能本来就不需要能量判断。这类统一化**不是**"替技能做判定"，而是"消除重复声明"。

#### 证据 B：主武器确实存在必须留在组件里的复杂判定（反例）

`MeiqiheziJuejueMainWeapon` 里同一个 `energy >= 20` 在两条路径上导向**完全不同的效果**：

- `onAttack`（:30-36）：能量 ≥ 20 → 直接 `return`（注释 :32 说明"范围伤害那条路写在 onLeftClick 里"）；能量 < 20 → 单体 8 点 + 进冷却。
- `onLeftClick`（:39-65）：能量 < 20 → `return`；能量 ≥ 20 → 扣 5 能量 + 5 格范围 14 点伤害 + 进冷却。

这已不是"够不够"的门槛，而是**能量档位决定这次攻击是哪一种攻击**。`20` 硬编码在 :33/:42，`5` 硬编码在 :44 且绕过 `energyCost` 字段。**这种判定必须留在组件里**——框架不该、也表达不了。

#### 因此：三段式施放流程（检查 / 决定 / 提交 分离）

```
1) 前置（框架）：只读声明字段 —— 冷却剩余、energyCost、沉默/眩晕
   → 硬闸门仅限「冷却中 / 被沉默 / 被眩晕」（这些组件无法推翻）
   → 「能量」只产出热键栏反馈，不拦截；是否因能量拒绝由组件决定（见 §7.2 边界说明）
   → 全程不产生副作用、不替组件决策
2) 决定（组件）：组件自己跑全部复杂判定（能量档位、距离、视线、目标状态、层数…）
   → 可以什么都不扣、可以拒绝本次施放、可以按分支决定扣多少
3) 提交（框架原语，组件显式调用）：
   - ctx.energy().tryConsume(n)      ← 而非 decreaseEnergy 硬扣
   - ctx.cooldown().start(ticks)     ← 而非 startSkillCooldown(getId(), 160)
```

收益：

- 组件的复杂判定**一行都不用搬到框架**；
- 阶段 1 的框架检查无副作用，只产出"为什么不能放"的状态 → 解决当前真正的痛点：7 个技能里 5 个检查失败是**静默 return**（`RedEvilShockSkill.java:26`、`MeiqiheziBloodySlashSkill.java:36-37`、`MeiqiheziCircleSlashSkill.java:38-40`…），玩家点一下什么都没发生；
- `energyCost` 字段终于有唯一职责（默认消费量），偏离就显式 `tryConsume(别的数)`——`MeiqiheziJuejueMainWeapon` 扣 5 这件事变得合法且可见，而不是绕过字段。

### 6.3 冷却：默认统一 + 逃生舱（待确认）

冷却与能量不同，它**能**被组件按分支控制。实测 14 处 `startSkillCooldown`/`startMainWeaponCooldown` 调用：

| 形态 | 数量 | 例子 |
|---|---|---|
| 无条件用声明值 `startSkillCooldown(getId(), getCooldown())` | 11 | `RedEvilShockSkill.java:39`、`RedSolitaryArroganceSkill.java:82`、`MeiqiheziCircleSlashSkill.java:41`、`MeiqiheziUnconcernSkill.java:30`、`RedDeeplySorrowSkill.java:30,46,55`、`TestSetSanTEToZeroSkill.java:26`… |
| **分支决定是否进冷却** | 1 | `MeiqiheziJuejueMainWeapon.java:34`（仅 <20 能量的路径进冷却）/ `:43` |
| 引导期间**反复重设**冷却 | 1 | `RedDeeplySorrowSkill.java:46`（每秒 `update` 里再 `start` 一次，用于持续期刷新） |
| 硬编码时长（非声明值） | 1 | `MeiqiheziBloodySlashSkill.java:40`（`160`，构造函数 :27 也是 160，当前巧合一致，改构造函数即静默不一致） |

**建议：冷却默认由框架在"成功施放"后按声明值启动，同时提供两个逃生舱**：

- `CastResult.skipCooldown()` —— 本次不进冷却（覆盖 `MeiqiheziJuejueMainWeapon` 的 `<20` 返回路径）；
- `CastContext.cooldown().start(ticks)` —— 组件完全接管（覆盖 `RedDeeplySorrowSkill` 的引导刷新）。

逃生舱让"分支型"与"统一型"都能表达，因此不需要现在二选一。**开放问题**：引导型技能的冷却刷新是否应被抽象为 `Channeled` 能力（见 §6.7），需要作者确认。

### 6.4 问题：生命周期/接口方法要不要传 `RoleInstance`？

**决策：不传 `RoleInstance`，也不抽"又一个信息类"。先把方法所有权归位，再传一个窄上下文。**

#### 实测：组件实际使用了 `RoleInstance` 的哪些方法（全部 12 个组件去重，共 21 个）

| 分类 | 方法（调用次数） | 归属 |
|---|---|---|
| **框架该自己做** | `startSkillCooldown`(9)、`isSkillReady`(4)、`getRemainingSkillCooldownSeconds`(4)、`getBuffManager→canCastSkill`(**11**)、`setIsInSanTEPunishmentState`(3) | 这 31 个调用点**全部**是样板：`isSkillReady`/`getRemaining*` 8 次全在热键栏图标代码里；`canCastSkill` 11 次全在"施放守卫"或图标代码里 |
| **纯管道（应消失）** | `setContext`(2)、`getContext`(3)、`getPlayer`(1) | 5 次字符串键查表应换类型化接口；`getPlayer` 全项目**仅被调用 1 次** |
| **真正属于组件** | `getCurrentEnergy`(11)、`isHostileTo`(5)、`getFaction`(3)、`increaseSanTE`(4)、`decreaseEnergy`(3)、`startMainWeaponCooldown`(3)、`heal`(2)、`setCurrentSanTE`(2)、`getCurrentSanTE`(1)、`getMaxSanTE`(1)、`increaseEnergy`(1)、`decreaseSanTE`(1)、`addBuff`(1) | 13 个方法，是"技能效果"本身 |

两条直接结论：

1. **`getBuffManager()` 被调用 12 次，其中 11 次只是为了 `.canCastSkill()`。** 组件为了问一句"我能放技能吗"，得穿过 `RoleInstance` 拿 `BuffManager`——说明 `BuffManager` 也是小上帝对象。
2. **`(Player caster, RoleInstance instance)` 里的 `Player` 是冗余的**：`instance.getPlayer()` 存在（`RoleInstance.java:446`），组件里只用到 1 次。`RedBleedPassive.update(Player player, RoleInstance instance)` 的两个参数指向同一个人。

#### 为什么"传 `RoleInstance`"有问题

不是"耦合感"，而是**契约面**：组件依赖 21 个方法，却拿到 70+ 个 public 方法，其中包含 3 段互不相容的冷却 API（`isSkillReady(String)` / `isSkillReady(String,int)` / `getRemainingSkillCooldownTicks`）。证据：`Skill.java:60` 用第一种，`MeiqiheziBloodySlashSkill.java:81` 用第二种——**同一个类里两种写法并存**，因为它们都在公开面上，编译器不会拦。

#### 为什么"抽一个信息类"也有风险

如果 `ComponentContext` 只是把 `RoleInstance` 的 getter 抄一遍，那只是把上帝对象改名，还多一层跳转（Middle Man 反模式）。

#### 做法：让 `RoleInstance` 实现一组窄接口，方法只声明它需要的

```java
// 组件的依赖面 = 3 个小接口，而不是 70 个方法
public interface EnergyPool {          // 覆盖 11 + 4 次调用
    int current();
    int max();
    boolean tryConsume(int amount);    // 检查 + 扣减合一
    void increase(int amount);
}

public interface SanTEPool {           // 覆盖 8 次调用
    int current();
    int max();
    void set(int amount);
    void increase(int amount);
    void decrease(int amount);
}

public interface FactionView {         // 覆盖 8 次调用
    Faction self();
    boolean isHostile(Player other);   // 内部走 FactionLookup，不再碰 RoleManager 单例
}

// 回调签名
void onCast(CastContext ctx);
// CastContext 暴露：energy() / sante() / factions() / cooldown() / buffs() / trigger() / self()
```

注意 `CastContext` 里**没有** `getPlayer()`（身份归 `ctx.self()`，按需用）、**没有** `getBuffManager()`（`canCastSkill` 升格为框架前置检查）、**没有** 图标渲染读数（归框架）。

#### 判据（新增组件时的唯一自问）

> **组件拿到它之后，会去改它吗？**

| 情况 | 处理 |
|---|---|
| 会改 | 放方法参数（`ctx.energy().tryConsume(5)`，调用点一眼看出改了能量） |
| 只读 | 构造时注入（冷却值、描述文案、槽位） |
| 框架内部、既读又改 | 干脆不给（冷却读数、`canCastSkill`、图标渲染） |

按此过一遍这 21 个方法，`RoleInstance` 对组件的暴露面应从 **21 个方法降到约 8 个**。特别地，`setIsInSanTEPunishmentState` 的 3 次调用**全部来自 `DefaultSanTEZeroPunishment` 自己**（:62,109,111），理应变成它的私有字段——现在却挂在 `RoleInstance` 上让所有组件都能改。

### 6.5 依赖注入的时机（必须注意的坑）

**`RoleInstance` 的构造顺序**：`initComponents()`（:75，建组件）→ 建 `BuffManager`（:77）→ 设生命属性（:80-88）→ 起 ticker（:93）→ **`triggerLifecycleOnSet()`（:100，最后一个）**。

因此：

- **在构造函数里注入 `EnergyPool` 不安全**——那时 `currentEnergy` 已赋值（:72-73）但 `buffManager` 尚为 null（:77 才创建）；
- **`onSet` 是唯一确定"所有字段就绪"的时点**；
- 跨组件依赖只能运行期获取：`RedBleedPassive.java:55` 在 `onSet` 里才创建账本对象并塞进上下文，这正是现有代码被迫用 `static requestBleedResolve(instance, ...)`（:66-67）的原因。

**分工**：

| 依赖种类 | 传递方式 |
|---|---|
| 身份、只读模板数据（id/名称/描述/槽位/冷却值） | **构造时注入**（数据在 `Role` 上已有） |
| 可变资源（能量/SanTE/生命/阵营/冷却） | **方法签名传入**（`CastContext`） |
| 跨组件协作（如流血账本） | **`awake` 时按接口解析并缓存引用**，`start` 时使用，与 `stop` 对称拆卸 |

最后一条顺带把"资源回收"从注释变成机制：`onSet`/`onClear` 成为对称的 attach/detach，`onClear` 后由框架**自动**回收该组件注册的任务与资源 → `MeiqiheziEquipmentsPassive.java:73` 那种空 `onClear` 不再造成装备残留，`DefaultSanTEZeroPunishment.java:29` 的 `taskId` 覆盖泄漏也被消除。

> 这也修正了 §5 中"回调签名去掉 `Player`（`onSet(RoleInstance)`）"的措辞：最终形式是 `start(ComponentContext ctx)`，`Player` 通过 `ctx.self()` 取得（本次准备阶段暂保持 `(Player, RoleInstance)`，窄上下文属阶段 2）。

> **生命周期命名决策（本次准备阶段落地）**：`onSet`/`onClear` 重命名为 **`awake` / `start` / `stop`，一律不带 `on` 前缀**——与既有 `UpdateAware` / `EnergyChangeAware` / `SanTEChangeAware` 的命名风格统一。语义映射：`onSet` 的"开始生效"整体给 `start`，`onClear` → `stop`，`awake` 为**新增阶段**，只承担跨组件依赖解析。
>
> `awake` 的契约：
> - **时序**：全部组件创建完成 → `awake` 全部 → `start` 全部 → **启动 ticker** → 渲染热键栏。当前 `RoleInstance` 构造是 ticker 先启动（:93-98）、生命周期回调后执行（:100），必须一并前移，否则 `awake` 期间 1-tick 任务已挂在调度器上、与"解析依赖"的语义相冲。
> - **幂等**且**不得改动任何玩家可见状态**（`stop` 尚未调用，重入会叠加效果：如重复发装备、重复上 buff）。
> - 大部分组件不需要它 → 用 `default` 空实现，按需覆写。

## 7. 完整重构方案（架构为主）

> 原则：**先解除对下游的破坏风险，再动内部结构**。`SHDFGamePlugin` 通过 `ServicesManager.load(RoleAPI.class)`（`RoleBridge.java:43`）拿服务，且其 `build.gradle.kts:15` 是 `compileOnly` 依赖整个 jar——所以 `RoleAPI` 的方法签名必须**只增不改**，直到两边同步升级。
>
> 重构策略：**绞杀者模式（Strangler）**——新旧结构并存，逐块替换，每步都能构建、能起服、能回滚。

### 7.1 目标架构（四层 + 一个明确边界）

```
┌─ L4 装配层 (registry / loader) ────────────────────────────┐
│  RoleLoader：启动时读 roles.yml + 静态技能注册表           │
│  RoleRegistry：纯容器（get/ids/all/register），无 static 块 │
└────────────────────────────────────────────────────────────┘
                 │ 构造 Role（不可变模板）
                 ▼
┌─ L3 聚合层 (core) ─────────────────────────────────────────┐
│  RoleInstance：聚合根 + 唯一的 ticker + 脏渲染 flush        │
│  实现 EnergyPool / SanTEPool / FactionView / CooldownRegistry│
│  持有 ComponentHost（组件集合、能力分派表）                 │
└────────────────────────────────────────────────────────────┘
                 │ 通过 CastContext 暴露窄接口
                 ▼
┌─ L2 组件层 (roleComponent) ────────────────────────────────┐
│  Skill / MainWeapon（HotbarItem）+ 能力接口                 │
│  HotbarActionable / CombatHook / Channeled                  │
│  UpdateAware / EnergyChangeAware / SanTEChangeAware         │
│  LifecycleAware（start 注入协作接口，stop 对称拆卸）        │
└────────────────────────────────────────────────────────────┘
                 │ 只依赖注入进来的抽象
                 ▼
┌─ L1 平台层 (platform) ─────────────────────────────────────┐
│  RolesContext(Plugin, Logger, Scheduler, KeyFactory)         │
│  Scheduler 抽象（Bukkit ↔ Folia）                            │
│  FactionLookup 抽象（取代 RoleManager.getInstance 直连）     │
└────────────────────────────────────────────────────────────┘

跨插件边界：api 包（RoleAPI + 数据 record）只接受不可变参数、只返回数据，
            不依赖 core/registry/roleComponent 的具体类（Phase 4.4 后可拆成独立 artifact）；
            外部插件（SHDFGamePlugin）只准用这一层 + ServicesManager。
```

**关键约束（架构上最重要的三条）**

1. **依赖方向单向**：L2 → L1/接口，L3 → L1/L2 的接口，L4 → 全部。**不允许 L2 依赖 L3 的具体类**（现状：`RoleInstance` 被组件直接持有）、**不允许任何层 import 插件主类**（现状：`Role.java:234`、`Skill.java:130`、`DamageUtil.java:21`…）。
2. **组件之间只通过接口协作，不通过 `Map<String,Object>`**（现状：`RedBleedPassive.java:24-26,55-56` ↔ `RedSanctifiedBladeMainWeapon.java:35`）。
3. **框架只检查与反馈，不替组件决策**（§6.2）。

### 7.2 核心接口草案

```java
// ---------- L1 平台 ----------
public interface Scheduler {
    void runOnEntity(Player player, Runnable task);          // Folia: EntityScheduler
    Cancellable runRepeating(Runnable task, long delay, long period);
    Cancellable runLater(Runnable task, long delayTicks);
}
public interface KeyFactory { NamespacedKey of(String key); }
public record RolesContext(Plugin plugin, Logger logger,
                          Scheduler scheduler, KeyFactory keys) { }

// ---------- L2 组件能力（三个语义域，不是每个回调一个接口）----------
public interface HotbarActionable {
    void onCast(CastContext ctx);                            // trigger ∈ LEFT/RIGHT/DROP
}
public interface CombatHook {
    void onAttack(Player victim, CastContext ctx);
}
public interface Channeled {
    void onChannelTick(CastContext ctx);
}

// ---------- L2 生命周期与通知 ----------
public interface RoleComponent {
    String id();
    Component displayName();
    Component description();
    Material icon();
}
public interface LifecycleAware {
    default void awake(Player player, RoleInstance instance) {}  // 新增阶段：只做跨组件依赖解析
    void start(Player player, RoleInstance instance);            // 原 onSet：attach，开始生效
    void stop(Player player, RoleInstance instance);             // 原 onClear：detach，框架随后自动回收资源
}
public interface UpdateAware   { void update(ComponentContext ctx); }
public interface EnergyChangeAware { void onEnergyChange(ComponentContext ctx, int pre, int now); }
public interface SanTEChangeAware  { void onSanTEChange(ComponentContext ctx, int pre, int now); }

// ---------- L2 回调上下文（窄！）----------
public interface CastContext {
    CastTrigger trigger();          // LEFT / RIGHT / DROP
    Player self();
    EnergyPool energy();
    SanTEPool sante();
    FactionView factions();
    CooldownRegistry cooldown();
    BuffAccess buffs();
    <T extends RoleComponent> T collaborator(Class<T> type);   // 取代 getContext(key)
}
// ComponentContext = CastContext + 框架服务
public interface ComponentContext extends CastContext {
    RolesContext roles();
    <T> T setting(String key, Class<T> type);                 // 技能自身配置
    Cancellable track(Cancellable task);                      // 登记资源，stop 自动回收
    void markHotbarDirty();
}

// ---------- L3 施放管道 ----------
public sealed interface CastResult {
    record Cast()                 implements CastResult {}     // 正常施放（框架按声明启动冷却）
    record CastNoCooldown()       implements CastResult {}     // 逃生舱：本次不进冷却
    record Rejected(String reason) implements CastResult {}    // 组件拒绝（附带反馈文案）
}
```

**框架侧施放管道**（`RoleInstance` 内部，组件不感知）：

```
handleCast(trigger):
  item = slotMap 中该 trigger 对应的 HotbarItem
  if (!precheck(item).ok()) { markHotbarDirty(); return; }
  //   precheck 只读声明字段（冷却 / 沉默 / 眩晕 / 能量），无副作用
  //   ⚠ 其中"能量"只用于**热键栏反馈**，不作为硬闸门（见下方说明）
  ctx = CastContext.of(this, trigger)
  result = item.onCast(ctx)                                  // 组件跑全部复杂判定
  switch (result):
    Cast          -> cooldown.start(item.cooldownTicks())
    CastNoCooldown-> （组件已自行处理）
    Rejected(r)   -> 反馈 r，不进冷却
  markHotbarDirty()
  // 注意：能量扣减不在框架做——组件自己 ctx.energy().tryConsume(n)
  // 这样 MeiqiheziJuejueMainWeapon 的"按档位扣 5 或扣不同值"天然合法
```

**关于"能量前置检查"的边界（重要，避免把 §6.2 的决策做反）**：

`Skill.energyCost` 声明值的定位是**默认消费量 + 热键栏提示依据**，不是硬闸门。原因：§6.2 的证据 B 里，`MeiqiheziJuejueMainWeapon` 需要按能量档位走不同分支，若框架按声明值提前拦掉，组件就永远看不到"能量不足"这一分支。因此：

| 场景 | 框架行为 |
|---|---|
| 能量 < 声明值 | **不拦截**，照常调用组件（让组件自己决定"拒绝"还是"走低能量分支"），但热键栏显示"能量不足"状态 |
| 组件调用 `ctx.energy().tryConsume(n)` 失败 | 组件自行决定：`CastResult.Rejected(...)` 或不进冷却 |
| 组件希望被硬性拦截 | 在 `onCast` 开头自行判并返回 `Rejected`（即现状写法，语义不变） |

这样既消掉了"5 个技能重复手写能量判断"的样板（可通过声明值让框架做 UI 反馈），又不夺取组件的决策权。

## 8. 明确不建议现在做的事

- **不要为了"看起来解耦"给每个类加接口**。`Role`/`RoleInstance` 目前只有单一实现，抽 `RoleImpl`/`RoleInstanceImpl` 只会增加跳转成本；真正需要抽象的是**跨插件边界（RoleAPI）**和**组件协作（`BleedLedger` 这类窄接口）**。
- **不要顺手重构 `roleComponent` 里的数值平衡**。数值（伤害/冷却/层数上限）属于策划域，重构时应保持逐字不变，否则回归验证无法区分"重构引入的 bug"和"顺手改的数值"。
- **不要在阶段 0–3 同时改 API 返回类型**（`-78`、`Material.AIR` → `Optional`）。这属于破坏性变更，必须与 `SHDFGamePlugin` 同步发布，单独放到阶段 4.4 并约定双版本兼容期。
