# 开放项 · 属性修饰符跨会话残留导致 STUN 首次施加抛异常

> **性质**：**预先存在的缺陷，非本批引入**。4.4 渲染器接管批只是**第一次**把它捕获进冻结件。
> **状态**：**已捕获、未受控复现、未修**。闭合方式建议见 §6（需另立卡，且必须走"新一代重新取证"流程）。
> **捕获处**：`debug-logs/测试记录/阶段5-起服日志-4.4外观取证.log`（t5 那一轮，第 1 轮 13:21:26）。

---

## §1 现象（冻结件内，1 条）

第 1 轮出现 **1 条插件归因 WARN + 栈**：

```
Modifier is already applied on this attribute!
    at manager/BuffManager.addBuff:53
    ← roleComponent/DefaultSanTEZeroPunishment$1.run:84
```

**第 2 轮无此条**。级别 = **WARN**（非 ERROR/SEVERE）⇒ 本工程既有的「按级别字段扫描 `ERROR|SEVERE`」口径**不会**捕获它（见 §7）。

## §2 通道证据（离线只读现算）

插件施加的**永久属性修饰符会跨会话留在 `playerdata`**：在 09-13、08-03 两个旧 `playerdata` 文件里现算到 `shadowhunterrolesplugin:role_health_modifier`。⇒ 属性修饰符的持久性**不是**假设，是可核事实。

## §3 判读（**未受控复现**，属假设而非结论）

残留的 `buff_movement_speed_modifier` 在玩家载入时被读回 ⇒ **首次** STUN 施加时与既有键相撞 ⇒ `addModifier` 抛异常。

**代码级不对称**（这是本条最可动作的观察）：

| 修饰符 | 施加前是否先移除 |
|---|---|
| `role_health_modifier`（生命） | **是** —— `RoleInstance` 构造器先 `removeModifier(am)` 再 `addModifier(am)` |
| `buff_movement_speed_modifier`（STUN） | **否** —— `BuffManager.addBuff` 直接 `addModifier` |

## §4 影响面（为什么值得修）

抛出点的顺序决定了**降级是部分的、因而不易被察觉**：

- `activeBuffs.put(...)` 在抛出点**之前** ⇒ 闸门 `canCastSkill()`/`canUseMainWeapon()` **照常生效**、**外观 `DISABLED` 照常显示**；
- 被跳过的是 `applyPotionEffect(STUN)` ⇒ **失明/黑暗等药水效果未施加**。

⇒ 表现为"技能被禁用了，但没有任何视觉致盲"，玩家与复核者都不容易归因。**属"看得见的行为差异，但不会报错"**这一类。

## §5 归因边界

- **非本批引入**：与本批改动面（渲染器接管 + `updateHotbar` 删除）无因果关系；
- **本批的级别字段扫描口径仍然成立**：该异常是 **WARN**，t2/t4 的 `ERROR|SEVERE` = 0 结论不受影响；
- **未受控复现**：§3 的因果链尚未用受控实验证实（需构造"残留修饰符 + 首次 STUN"的确定性用例）。

## §6 建议的最小闭合方式（未来卡，不属阶段 5）

1. **受控复现**：制造"修饰符残留 + 首次 STUN"的确定性用例，确认 §3 的因果链（**先证伪、再修**）；
2. **对称化**：给 STUN 键补"先移除再添加"的前置（对齐生命修饰符的既有写法）；
3. **载入期清账**：在角色装配/清理路径上把本插件历史遗留的修饰符一并回收（避免永久残留）；
4. **重新取证**：改 src ⇒ 新代制品 ⇒ 必须走完整取证流程（重建 → 起服 → 主冻结 → 停机 → 归档），**不得**作为"顺手修"夹带进任何批次。

## §7 ⚠️ 对本工程既有扫描口径的补充（**建议纳入后续所有批次**）

既有 Mode B 判据是「按**级别字段**扫描 `ERROR|SEVERE` = 0」。本条证明该口径**存在盲区**：

> **WARN 级、但带插件栈帧（`com.shadowHunterRolesPlugin.*`）的异常，会被完全漏掉。**

⇒ 建议给后续卡追加一项独立扫描：**「插件归因异常」** = 在冻结件中检索 WARN 级行及其后续栈帧里出现的插件包名，命中即逐条判读（是预期 WARN 还是缺陷）。它与既有 ERROR/SEVERE 扫描**并存**，不互相替代。

**同族提醒**：这与本工程既有两条纪律同源 —— 「**裸 ERROR 会命中 oshi WARN 正文**」（假阳性方向）与本条（**只看级别会漏掉 WARN**，假阴性方向）。两个方向都来自"用级别当唯一判据"。

---

**给后来者的一句话**：**"没有 ERROR"不等于"没有异常"** —— 判据要写清**级别 + 归因 + 扫描范围**三件套，缺一件就会有一条通道是盲的。
