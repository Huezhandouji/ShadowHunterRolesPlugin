# 0004 · 扩展性审查：第三个实例测试

- **状态**：已采纳（当前有效）
- **对象**：判断一个扩展点"是否真的开放"的方法

## 背景

扩展点很容易**看起来开放、实际写不出**：仓库里只有一个使用点时，谁也无法证明第二个（更不用说第三个）用法能写出来。"签名看起来够用"是一种非常容易出错的判断——它不检查继承冲突、覆写是否互相吞并、以及某个能力面是不是只能被一种基类使用。

## 决策

新增或改动扩展点时，必须过**第三个实例测试**：

> 除现有实例之外，再造一个**能写出的第三例**（可以是仓库外的探针，不必进版本库），并证明它与现有实例**可以同时成立**。

配套两条：

1. **覆写点须可叠加** —— 两个扩展各自生效，不能互相吞并（后写的不覆盖先写的，除非明确如此声明）；
2. **没有使用点的能力 = 未验证的能力** —— 要么给它一个真实使用点，要么在文档里明确标注"未验证"，不许默默假设它可用。

## 被放弃的替代方案

**替代方案（按签名判断）**：接口签名看起来能表达需求就算开放。放弃理由：真实失败形态是"写第三个实例时才发现"——例如能力面只允许单继承（一个类没法同时是两种能力）、或两个覆写点落在同一段逻辑上互相覆盖。这类问题只有**真的写出第三例**才会暴露。

## 后果（含代价）

- **每次动扩展点都要多写一个例子**：成本明确上移到"新增扩展点"这一步；
- **例子可能不进版本库**：仓库外的例子一旦被清理，就只剩结论、没有可复现的痕迹——因此必须在文档里登记"用何种第三例验证过"，否则这条记录本身会失效；
- **第三例写不出的处理方式**：扩展点必须回退（改设计）或**明确标注限制**，不允许"先放着、以后再有人遇到问题再说"。

## 门槛自证

- **难以回退**：一旦有人按"扩展点可用"写了组件，事后收紧扩展点就要改这些组件；而"审查方法"本身也会被后续所有改动继承。
- **缺上下文会令人困惑**：读者会看到扩展点旁边写着具体的使用例子（甚至仓库外的例子），不问就会以为是随手补的示例代码。
- **是真实取舍**：确实可以按签名判断（更快），也评估过"只保留一个实例就够"的做法；选严格测试是因为扩展点是给后来者的承诺。
