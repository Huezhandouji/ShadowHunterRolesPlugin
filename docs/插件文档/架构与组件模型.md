### 3.1 新基类 `RoleComponent`（已落地）

`roleComponent/RoleComponent.java` 只允许出现三样东西：① `svc` 字段 ② 钩子方法 ③ `getComponent`——任何"顺手加个 helper"都属越界（`:5-16`、设计 `docs/组件系统设计-Unity风格.md` §2 基类纪律）。

**5 个 default 钩子（框架无条件广播）**：

| 钩子 | 语义 | 出处 |
|---|---|---|
| `awake()` | 装配阶段：只解析跨组件依赖并缓存引用；**幂等**，不得改动任何玩家可见状态 | `RoleComponent.java:72-74` |

### 3.3 混合期的两套启停机制（**新钩子已广播 + 旧接口仍在**）

> **一句话（截至 commit `a69cdd8`，B②-c 落地后）**：**组件启停 = 容器在三个 legacy 时序点广播新钩子** `awake()` / `start()` / `stop()` —— 广播点与旧扇出**同一时序点**，且 **`stop()` 严格早于 `cancelAllAndClear()`**；混合期**legacy `LifecycleAware` 扇出仍在**，对未迁移组件无影响（它们的新钩子是基类空实现，行为仍由 legacy 路径决定）。

**三个广播点与兜底回收的顺序**（`core/RoleInstance.java`，实测）：

| 顺序 | 广播/动作 | 行 | 语义 |
|---|---|---|---|
| 1 | `component.awake()` | `:662` | 装配后解析跨组件依赖（幂等） |
| 2 | `component.start()` | `:691` | 开始生效 |
| 3 | `component.stop()` | `:725` | 停止生效，**在兜底回收之前** |
| 4 | `componentRegistry.cancelAllAndClear()` | `:853` | 框架兜底取消该组件资源表里的任务（`clear()` 路径） |

> **幂等说明（源码注释，`:720-722`）**：若组件在 `stop()` 里自行取消任务，随后 `clear()` 的 `cancelAllAndClear()` 仍会取消其资源表中的条目 —— 两者**不会对同一组件双触发同一逻辑**（重复取消是幂等的）。

### 3.4 契约事实：**迁移标记只属于主动组件**

> 这一条容易被误读（"为什么 `markMigrated();` 只有 4 处，而迁移进度说 6 个组件已完成"），所以单独写清。

| 事实 | 出处 |
|---|---|
| `isMigrated()` / `markMigrated()` **只定义在 `roleComponent/ActiveComponent.java`**（默认 `false`；由迁移该组件的批次在**自己的构造器**里调用一次） | `roleComponent/ActiveComponent.java:44-52` |
| `PassiveSkill extends RoleComponent` —— **没有**这两个方法（它只有 `displayName`/`description`），**被动也不需要** | `core/PassiveSkill.java:12-25`（`class PassiveSkill extends RoleComponent`） |
| 原因：该标记是**混合期派发判据**，只服务于"能被施放/攻击"的路径（`HotbarActionable.onCast` / `CombatHook.onAttack` ⇒ 旧回调 vs 新管道）；**被动的派发只有生命周期钩子**，容器对**全部已注册组件**无条件广播 `awake`/`start`/`stop`（见 §3.3），因此"迁没迁"只体现在"是否还 implements `LifecycleAware`" | `core/RoleInstance.java:662/691/725`；设计 `docs/组件系统设计-Unity风格.md` §3.1 判据一（无条件广播 → 基类钩子） |
| **B⑤ 将追加 `update` 广播**：届时被动/主动的 `update` 也走新钩子（今天仍是 `instanceof UpdateAware` 扇出，`RoleInstance` 内 3 处） | `git grep -c "instanceof UpdateAware" -- src/main/java/…/core/RoleInstance.java` = **3**（截至 `4dcc6e9`） |

**计数口径（写文档/报进度时必须说明）**：`markMigrated();` 命中数 = **已迁移的主动组件数**（契约上不含被动）；"已迁移组件总数" = 主动（按标记）＋ 被动（按"已改新钩子 + 去 legacy"）。两者不要混用。

## 4. 派发管道：`onCast` / `onAttack` / `CastResult`

### 4.1 唯一的结果语言

`core/dispatch/CastResult.java:7-19`：

| 值 | 语义 | 框架动作 |
|---|---|---|
| `SUCCEED` | 施放成功 | **按 `HotbarItem.getCooldownTicks()` 启动冷却** |
| `NO_COOLDOWN` | 组件已自行处理（含"不做事"） | 框架不动冷却 |
| `REJECTED_DISABLED` | 被沉默/眩晕禁用 | 框架给反馈（action bar；冷却中静默） |
| `REJECTED_NO_ENERGY` | 能量不足 | 框架给反馈 |

信号对象只带"这一次的数据"：`CastSignal(CastTrigger trigger)`（`core/dispatch/CastSignal.java:4`）、`AttackSignal(Player victim)`（`AttackSignal.java:6`）；触发来源枚举 `CastTrigger = RIGHT_CLICK / LEFT_CLICK / DROP`（`CastTrigger.java:4-8`）。**施动者永远是 `svc.self().player()`**，不再出现在参数里。

### 4.2 冷却声明值是唯一真值源（设计 4.7 / O-13）

框架在收到 `SUCCEED` 后统一执行 `componentServices.get(component).cooldowns().start(...getCooldownTicks())`（`RoleInstance.java:192` 技能侧、`:211` 攻击侧；两处都在 `handleCast`/`handleAttack` 内）⇒ 组件**不再自己** `startSkillCooldown(getId(), <字面量>)`。今天之所以有这条要求：技能侧 7 处都写自己的字面量，构造参数里的 `cooldown` **从未被技能读取**（设计 `:286` 的陷阱②）。

### 4.3 新旧两条路径与"混合派发"（**这是当前最重要的现状**）

| 路径 | 入口 | 生效条件 | 冷却由谁启动 | 现状 |
|---|---|---|---|---|
| **旧路径** | `listener/SkillListener`、`listener/MainWeaponListener` → `RoleInstance.castSkillRightClick/…` → 组件旧回调 `onRightClick/onLeftClick/onDrop/onAttack` | 该 id 的组件**未迁移**（`isMigrated() == false`） | 组件自己 | 截至 `b4c1ba4`：8 个主动组件（6 技能 + 2 主武器）里 **2 个**走新管道（B① `RedEvilShockSkill`、B②-b-1 `MeiqiheziUnconcernSkill`）、**6 个**走这里；6 个被动**不经**此管道（走旧 `*Aware` 分派，见 §3.3） |

- 攻击路径：`handleAttack(Player victim, Player attacker)`（`:199-215`）与 `runComponentPipeline` 同构；目前它**没有调用点**（主武器的攻击入口仍由 `MainWeaponListener.onAttackPlayer` 直接走旧回调），因此"主武器迁移"（B⑦）必须同时处理这一入口 —— 属未完成事项。

### 4.4 渲染契约（框架统一渲染，组件不参与）

- 状态判定顺序固定：**冷却 → 禁用 → 能量不足 → 就绪**（`core/hotbar/HotbarRenderer.java:38-49`，状态枚举 `core/hotbar/IconState.java:7-12`）。

## 5. 容器的资源回收与生命周期（已落地部分）

- `TimerPortImpl` 把 `run/runLater/runRepeating` 每个都 `track`（`core/TimerPortImpl.java:24-50`），因此组件即使忘了取消也不会泄漏 —— 但**当前只有端口实现存在，还没有组件在使用它**（见 §6 的计数）。
