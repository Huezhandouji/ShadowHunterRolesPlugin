# 任务卡编写指南（ShadowHunterRoles 重构项目）

> **适用**：队长（立卡人）与执行者（claim 卡的人）。**读完这一份**，可以避免本工程已经踩过的全部卡务坑。
> **口径**：本指南所有约束都是**实测**结论（本晚 300+ 提交、60+ 张卡的现场），不是推测；引用身份一律用 **bytes + SHA256**，**不引行号**（行号是移动靶 ✗）。
> **位置**：`debug-logs/测试记录/任务卡编写指南.md`（本目录被 `.gitignore` 忽略 ⇒ 入库要 `git add -f` ✓）。

---

## §0 一句话

**一张好卡 = 可执行的动作 + 可测量的判据 + 明确不越界的边界 + 执行者不必猜的字段。**
本工程绝大多数返工，都不是技术问题，而是**卡面写得让人猜** ✗。

---

## §1 卡面字段清单（按重要性排序）

| 字段 | 必须 | 写法要点 |
|---|---|---|
| `subject` | ✅ | 一句话说清**做什么**（不要写"修复问题"这种空话 ✗）。含关键词便于日后检索（如"清理批""取证轮""独立复核"）。 |
| `kind` | ✅ | `work` / `requirements` / `implementation` / `verification` / `review` / `repair` / `integration`。**决定校验器要不要 `inScope`/`verify`/`reviewedTaskId`/`sourceTaskId`**（见 §3）。 |
| `objective` | ✅（质量类必填） | 「做到什么程度算成功」——比 subject 具体一层，可被验收条目分解。 |
| `description` | ✅ | **背景 + 事实（带时刻的现算值）+ 要做什么 + 边界**。把"为什么现在做"写清，避免执行者重做已完成的事 ✗。 |
| `inScope` | ✅（implementation/repair） | **仓库相对**路径清单（POSIX 正斜杠）✗。**证据文件名必须在这里逐字出现** ✗（见 §5）。 |
| `outOfScope` / `nonGoals` | 建议 | 明确"不要做什么"：`api/**`、`ComponentServices` 成员数、事件发布、注册方式、git 写…… |
| `acceptance` | ✅（质量类） | **逐条可测**的验收项；结卡时**必须逐条给 `acceptanceResults`** ✗（见 §3 第 7 条）。 |
| `verify` | ✅（implementation/repair） | **执行者真会跑的命令**（要能贴进 `commandsRun`）✗；**不要**写会随环境漂移的期望（见 §5 陷阱 ③）。 |
| `deliverables` | 建议 | 预计产出的文件（与 `inScope` 一致）。 |
| `dependencies` | 建议 | 前置卡 id。**注意**：依赖一旦 `cancelled`/`failed`，下游**永久阻塞** ✗ ⇒ 用**替代卡链**。 |
| `assignee` | 建议 | 指定成员；不指定则进共享池（但本工程实践中**指定更可靠** ✓）。 |
| `reviewedTaskId` | ✅（review） | 被评审的卡。 |
| `sourceTaskId` / `sourceFindingIds` | ✅（repair） | 修的是哪张卡的哪条 finding。 |
| `round` | review/repair | 1-based 轮次；**修复循环要递增** ✓。 |

**命名建议**（证据件）：
```
阶段<N>-<主题>-说明.txt      ← 交付说明（含判据、身份、口径）
阶段<N>-起服日志-<主题>.log  ← 冻结日志（仍在服务器在线时复制 ✓）
阶段<N>-<主题>-停服物证.txt  ← 停机三路互证 + 冻结件身份
阶段<N>-<主题>-独立复核报告.md（verification 类）
```

## §2 立卡前必须现算的三件事

1. **目标路径现在是什么状态？**（`git status --porcelain -- <path>`；`git log -1 -- <path>`）
   —— 不要凭记忆写"应改成 X"，先看它现在是不是已经是 X ✗（本工程多次发生"卡在追一个已完成的目标" ✗）。
2. **有没有别人的卡占着同一路径？**（工具会拒：`inScope overlaps … serialize these tasks or split the paths` ✗）
   ⇒ 要么**串行**（等它结卡再立），要么**拆路径**（本工程实例：清理批因 `command/**` 与在办卡重叠 ⇒ 拆成"只删死 import" + "指令层收尾留给后续卡" ✓）。
3. **这活是不是已经做完了？**（查 `git log`、查 `debug-logs/测试记录/` 里的证据件）
   —— 若已完成 ⇒ **不要立卡** ✗，改为在台账/交接件里登记 ✓。

## §3 工具层的硬约束（实测，违反即拒收）

1. **`inScope` 重叠会被直接拒** ✗ ⇒ 串行或拆分。
2. **`changedPaths` 必须 ⊆ `inScope`，且用仓库相对形式** ✗
   —— 写成工作区相对（带仓库目录名前缀）会被判 `is undeclared` ✓；实际改了 `inScope` 外的文件必须**主动申报 + 队长追认**（先例：`t39`/`t50`/`t59`/`t65`/`t66` ✓）。
3. **`verify` 的每一条都必须出现在 `commandsRun` 里** ✗
   —— 否则校验器拒：`implementation completion requires a passed commandsRun entry for every verify command` ✓。
4. **`implementation`/`repair` 必须给 `inScope` + `verify`**；`review` 必须给 `reviewedTaskId` + `verdict`；`repair` 必须给 `sourceTaskId` + `sourceFindingIds`。
5. **终态卡（`completed`/`failed`）不可回填、不可改派** ✗
   —— 内容再有更新，只能**新开卡/勘误件**（先例：报告 v1→v4 用"新修订 + 取代申报"表达，不改已结卡的 output ✓）。
6. **`implementation` 结卡要求逐条 `acceptanceResults`** ✗
   —— 若**无法逐字复现卡面 `acceptance` 条目**，**不要伪造完成** ✗；按"**作废（cancelled）**"处置并在 output 写明理由（本工程实例：`t65` 内容早已交付、只剩手续 ⇒ 作废 ✓）。
7. **一个成员不得同时持有两张未完成卡** ✗
   —— 立卡时先查该成员名下是否有未完卡；冲突时由队长把旧卡收到自己名下或作废 ✓。
8. **失败/取消的尝试会污染后续 update**（同一卡后续要极简 payload ✓）。
9. **移除成员会把其名下历史卡回池重派** ✗
   —— 回池后要**主动制止死卡重做** ✓；执行者遇到"派单但 `attempt_id` 与结卡时相同"⇒ **不 claim、不重开、上报一行** ✓。
10. **卡面契约不可编辑**（`inScope`/`acceptance` 立了就改不了 ✗）
    —— 所以**立卡前把字段想清楚**；要扩围只能"报文授权 + 队长追认"或**新开卡** ✓。

## §4 验收条目的写法（本工程最贵的经验）

**模板**：`【判据】+【命令】（作用域 + 匹配形态 + 口径）+【期望值】+【若不符怎么办】`

1. **一条判据只测一件事**，且**可复算**：给出**具体命令**（含作用域与匹配形态 ✓），不要写"检查是否正确" ✗。
2. **口径三件齐** ✗：**模式 + 定域 + 口径（行级 / 出现次数 / 是否含注释 / 是否含定义）**。
   实例：`sendKey` 的"处数"有三种数法 —— 裸词无边界不分大小写 **15** / 大小写敏感 **15** / **仅调用点 14** ✓ ⇒ 不写口径 ⇒ 同一条命令测出两套结论。
3. **锚串是更长标识符子串时，必须加词边界 + 显式大小写** ✗
   —— `cooling=` ⊂ `wasCooling=`（曾被吞成 9 vs 6）· `send` ⊂ `sendKey` · `[sched]` ⊂ 裸词 `sched` ⇒ 写 `\bcooling=true` / `\bsendKey\(` / `\[sched\]` 并显式 `-CaseSensitive` ✓。
4. **区分"归零组"与"减少组"** ✗
   —— 真删代码的批，双口径期望是 **delta < 0 且逐条可解释**（+ (d) 逐条申报），**不是"0 行"** ✗；"归零"只适用于"期望消失"的判据 ✓。
5. **单一范围扫描不能支撑全局断言** ✗
   —— 实例：只在"被复审的那一轮"里测到 0，就写成"全局未覆盖" ⇒ 实际同一制品身份的另一轮里已有 1 命中 ✓ ⇒ 断言要写**范围**，或**横扫同一 artifact identity 的全部已冻结轮** ✓。
6. **静态级 vs 运行级必须分开写** ✗
   —— "源内有调用" ≠ "运行时真有输出"；要求运行级就必须说明**在冻结件里 grep 到什么** ✓。
7. **仪器必须双向自证** ✗（本工程最有价值的一条）
   —— 断言要在**已知为负样本上报 MISMATCH**、在**已知为正样本上报 OK**；只证明"正样本能过"= 可能有真空通过 ✓（实例：某 runner 的冷却断言是**析取**，而 usage 行同时含 `cooldown/end/restart` ⇒ 没跑过也全绿 ✗）。
8. **必须包含"未覆盖项如实申报"条款** ✓
   —— 让执行者把"没跑的""只有静态级的""需要外部环境的"逐条写出来；**不写 = 卡不完整** ✗。
9. **需要起服的卡，把顺序写进验收** ✓
   —— 广播 → 窗口三路互证 → （必要时先重建）→ 起服 → **仍在线时先冻结日志** → 只 `job_kill` → 三路复证 ✓；并写明**证据必须自绑定**（commit + jar SHA256 + 日志身份 + F1 链 ✓）。
10. **"期望值必须与测量口径同写"** ✓ —— 否则同一张表会被测成两套结论（本工程当晚出现 3 次 ✗）。
11. **【已实测 · 「真空轮」】`verify` 里的路径必须先在写卡时验证存在** ✗
    —— 若路径写错 / 指向不存在的文件，比对类工具可能**在抛参数错之后仍然写出「通过」报告**：
    实测工具 = `.scratch/bot/log-delta.ps1`（89 行 / `4A5A88B0…082C`）——`:29` 对不存在的路径 `return @()` ⇒ PowerShell 把空数组解包成 `$null` ⇒ `:46` 的 `Compare-Object -DifferenceObject $null` 抛 `ParameterArgumentValidationNullNotAllowed`；而 `:25` 是 `$ErrorActionPreference = 'Continue'` ⇒ 脚本**继续**执行到 `:56-59`，照样输出 `current 行数 = 0 / ADDED = 0 / REMOVED = 0` ⇒ **外观完全像通过** ✗。
    **四元组实测**（`t27` 双跑，两份落盘件在**仓库外**：`.scratch/bot/logdelta-t27-verbatim.txt` 785 B / `logdelta-t27.txt` 782 B）：
    - **甲（原样 · 路径笔误 `runtime\logs\latest.log`）= `anchor 13 / current 0 / ADDED 0 / REMOVED 0`** ⇒ **真空通过（该次读数无效）** ✗
    - **乙（修正为 `run\logs\latest.log`）= `anchor 13 / current 13 / ADDED 0 / REMOVED 0`** ⇒ 有效 ✓
    ⇒ **关键结论**：`C=0` **单独**没有能力区分"有效"与"拿空气比对"（真空轮的 ADDED 与 REMOVED **也都是 0** ✗）—— 该 0 的含义是"两侧都是空集"，与"两侧相同"不可区分。
12. **`verify` 写法硬规则（三条，写卡时逐条自检）** ✓
    ① **路径必须先证存在**：`verify` 里出现的**每一个路径**，写卡前都要现算一遍（`Test-Path -LiteralPath '<绝对路径>'`）；外部工具的命令同理 —— **先证工具可调用 + 输出非空**（空 vs 空 = 相等，是本族最危险的假阳性 ✗）。
    ② **凡「应为 0」的判据，不得只写一个聚合量** ✗：禁止"**只看 `C=0`**"这类单条件；必须写成**多条同时成立**，例如
    `ADDED=0` **∧** `REMOVED=0` **∧** `current 行数 = <写卡时现算值>`（三条全真才算过；任一缺项 ⇒ 该轮**无效**）。
    ③ **每条判据都要附「已知为真」的正样本读数**：本例即乙跑的四元组（`anchor 13 / current 13 / ADDED 0 / REMOVED 0`）—— 没有正样本，读者无法判断"这个 0 是干净、还是没跑到文件" ✗（与 §4 第 7 条「仪器必须双向自证」同源）。
13. **判据自检的「旧侧样本」必须取【改写前】的提交** ✗
    —— 用于证明"判据有区分力"的旧样本，必须取**改写发生之前**的修订点（`git grep -n -E -f <模式文件> <commit> -- <路径>`，或 `git cat-file blob <rev>:<路径>` 逐字节落盘后再测）。
    **不得**取「**产物入库的那一次提交**」✗ —— 那一次的内容已经是**改写后**版本 ⇒ 旧侧也报 0 ⇒ 看起来像"**判据没有判别力**"，实际是**样本取错** ✗。
    实例：文档痕迹判据的旧侧样本 = `0c6930d:docs/插件文档/架构与组件模型.md`（旧侧 8 条集合非 0 = `27 / 30 / 44 / 31 / 27 / 19 / 4 / 58`，新侧 `0 / 0 / 版本号 / 0 / 0 / 0 / 0 / 0`）；反向实例 = 若改取"重写产物入库的那次提交"，同一批模式会得到 0 ⇒ 假"判据无效" ✗。

## §5 立卡人最容易犯的五个错（本工程实测，含队长自己的）

| # | 错 | 后果 | 正确做法 |
|---|---|---|---|
| ① | **两张卡 `inScope` 写了同一个文件名** ✗ | 两位执行者撞车；后到者只能改名或停手 | 立卡时**分配文件名**；若已撞车，队长**整件改名对齐**（内容/身份不变 ✓）并在卡外登记 ✓ |
| ② | **执行者看不到卡面字段**（只在报文里口头说要求）✗ | 执行者按自拟名写文件 ⇒ `changedPaths ⊆ inScope` 拒收 | **关键指令用立卡/改派**（把字段写进卡或写进改派 reason ✓）；消息通道偶有不可靠 ⇒ 别只靠聊天 ✓ |
| ③ | **`verify` 写死会随环境漂移的期望** ✗ | 例如 `git status --porcelain -- src` 期望"空"，而他人批次正在途 ⇒ **假失败** | 期望要么只针对**自己改的路径**，要么写明"在他人批次之外"；或改成"我这几条路径为空" ✓ |
| ④ | **`acceptance` 条目写得无法逐字复现** ✗ | 结卡时校验器要求逐条 `acceptanceResults` ⇒ 卡无法正常结 | 验收条目**编号 + 短句 + 单义**；必要时把长条目拆成多条 ✓ |
| ⑤ | **把"运行级"写成"静态级"就算覆盖** ✗ | 后人以"已覆盖"作断言时掺了假 | 见 §4 第 6/8 条 ✓ |

**另外两条执行者侧纪律**（写进卡的 `acceptance` 更保险 ✓）：
- **承重证据必须落在受版本控制的位置** ✗（实例：闭环依赖的 chat 侧原始转录原先在**仓库外的兄弟目录** ⇒ 一旦被清理，已入库证据的引用就悬空 ✓）。
- **引"代"必须点名 `commit`/`tree`（或 jar 身份）** ✗ —— **禁用"HEAD 的 tree"这种相对说法**（实例：`t60` 一改 `src/main`，被复审 tree 就不再等于 HEAD 的 tree ✓）。

## §6 三类卡的骨架模板（可直接复制改写）

### 6.1 implementation 卡（改代码）
```
subject      : <动作> + <对象>（如"清理批：删 X 的死 import"）
kind         : implementation
objective    : 达成 <可观察结果>，并自带构建/Mode B/物证/归档证据
description  :
  【背景】<为什么要做；带时刻的现算事实>
  【要做什么】<逐条>
  【边界】零 git 写；不动 api/**；不改注册方式/语义；<其它红线>
inScope      : <仓库相对路径：源码 + 三份证据文件名（逐字）>
nonGoals     : ["改动 <无关包>", "更改语义", "在 <前置> 之前动手"]
acceptance   : [
  "【归零组】<命令 + 口径> ⇒ 期望 0",
  "【减少组】双口径 delta < 0 且逐条可解释（含 (d) 申报），不得写'0 行'",
  "构建通过：最新 .class + src 新于 jar = 0",
  "Mode B 三行 + 正序集合差只看 C=0（锚 <参考日志>）；**并同时给 `ADDED=0` ∧ `REMOVED=0` ∧ `current 行数 = <现算值>`**（§4 第 12 条：`C=0` 单独不构成判据）",
  "证据自绑定：commit + jar SHA256 + 日志身份 + F1 链",
  "新代制品归档 + MANIFEST 追加一行（一行一值）",
  "未覆盖项如实申报（无则写'无'）"
]
verify       : ["git status --porcelain -- src", "git rev-parse HEAD", "<本卡专属判据命令>"]
deliverables : ["<源码路径>", "阶段<N>-<主题>-说明.txt", "阶段<N>-起服日志-<主题>.log", "阶段<N>-<主题>-停服物证.txt"]
```

### 6.2 verification 卡（独立取证/复核）
```
subject      : <对象> 的独立 <复核|取证>（含 <逐条判据>）
kind         : verification
objective    : 不引用实现者结论，自行现算 <判据集> 并给 verdict
description  :
  【背景】<已知状态 + 身份>
  【要做什么】① 自行现算判据 ② 基线自证 ③ <三代锚/双路径> ④ 对实现者申报逐条给结论
  【边界】只读为主；不改 src/历史证据；不起服（需要时写明窗口纪律）
inScope      : ["阶段<N>-<主题>-独立复核报告.md"]
acceptance   : [
  "判据逐条自算（给出命令 + 期望 + 实测）",
  "基线自证：快照逐件与点名 commit/tree 的 blob 比对（不只自洽）",
  "作用域标注：<行级/出现次数、src/全仓、白名单内外> 逐条写明",
  "实现者申报逐条核验（含'未覆盖项'是否属实）",
  "已知未闭合项给出裁断（覆盖 / 仍缺 / 需新卡）",
  "边界：未起服 / 未改 src / 未做 git 写"
]
verify       : ["git rev-parse HEAD", "git status --porcelain -- src", "<判据命令>"]
```

### 6.3 review 卡（评审"该不该算完成"）
```
subject      : <批次> 评审（verdict + findings）
kind         : review
reviewedTaskId : <被评审卡>
objective    : 对 <被评审卡> 出 verdict（pass / needs_revision / reject），findings 分级并给 requiredFix
description  : 【必查项】① 自带物证覆盖自己的制品 ② 判据口径是否写全 ③ 有无'静态级冒充运行级' ④ 参数/顺序等逐调用点核对
acceptance   : ["verdict = <期望>", "findings 分级（blocker/high/medium/low）+ requiredFix", "复核实现者身份与 F1 链", "不替被评审卡下结论以外的事"]
```
**评审分离纪律** ✗：**验证与评审必须是不同的人**；**同一成员不得同时持有某卡与其下游评审卡** ✓（实例：曾有成员被同时派了 verification 与其下游 review ⇒ 正确处置 = **拒绝 claim + 上报** ✓）。
