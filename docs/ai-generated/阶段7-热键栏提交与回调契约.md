## §0 用户设计原话（逐字，本件的唯一需求来源）

> 「`HotbarRenderComponent` 负责接受其他组件发来的一个 `ItemStack`，然后绑上 PDC，然后渲染物品（使用守护监听器保证物品不可移动不可丢弃），然后返回一个『句柄』，使得其他组件可以设置物品被左右 Q 键点击时的回调。」

**拆成五步机制链**（本件逐段定契约）：

```
① 提交 (submit)  →  ② 绑身份 (bind PDC)  →  ③ 落位渲染 (render)
                                            →  ④ 守护 (guard)  →  ⑤ 句柄 (handle) → 回调派发
```

**范式变更（一句话）**：现形态是**拉取式**（帧末 flush 时渲染组件遍历容器、问每个组件的 `buildItem()`）；
新形态是**提交式**（组件在**自己的时机**把「要显示的样子」连同**键回调**交给机制面，机制面负责绑身份、落位、守护、派发）。

## §2 ★ PDC 身份契约定案（第一优先）

### 2.1 为什么这是第一优先

守护监听器的**唯一判据**就是**热键栏身份键**（候选② 下 = 新增的单一键；两旧键退场）：

```
private static boolean isProtected(ItemStack item) {
    return Skill.Utils.isSkillItem(item) || MainWeapon.Utils.isMainWeapon(item);
}
```

⇒ **键是「受保护」的全部依据**。换键而不同步改守护 ⇒ `isProtected` 恒 `false` ⇒ **守护静默失效**：
物品可被**拖拽**、可被 **F 键换手**、可被**漏斗搬走**（合成格那项本来就只算「尽力而为」，见该类 javadoc 自陈）。
**最坏情形**：机制面照常渲染、玩家照常点击能用，但物品能被打进箱子/别的玩家背包 ⇒ **能力外流**，且**没有任何编译期或测试期信号**。

★ **本件已按用户裁定改为候选②**（单一新键 + 值用随机 UUID）⇒ 这条风险从「假设」变成**必然发生的迁移面**，其逐处清单与缓解措施见 §2.5 / §2.6，**不得省略**。

### 2.2 三种候选与取舍（★ 最终依据 = **用户裁定**）

| # | 候选 | 优点 | 代价 / 风险 | 判定 |
|---|---|---|---|---|
| ① | **保留两个既有键**（`"skill_id"` / `"main_weapon_id"`），只把**写入点**从家族基类搬到机制面 | ①**零迁移**：现存物品仍被识别与保护；②守护**一个字都不用改**；③键名与值语义是已入库的「冻结面」 | 机制面要「知道该写哪个键」⇒ 需提交时携带**家族/键选择**；且「身份」仍是**家族 id**（同一组件的多件物品**无法区分**）⇒ 句柄只能按「组件 + 槽位」认，无法按**物品实例**认 | ★ **已被用户裁定取代**（原为本件自选，见 §10 冲突 ④） |
| ② | 新增**单一**键（`"hotbar_id"`），**值 = 该物品实例的随机 UUID**，两旧键退场 | ① 键语义最干净（**一个键 = 一个身份**）；② 身份粒度 = **物品实例**（同一组件可提交多件、各自独立句柄）；③ 机制面**不再需要**「写哪个家族键」的入参 ⇒ 更少耦合 | ★ **破坏性**：现存背包里带旧键的物品**全部不再被识别**（守护失效 + id 取不到 + `clearFrom` 扫不到）⇒ 必须给**逐处迁移清单 + 风险与缓解**（§2.5 / §2.6） | ★★ **采用** —— 依据 = **用户裁定原话「选 2，用随机 uuid」** |
| ③ | 单键 + **同时写旧键**（双写过渡） | 兼容 + 可渐进 | 两键共存期「哪个是真身份」必须写死，否则**双重身份**（同一物品既是 `skill_id` 又是 `hotbar_id`）；过渡结束后这笔债还得再收一次 | **不采用**（双身份是新的歧义源） |

★ **候选③+（队长代裁的变体）** 与 **候选①（本件原自选）** 均已被**用户裁定② 取代** ⇒ 后续任何实现**不得再按候选① 落地**（记载见 §10 冲突 ④）。

### 2.3 ★ 定案（逐条可施工 · 候选② + 随机 UUID）

1. **新增单一身份键**：`"hotbar_id"` —— 定义位置 = **机制面**（`HotbarRenderComponent` 侧，`public static final NamespacedKey HOTBAR_ID_KEY = KeyFactory.Registry.of("hotbar_id")`）。
   - ★ **命名约定与既有键逐字一致**：`KeyFactory.Registry.of(String)` 的**唯一入口**（`KeyFactory.java:20-38`），与 `Skill.Utils.SKILL_KEY = KeyFactory.Registry.of("skill_id")`（`Skill.java:211-213`）· `MainWeapon.Utils.MAIN_WEAPON_KEY = KeyFactory.Registry.of("main_weapon_id")`（`MainWeapon.java:189-191`）同形；
   - 键名 `hotbar_id` **现算全库未占用**（复算见 §9 V1 末段）✓。
2. **值语义 = 该物品实例的随机 UUID**：`PersistentDataType.STRING`，值 = `UUID.randomUUID().toString()`。
   - ★ **与既有 UUID 字符串存法同形**：`DamageUtil.LAST_DAMAGER_KEY`（`core/util/DamageUtil.java:20` 定义 · `:56-57` 以 `PersistentDataType.STRING` 写入 · `:25-27` 读出后 `UUID.fromString`）⇒ 本键照抄这一形态；
   - **每次「绑键步」为每个物品实例生成一个新 UUID** ⇒ 身份 = **物品实例**，不是「组件 + 槽位」。
3. **写入点 = 机制面的「绑键步」**（`HotbarRenderComponent`）：
   - 提交内容到达机制面后，机制面**自己**把 `HOTBAR_ID_KEY` 写进 `ItemMeta` 的 PDC（值 = 本实例新生成的随机 UUID）；
   - ★ **写入仍然唯一**：每个物品**恰好一次** `setItemMeta` —— 机制面在**同一次** `setItemMeta` 之前完成写键；**不得**先 `setItemMeta` 再取回 meta 二次写入；
   - ★ 家族基类 `buildItem()` 里那一行写键（`Skill.java:202` · `MainWeapon.java:180`）**随旧键族迁移一并移除**（清单见 §2.5）；
   - ★ 机制面**不再需要**「该写哪个家族键」的入参 ⇒ `HotbarFamily` **不再承担键选择职责**（保留与否见 §3.1 的改写）。
4. **身份权威 = 新键**：判定「这是不是热键栏物品」**只看** `HOTBAR_ID_KEY`；两旧键**退场**（定义与读写全部移除，清单见 §2.5）。
   - ⇒ 守护监听器**必须**改判据（旧判据 = 两个家族 `Utils`）；处置见 §2.4 定案与 §2.6。
5. **同一组件可提交多个物品实例、各自独立句柄**：身份是**每实例 UUID** ⇒ 同一组件对**不同槽位**、甚至同一槽位的**不同物品实例**都能各自持有句柄；句柄按**实例**认，不按「组件 + 槽位」认。
6. **同一组件对同一槽位重复提交的语义 + 注销粒度**：
   - **重复提交 = 替换**：同一 `slot` 再次 `submit(...)` ⇒ 机制面为该次提交生成**新的 UUID**、**旧实例的句柄立即失效**（与 `replace()` 同语义，§4.1 第 4 行）；旧物品若仍在背包里，会在**同一次落位**被新物品覆盖（写点仍唯一，§3.3）；
   - **注销粒度 = 按实例**：`release()` 只注销**该句柄对应的那一个物品实例**，**不**影响同一组件的其他句柄、也**不**影响同槽位的其他实例（后者已被上一条的替换语义接管）；
   - ★ **粒度写死的理由**：身份是实例 UUID ⇒ 「按组件注销」「按槽位注销」都会与「同一组件多实例」直接冲突（会误注销兄弟句柄）。
7. **机制面不新增第三套识别逻辑**：机制面**只读自己的** `HOTBAR_ID_KEY`（`has` / `get`），**不再**经 `Skill.Utils.isSkillItem` / `MainWeapon.Utils.isMainWeapon`（那两个 `Utils` 随旧键族退场，见 §2.5）。

★ **兼容读与否的定案（必选其一）**：**选 ② 不兼容读（守护只认新键）**。理由：
1. **与「旧键族退场」口径一致**：本卡第 ② 项的判据是「**旧键 writer 归零**」；若守护兼容读旧键，则旧键仍被**读取**（消费者未退场）⇒ 「归零」只能做到一半、后续还得再收一次；
2. **不引入双重身份**：兼容读 = 同一物品可能同时被两套判据认（正是 §2.2 候选③ 被否的理由）⇒ 候选② 的价值（一个键 = 一个身份）会被抵消；
3. **代价可控且可观测**：窗口期后果已逐条列出（§2.6），且**有缓解措施**（一次性重刷 + 渲染覆盖 + 异常留痕）。

**§2.5.1 旧键 writer 归零的判据（可跑）**：
- ★ **writer 归零**：`src/` 内 `getPersistentDataContainer().set(Utils.SKILL_KEY` 与 `…(Utils.MAIN_WEAPON_KEY` 命中 = **0**（命令见 §9 V1b）；
- ★ **键字面量归零**：`src/` 内 `"skill_id"` 与 `"main_weapon_id"` 命中 = **0**；
- ★ **键常量归零**：`src/` 内 `SKILL_KEY` / `MAIN_WEAPON_KEY` 命中 = **0**（含注释 —— `KeyFactory` javadoc 与两 `Utils` 的 javadoc 都要同步）；
- ★ **新键唯一**：`src/` 内 `HOTBAR_ID_KEY` 定义 = **1 处**（机制面）+ 读取口 = 机制面与守护各 1 处（判定面**唯一**）。

### 2.6 ★ 迁移风险与缓解措施（如实保留 —— 这是候选① 的核心理由，改采纳② **不得删**）

**风险本体**：现存玩家背包里**带旧键**的热键栏物品，在候选② 落地后**不再被识别** ⇒ 三条后果**同时**发生：

| # | 后果 | 具体表现 | 可观测性 |
|---|---|---|---|
| ① | **守护失效** | 旧键物品可被**拖拽 / F 键换手 / 漏斗搬走** ⇒ **能力外流**（打进箱子或别的玩家背包） | ★ **无编译期/测试期信号**；仅能靠端到端判据（§2.6.1）事后发现 |
| ② | **id 取不到** | 施放/攻击路径取不到 id ⇒ 旧键物品**点了没反应**（但物品外观照旧 = 玩家会当成 bug） | 玩家可感知；服务端**无**日志（该路径不报错） |
| ③ | **清角色扫不到** | `HotbarItems.clearFrom` 只认新键 ⇒ 旧键物品**清角色时不被清除**，留在背包里 | 玩家可感知（物品残留） |

**渲染覆盖时机（窗口多长）**：
- 机制面**只在自己渲染某槽位时**才给该物品写新键 ⇒ 覆盖发生在「**该槽位下一次被渲染**」时；
- 帧末 flush 的入口条件是「①已置脏 **或** ②外观依赖活状态且占栏位者正在冷却」（§7.4，**逐字保留**）⇒ 若组件已提交且本帧置脏（§7.4 新增的「提交必须置脏」），则**下一帧末**即覆盖该槽位 ⇒ **窗口 ≈ 1 tick**；
- ★ 但**窗口不是有界的**：若该槽位**本版未被提交**（组件未迁移到提交式、或该组件本轮不提交），则该槽位**永不**被覆盖 ⇒ 旧物品**长期残留**；
- ⇒ **结论**：覆盖窗口 = 「**1 tick（已提交）～ 永不（未提交）**」，**不能**当作有界迁移保证。

**★ 不可消除的缺口：离线玩家背包**：
- 服务端**无法**给离线玩家的背包物品改 meta（Bukkit 的 `PlayerInventory` 只在玩家对象存在时可写；离线玩家的 `Player` 不可得）⇒ **离线玩家背包里的旧键物品 100% 无法被覆盖**；
- ⇒ 这是候选② 的**结构性代价**，**无法消除**，只能靠**缓解措施**（下方）或「登录后首刷」把窗口缩到「登录 → 首刷」之间。

**缓解措施（三选，逐条注明代价）**：

| 措施 | 做法 | 代价 |
|---|---|---|
| **A. 守护临时兼容读旧键** | `isProtected` 在过渡期写成「新键 **OR** 两旧键」 | ★ 与 §2.5 定案的「不兼容读」**冲突**（要么改判据、要么留窗口）；且旧键消费者**不归零** ⇒ 后续还得再收一次；**本件不采用**（仅在必要时作为**限时**过渡，须另立卡） |
| **B. 双写过渡** | 机制面同时写新键与旧键 | ★ 正是候选③ 被否的理由（**双重身份**、歧义源）；且旧键 writer **不归零** ⇒ 与第 ② 项判据冲突；**本件不采用** |
| **C. 一次性重刷流程**（★ **本件采用**，与 §2.5 的「不兼容读」配套） | ① 部署窗口内对**在线**玩家执行一次整栏重写（既有 `firstFlush` 行为天然覆盖「已提交」槽位）；② 对**离线**玩家：登录时由角色装配路径照常首刷 ⇒ 把窗口缩到「登录 → 首刷」；③ **旧键物品一旦被点击/拖拽即留痕**（§5.2 的 `[hotbar]` 日志 + 守护改判后不再拦截 ⇒ 必须在实现卡里把「旧键物品命中」写成 `WARNING` 一行，**不静默**） | ★ 代价：① 只能覆盖在线玩家 + 登录后首刷的玩家，**离线期间**的旧物品仍可能被拖走（窗口 = 登录前）；② 需要实现卡新增一行「旧键命中」告警日志（**新增可见行为**，须登记） |

★ **缓解措施的验收口径**：三事件（拖拽 / F 键 / 漏斗）对**新键**物品必须被拦；对**旧键**物品**不再被拦**（这是预期的破坏面）但必须**留一行可 grep 的日志** ⇒ 判据 = 「破坏面可观测，不是静默」。

**§2.6.1 三项验证方式（与 §2.3 第 4 条的反向判据一并保留）**：
1. **新键物品被保护**：提交 → 渲染出物品 → 拖拽 / F 键 / 漏斗搬运三事件**都应** `setCancelled(true)`（取证 = `run/logs/latest.log` 原始行 + 物品仍在原位）；
2. **旧键物品是否仍被保护**：拿一件带 `skill_id` 的物品试同样三事件 ⇒ **预期：不再被拦**（这是本设计**预期**的破坏面）⇒ **必须同时看到一行 `[hotbar] legacy-key item …` 告警**（否则就是静默失效）；
3. **无键普通物品不被误保护**：普通石头/玩家自己的物品 ⇒ 三事件**都不被拦**、且**无**告警行（防「判据过宽」）；
★ **反向判据（保留）**：临时把绑键步写入的键**故意写错**（只在本地实验里改）⇒ 上述三事件应**不再被拦**；若仍被拦，说明拦的不是这个键 ⇒ **判据本身失效**（不是实现通过）。

## §3 ★ 提交 / 渲染契约定案

### 3.1 提交入口（签名定案）

机制面新增**一个**公开提交入口（**新增**，不替换 `Plan` 的既有拉取路径 ⇒ 两路可共存，见 §7.3）：

```java
// 在 HotbarRenderComponent 上（组件实例方法；提交者就是调用者自己）
public HotbarItemHandle submit(HotbarItemSpec spec);

// 提交内容：物品的「样子」+ 身份 + 槽位 —— 全是数据，不含 Bukkit 事件类型
public record HotbarItemSpec(int slot, String componentId, HotbarFamily family, HotbarItemView view) {}

public enum HotbarFamily { SKILL, MAIN_WEAPON }
```

- **`componentId`**：提交者自己的注册 id（= PDC 键的**值**）。**以字符串传参**，不传 `RoleComponent` 引用、更不传具体组件类型 ⇒ 机制面不需要提交者的类型（§8 分层判据）。
- **`family`**：决定写哪个键（`SKILL` → `SKILL_KEY`；`MAIN_WEAPON` → `MAIN_WEAPON_KEY`）。**用枚举表达家族**，不在机制面出现 `Skill` / `MainWeapon` 类名。
- **`view`**：物品的**语义外观**（材质 / 显示名 / 描述 / 状态行 / 是否加粗…）—— 由组件给出（`IconState` 那一族的产物 + 文案），机制面**只组装**、不做状态判断。
  - **判据**：机制面收到 `view` 后**不得**读取任何组件状态（冷却 / 能量 / buff）；「现在该显示成什么样」是**提交者**在提交前算好的。
- **`slot`**：槽位仍**来自组件表现规格**（`specification.slot()`），由提交者给出（§7.2）。
- **`ItemStack` 变体（等价入口，二选一即可）**：若某组件已自行产出完整 `ItemStack`（如既有 `buildItem()`），机制面接受 `ItemStack` 形态并在其后绑键；**两种入口共用同一绑键与落位路径**，不得各写一套。

### 3.2 返回句柄：类型与能力（定案）

```java
public interface HotbarItemHandle {
    // ① 回调设置（三键全覆盖；null = 清除该键回调）
    HotbarItemHandle onLeftClick(Runnable callback);
    HotbarItemHandle onRightClick(Runnable callback);
    HotbarItemHandle onDrop(Runnable callback);

    // ② 只读查询：本句柄当前对应的槽位（未落位 / 已失效 ⇒ OptionalInt.empty()）
    OptionalInt slot();

    // ③ 注销 / 替换
    void release();                 // 注销：此后本句柄不再收到任何回调
    HotbarItemHandle replace(HotbarItemSpec spec);   // 替换内容：槽位可变；旧句柄随之失效
}
```

**能力面逐条理由**：

| 能力 | 为什么必须有 |
|---|---|
| `onLeftClick` / `onRightClick` | 用户原话「设置物品被左右 Q 键点击时的回调」 |
| `onDrop` | Q 键**已被复用为"用技能"**（既有行为：`PlayerDropItemEvent` 被取消且当作一次施放）⇒ 三键必须同类 |
| `slot()` | 既是组件需要（自检/调试），也是**验证卡**需要的可观察量（见 §9 V5） |
| `release()` | 组件**主动**放弃（组件自己停用某件物品）——与「被动失效」（§4）分开 |
| `replace(...)` | 同一槽位换内容（如主武器换形）**不必**注销再提交（否则中间有一帧无主状态） |

### 3.3 与 `HotbarRenderer` 的关系（唯一写点不得增加）

- **写点仍是 `HotbarRenderer` 里那一次 `inv.setItem(...)`**（全库 `inv\.setItem\(` 必须仍 = **2**）。机制面**只产出计划**，不自己写背包。
- `HotbarRenderer.Entry(slot, item)` 与 `Plan` **保留**（§7.2）：提交进来的条目最终**经由同一 `Plan` 交到同一写入循环**。
- ★ **禁止**在 `HotbarItemHandle` 的任何方法里直接 `player.getInventory().setItem(...)` —— 那会引入第二个写点，直接违反已入库判据。

## §4 ★ 句柄失效语义（绝不允许回调在失效后被调用）

### 4.1 四类失效事件与定案

| # | 失效事件 | 触发点（现状锚点） | 定案 |
|---|---|---|---|
| 1 | **组件 `stop()`** | 生命周期：容器在两阶段生命周期里对每个组件调 `stop()` | `stop()` 返回后，该组件提交的**全部句柄立即失效**（回调不再被调用） |
| 2 | **组件被隔离** | 组件在受保护调用里抛异常 ⇒ 入隔离队列 | **立即失效**（与 #1 同级）；语义理由：被隔离的组件**不得再被驱动**，回调也是驱动 |
| 3 | **角色清除 / 玩家离线** | 静态清除路径 `HotbarItems.clearFrom(player)`；死亡 / 重生 / 掉线三条调用链 | 该实例的**全部句柄失效**；物品本身由既有清除路径清掉 |
| 4 | **`release()` / `replace()`** | 组件主动 | 立即失效；`replace()` 返回**新句柄**，旧句柄失效 |

### 4.2 「绝不允许失效后被调用」的实现契约（三条，必须全做）

1. **失效 = 句柄内部状态翻转**（一个 `volatile boolean live` 或等价物），**不是**靠调用方自觉；
2. **机制面在派发前逐句柄检查**：`if (!handle.isLive()) return;` ⇒ 已失效句柄的回调**不可达**；
3. **失效必须发生在「同一趟交付窗口之外」**：若失效发生在某次正在进行的派发窗口内（例如某句柄的回调里把另一个组件隔离了），
   则**本次窗口内已经取出的句柄仍按已交付处理**（与既有「逐监听器隔离 + 同窗口」语义一致），**但下一趟不得再取到它们**。
   ★ 理由：既有 `withinIterationWindow` 的语义就是「窗口内已进入遍历的条目，隔离请求**记下**、窗口结束再执行」—— 句柄失效必须**沿用**这条语义，不得自成一套（§6.3）。

### 4.3 失效不是「静默丢弃」

失效句柄在**派发命中**时走「未命中句柄」路径（§5.2）⇒ **仍然留下可观察痕迹**（日志/审计），不得完全静默。

## §5 ★ 回调派发契约定案

### 5.1 listener 的角色收窄（定案）

**改后**：listener **只做纯翻译** —— 把平台事件翻译成「**本次点击落在哪个槽位 + 哪种键**」：

```
PlayerInteractEvent(RIGHT_CLICK_*)  →  机制面.dispatch(slot, Key.RIGHT)
PlayerInteractEvent(LEFT_CLICK_*)   →  机制面.dispatch(slot, Key.LEFT)
PlayerDropItemEvent                 →  机制面.dispatch(slot, Key.DROP)
EntityDamageByEntityEvent           →  （攻击面：见 §6.2 的定案，走同一机制面的攻击入口）
```

- **listener 不再读 PDC**（现 4+3 = 7 处 `getSkillId` / `getWeaponId` 调用中的 7 处，§2.4）⇒ **不再需要 `Skill.Utils` / `MainWeapon.Utils`**。
- **`event.setCancelled(true)` 的时机**：仍由 listener 负责（它才持有事件对象）——但**判据变了**：
  - 现判据 = 「物品是技能/主武器物品」（PDC 判据）；
  - **新判据 = 「该槽位有活跃句柄」**（机制面回答）。
  - ★ 行为等价性：一条活跃句柄 ⇔ 该槽位由机制面写过一次（因此一定带键）⇒ 取消面**不扩大、不缩小**。
  - ★ **例外必须写死**：`InventoryClickEvent` 那两条保护（点击热键栏物品 / 光标持有热键栏物品）**继续用 PDC 判据**，不经句柄 —— 因为「光标上的物品」**没有槽位**，句柄模型覆盖不到它。**这是本设计明确留下的唯一 PDC 直读点**。

### 5.2 未命中句柄时不得静默吞事件（定案）

| 情形 | 定案行为 |
|---|---|
| 该槽位**无活跃句柄** | listener **不取消事件**、**不派发** ⇒ 事件按原版语义继续（这不是"吞"） |
| 该槽位有活跃句柄、但**该键的回调为 `null`** | **照常取消事件**（物品受保护，不能丢）+ **不调用任何回调** ⇒ 记一行 `[hotbar] no-callback slot=<n> key=<LEFT\|RIGHT\|DROP>` **到服务端日志**（可观察） |
| 句柄**已失效**但槽位仍被点击 | 同上一行（走同一路径）；★ 该状态说明「失效了但物品还在」⇒ 属于**必须报警**的异常态，日志级别用 `WARNING` |
| 槽位越界 / 玩家无实例 | listener 早退（不取消、不派发），**不静默**：只在 `DEBUG` 级留痕（避免刷屏） |

> ★ 「不得静默吞事件」的判据 = **每一次"本可以派发却没派发"都必须留下一行可 grep 的日志**（前缀固定 `[hotbar]`）。

### 5.3 逐句柄故障隔离（定案：**机制面自带，语义照抄 `guardedCall`**）

**定案**：机制面**自带**逐句柄隔离，**不**把异常冒泡给 listener、也**不**冒泡给组件的 `guardedCall`（因为回调的调用者已经是机制面，不是容器）。

**为什么不是「沿用容器的 `guardedCall`」**：

1. **调用者不同**：`guardedCall` 是 `RoleInstance` 的私有设施，语义是「容器驱动组件时**逐监听器**隔离」；回调是**组件自己的代码**被机制面调用 ⇒ 冒泡出去就变成「一个组件的回调异常打掉整次点击派发」。
2. **隔离的归属不同**：`guardedCall` 命中时会把**该组件**送进容器的隔离队列（带"只隔离抛异常的那一个"语义）。机制面**不得**自建第二套隔离表 —— 那会与容器的隔离语义分叉。
3. ⇒ **定案 = 机制面只做「捕获 + 记日志 + 继续派发」；是否隔离该组件由既有容器设施决定**：
   - 机制面捕获回调抛出的 `RuntimeException` ⇒ 记 `[hotbar] callback threw slot=<n> key=<k> by=<componentId>` + 堆栈（`WARNING`）+ **继续**（其余句柄照常收到）；
   - **不**由机制面决定隔离；若该组件确实需要被隔离，应由**容器侧**在它自己的受保护调用里判定（与既有语义一致）。

**行为等价性检查（与「逐监听器隔离」不变量对照）**：
- 既有语义 = 「**只隔离抛异常的那一个、其余照常收到**」；
- 本定案 = 「**只有抛异常那一个回调被中断、其余句柄照常收到**」+「隔离归属留给容器」；
- ⇒ **同一句话的两种实现面**，且**不改变** `guardedCall(entry.owner(` 那一条的现算口径（§6.4）。

## §6 ★ 聚合根边界定案（含三条不变量的重算口径）

### 6.1 逐条去留表

| 成员 | 现状锚点（@HEAD `1c66326`） | 定案 | 理由 |
|---|---|---|---|
| `RoleInstance.handleCast(CastTrigger, Player)` | `RoleInstance` 的 `public boolean handleCast(`；体内二次读 PDC 取 id | ★ **删除** | 职责被完全接手：**PDC 读取**（`:354-357` 那三行）由 listener 的槽位翻译取代；**派发**由机制面的句柄回调取代（§5.1） |
| `RoleInstance.handleAttack(Player, Player)` | `RoleInstance` 的 `public boolean handleAttack(` | ★ **删除** | 同上（`getWeaponId` 那两行同理） |
| `ActiveComponent.CastTrigger` | `ActiveComponent` 的 `public enum CastTrigger`（三值 RIGHT_CLICK / LEFT_CLICK / DROP） | ★ **保留** | 它是**组件词汇**（`onCast(CastSignal)` 的入参词汇），机制面只翻译 key、不解释（§8） |
| `ActiveComponent.CastSignal` | `ActiveComponent` 的 `public record CastSignal(CastTrigger trigger)` | ★ **保留** | 同上（组件的施放入口签名不变 ⇒ 组件侧零改动） |
| `ActiveComponent.AttackSignal` | `ActiveComponent` 的 `public record AttackSignal(Player victim)` | ★ **保留** | 同上 |
| `ActiveComponent.onCast` / `MainWeapon.onAttack` | 组件侧的施放/攻击实现 | **保留**（组件的**语义**） | 机制面**不调用**它们 —— 由组件自己把它们**注册成句柄回调**（§5.1 的"回调"就是这两个方法的包装） |

### 6.2 攻击面（`EntityDamageByEntityEvent`）的定案

`handleAttack` 被删后，攻击不再经聚合根。定案：

- **机制面新增一个攻击入口**：`HotbarItemHandle.onAttackVictim(BiConsumer<Player, Player> callback)` 或等价形态（句柄的第 4 个回调位）；
- listener 的 `onAttackPlayer` 收窄为：**取攻击者主手槽位** → 机制面 `dispatchAttack(slot, victim, attacker)`；
- ★ **主手判定必须走槽位**：现形态读 `attacker.getInventory().getItemInMainHand()`（那是"主手物品"），新形态**必须**由 listëner 提供**槽位号**，机制面再核「该槽位有活跃句柄」⇒ 判定面从"物品身份"改成"槽位身份"，**语义等价**（热键栏槽位是确定的）。
- ★ **取消原版伤害**仍由 listener 做（它持事件对象），判据同为「该槽位有活跃句柄」。
