## §1 通用口径（口径三件齐 · 判据自检 · 锚串边界）

### §1.1 三种「数法」的定义（**期望值必须与测量口径同写**）

同一条 `git grep` 命令在三种数法下给出三个值 —— 本工程已为此付出过代价（台账 §12.3 记载：`cooling=` 含于 `wasCooling=`，曾被吞成 9 vs 6；`send` 含于 `sendKey`，15 vs 14）。**本件在现树的同类实测见 §1.3 实例 2。** 本件固定三种数法的名字：

| 数法 | 定义 | 本件用途 |
|---|---|---|
| **裸计数** | 固定串全量命中，**含**定义行与注释/javadoc/文案行 | 只作对照，**不作判据期望** |
| **仅代码** | 裸计数 − `^\s*(\*\|//\|/\*)` 注释/javadoc 行 | 辅助 |
| **仅调用点** | 仅**调用语句**：行内含 `符号();`（**带分号**）⇒ **结构上**排除定义行（`public void markDirty() {` 无 `;`）与 javadoc 里的 `{@link #markDirty()}`（无 `;`）；**注释行不做结构性排除** ⇒ 命中集**必须逐行判读首字符**（见下"注释行复核"） | **本件主判据口径** |

**现算实例（`markDirty`，作用域 `src/main/java`）** —— 同一个符号、三条命令、三个值：

```
$ git -C ShadowHunterRoles grep -n -F  'markDirty'        -- src/main/java   ⇒ 10 行（裸计数：2 调用 + 1 定义 + 2 注释 + 5 javadoc）
$ git -C ShadowHunterRoles grep -n -E  'markDirty\(\)'    -- src/main/java   ⇒  7 行（含定义 1 + 注释/javadoc 4）
$ git -C ShadowHunterRoles grep -n -E  '\bmarkDirty\(\);' -- src/main/java   ⇒  2 行（仅调用点）
```
> 计数口径：**输出行数**（PowerShell 下用 `(… | Measure-Object).Count` 或直接数输出行）；**禁**用"文件行数"类命令（`-split "\`r?\`n"` 会把文件尾换行多算 1 个空元素，台账 §附录二 D 实测）。
⇒ **拿 10 或 7 去比"期望 5"必然误判**。所有判据一律**三件齐**：**模式 + 定域 + 口径（行级/出现次数 · 是否含注释 · 是否含定义）**；未扣除者**显式标注为「裸计数」**。

**「注释行复核」——主口径的伴随步（本件每条计数判据都要求）**：
`\b<符号>\(\);` 形态**只能**结构性地排除"定义行 + javadoc 链接"；**若注释行里也写了 `符号();`，该行会被计入**。因此计数判据**必须**附一步逐行判读：

```
git -C ShadowHunterRoles grep -n -E '\bmarkDirty\(\);' -- src/main/java     # 主口径的命中集
# 逐行用 read 工具判读首字符：'/' 或 '*' 开头 = 注释/javadoc 行 ⇒ 从计数中扣除并在交付里逐行列名
# 辅助对照（**仅对"带限定前缀"的写法**有效，对类内裸调用会漏 ⇒ 不得单独作判据）：
git -C ShadowHunterRoles grep -n -E '^\s*[^/*[:space:]].*\bmarkDirty\(\);' -- src/main/java
```
**本树现算事实**（已复核）：`\bmarkDirty\(\);` 的 **2** 条命中、`\bupdateHotbar\(\);` 的 **8** 条命中，**全部是语句行**（无一条落在注释/javadoc 内）；两者的"注释/javadoc 提及"都在**无分号**的形态里（`//…markDirty()…`、`{@link #markDirty()}`、`{@code RoleInstance.updateHotbar()}`）⇒ 这正是 `();` 这个口径的价值。

### §1.2 判据自检与负对照（**全件共用**；防假绿灯的唯一手段）

**纪律（第 17 例陷阱的正面用法）**：**任何"判据返回 0"的结论，必须先拿一个"已知有命中"的样例会诊该判据** —— glob/目录 pathspec 的末段若没落到文件，返回 0 **不是"干净"，而是"路径没落到文件"**。

**全件共用的负对照**（现算实测，可直接复现）：

```
$ git -C ShadowHunterRoles grep -n -F 'stateOf' -- src/main/java/com/shadowHunterRolesPlugin/core/hotbar
  ⇒ 2 行（HotbarRenderer.java:8 javadoc + :43 定义）          ← 路径落到文件 ✓
$ git -C ShadowHunterRoles grep -n -F 'stateOf' -- src/main/java/com/shadowHunterRolesPlugin/core/hotba
  ⇒ 0 行 · exit 1 · 无 stderr                                 ← ⚠️ 末段不是文件：**假 0**
```
⇒ 本件**每条判据**都附一个「已知有命中」的自检样本（§4 各条内联；汇总见 §10）。

## §3 帧末 flush 与唯一消费者（C-04 / C-05 / C-06；A3）

### §3.1 flush 落点（**写死**）

| 项 | 内容 |
|---|---|
| 文件 | `src/main/java/com/shadowHunterRolesPlugin/core/RoleInstance.java` |
| 符号 | `RoleInstance#triggerUpdate()`（私有 ticker 回调；现算 `this::triggerUpdate` 全仓 **1** 处，`runRepeating(this::triggerUpdate, 1L, 1L)`） |
| 落点 | **方法尾**（现有三段之后：组件 `update()` 广播 → `scanCooldowns()` → 旧轮询分支）：`if (hotbarRenderer.isDirty()) { <写物品>; hotbarRenderer.clearDirty(); }` |
| 三段顺序（**不可交换**） | ① `isDirty()` 判脏（入口）→ ② 写物品（**唯一渲染写点**，C-07）→ ③ `clearDirty()`（清脏） |
| 为什么是"帧末" | 该回调已是「每 tick 一次、且在组件更新之后」⇒ 组件/事件路径的更新延迟 ≤ 1 tick（50 ms） |

### §3.2 `clearDirty()` 的**唯一**消费者

- **唯一消费者 = flush 尾部**（上表 ③）。
- **不得**在端口/组件/渲染器内部调用 `clearDirty()`（会吞掉本 tick 的可见更新）。
- 骨架期"无消费者"是**正确**的；接管后应变成 **1 个调用点**（判据 C-05）。

### §3.3 `isDirty()` 的消费者

- **唯一消费者 = flush 入口条件**（上表 ①）；**不得**出现第二个"读脏"点（否则两个 flush 竞态/重复写）。

### §3.4 `B-2`：冷却中的**每 tick 置脏源**（形态写死；**不得新增调用点**）

**语义要求**：任意技能**处于冷却中**（条目存在且未到期）时，每 tick 至少要 flush 一次 —— 否则技能名里的 `" x.xs"` **不再逐 tick 递减 = 可见行为变化**（blocker `B-2`；机制是 `displayName` 刷新，**不是**"每 tick 一次 `setItem`"，见 §8.1）。

**形态（冻结）**：把该条件**并入 flush 的入口条件**，例如
```
if (hotbarRenderer.isDirty() || <存在冷却中的技能>) { <写物品>; hotbarRenderer.clearDirty(); }
```
谓词口径（等价于今天的 `shouldUpdateItemMeta()`）：**只数技能**（`skillCooldowns`）且"未到期"者为真；主武器冷却中**不需要**每 tick 刷新（无秒数文本 ⇒ 外观恒定，与今天一致）。

**红线 R-4（本件新增口径红线）**：该谓词**不得**通过**新增第 6 个 `markDirty();` 直呼**实现 —— 那会与 C-02 的期望 5 冲突。若 `t2` 认为必须新增调用点 ⇒ **停手上报**（属"改判据"，须重新冻结）。

## §9 制品代次纪律（C-16；A10）

1. **本批只产生一代** jar（`t2` 的构建 ⇒ 一代）；该代 jar 必须归档 + 登记：
   ```
   Copy-Item build\libs\<本代>.jar → debug-logs/回滚快照/jars/…-<mtime>-<SHA256 前 8 位>.jar
   # MANIFEST.txt 追加【一行一值】：bytes / mtime / SHA256 / 覆盖它的运行证据 / 与前代关系
   ```
2. **`t4`/`t5` 不得重建该代 jar**：判据 = 该 jar 的 **bytes + mtime + SHA256 逐字一致**，三个时点现算：`t4` 开工前 / `t5` 开工前 / `t5` 结卡前。
   ```
   Get-Item -LiteralPath <归档 jar> | Select-Object FullName,Length,LastWriteTimeUtc
   Get-FileHash -LiteralPath <归档 jar> -Algorithm SHA256
   ```
3. **重建等价性只能在副本上验**：把 jar 复制到 `build/` 或临时目录，对**副本**做「删 + 重建 + 比对」——**不得触碰工作树/归档 jar 的 mtime**（否则 F1 链反转 ⇒ **自相矛盾，比没有证据更危险**）。
4. **若不符怎么办**：出现「删 jar + 重建」或 mtime 前移 ⇒ 该代**证据链失效** ⇒ 该代运行证据作废，**重新起服取证**（**不得事后补写**冒充当时物证）。
5. **只认自己那一代**：`t5` 的外观证据只认领**它自己那一代** jar；不得用新证据冒充旧代覆盖。
