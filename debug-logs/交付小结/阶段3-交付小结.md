## 2. 验收判据逐条

### 2.1 I-5（api 包不 import 内部具体类）

**实测命令**（指南 §3.2 的口径）与**原样输出**：


- **实现类归零**：`roleComponent` 命中 **0**、`registry` 命中 **0**、`manager` 命中 **0**；`api` 包现只有 `RoleAPI.java` + `RoleInfo.java` 两个文件（`RoleAPIImpl` 已移出）。
- **剩余 2 行都是 `core.Faction`** —— 这是**公开枚举**，出现在 `RoleAPI` **既有**签名（`getFaction/setFaction/areHostile`，§6.4 规定"只增不改"）与卡面指定新增的 `RoleInfo.faction` 上。**要清零必须二选一：改动既有签名（被 §6.4 禁止）或把 `core.Faction` 迁出（需覆盖 `core/`+`roleComponent/` 的卡）** → 见 §5 **偏差申报 D-1**。
- 结论：**"api 不持有任何内部实现"这一目标达成**（唯一剩余项是公开枚举，且是**被冻结的公共词汇表**）；严格 grep 不为空的部分已如实列出，不谎称"空"。

### 2.2 RoleRegistry 纯容器

- **无 `static{}` 块**（原 `static { registerHunterMeiqihezi(); registerShadowRed(); }` 已删除）
- **无静态 Map**（原 `private static final Map<String, Role> ROLES` 已删除；现为实例字段 `private final Map<String, Role> roles`）
- 容器方法：`register(Role)` / `get(String)` / `contains(String)` / `ids()` / `all()` / `size()` / `isEmpty()`
- `contains` 是"容器侧 hasRole"：**Java 不允许同一签名同时存在静态与实例方法**，而静态 `hasRole(String)` 被**本卡 out of scope** 的 `command/RoleCommand.java`、`manager/RoleManager.java` 调用，故实例侧命名为 `contains`（语义相同），静态侧保留为**兼容桥**。

### 2.3 RoleAPI 只增

**既有方法逐条比对**：以 `t13-before` 快照的 `api/RoleAPI.java` 与现行文件做方法签名集合对比 → **删除 0 / 修改 0**（仅新增）：

`RoleInfo` = `record(String id, Component displayName, List<Component> description, Material icon, Faction faction)`。
