# 架构与组件模型

这份文档写给**准备改这个插件的开发者**。读完它你能回答：一个角色从"模板"到"玩家身上的实例"经过哪些对象；一个技能被触发时经过哪条链路；组件能碰什么、不能碰什么；热键栏是谁在什么时候写的；清除角色时框架会回收哪些东西。

> 只用「文件 + 符号」定位代码，不写行号。
> 组件层的写法（怎么写一个新组件）见 `开发指南-新增角色或组件.md`；玩家可见的数值与玩法见 `角色与技能.md`。

## 总览

```
装配期（插件启用，一次）
  ShadowHunterRolesPlugin.onEnable
    ├─ KeyFactory.Registry.install(keys)              名字空间唯一来源
    ├─ new RolesContext(plugin, logger, scheduler, keys, factions)
    ├─ new RoleRegistry()                            角色模板容器（纯容器）
    ├─ new RoleLoader(getLogger()).loadInto(registry) 逐条装配角色模板
    ├─ new RoleManager(rolesContext, roleRegistry)
    ├─ getCommand("role").setExecutor(new RoleCommand(...))
    ├─ registerEvents(5 个 listener)
    └─ ServicesManager.register(RoleAPI.class, RoleAPIImpl)

运行期
  角色模板层   Role（数据 + 组件工厂 + 槽位表）        core/Role
       ▼       RoleRegistry（纯容器，无静态状态）      registry/RoleRegistry
       ▼       RoleLoader（显式装配，按角色隔离失败）  registry/RoleLoader

  实例层       RoleManager（UUID → RoleInstance）     manager/RoleManager
       ▼       RoleInstance（聚合根）
       │         ├─ ComponentRegistry（组件集合 + 每组件资源表 + 查找）
       │         ├─ HotbarRenderer（唯一渲染者）
       │         ├─ BuffManager（控制效果计时 + 闸门）
       │         └─ 10 个端口适配器 → ComponentServices
       ▼
  组件层       RoleComponent（基类：svc + 5 个钩子 + getComponent）
                 │           + 按需实现的能力接口（能进热键栏 / 能被施放 / 能参与攻击 / …）
                 ├─ PassiveSkill   → 被动组件   （可选便利基类）
                 └─ ActiveComponent ─┬─ Skill      → 技能组件   （可选便利基类）
                                     └─ MainWeapon → 主武器组件（可选便利基类）

  装配入口     Role.Builder.addComponent（两个重载：带槽位 / 不带槽位）
```

| 层 | 关键类型 | 职责 |
|---|---|---|
| 模板 | `core/Role` | 存 id / 显示名 / 描述 / `maxHP` / `baseATK` / `maxEnergy` / `maxSanTE` / 阵营 / 图标 / 组件工厂 / 槽位表；`createInstance` 造实例 |
| 容器 | `registry/RoleRegistry` | 纯容器：实例字段 `LinkedHashMap`，只有 `register` / `get` / `contains` / `ids` / `all` / `size` / `isEmpty`，没有静态块、没有静态 Map |
| 装配 | `registry/RoleLoader` | 两条 `Definition`；逐条 `build()` + `register()`；单个角色失败只跳过它并记 `SEVERE` |
| 持有 | `manager/RoleManager` | `Map<UUID, RoleInstance>`；`selectRole` / `clearRole` / `hasRole` / `getRoleInstance` / `areHostile` / `clearAllPlayersRole` |
| 聚合根 | `core/RoleInstance` | 真值持有（能量 / SanTE / 生命 / 阵营 / 冷却 / 控制效果）+ 组件集合 + 每刻广播 + 渲染置脏与帧末重绘 + 资源回收 |
| 组件基类 | `roleComponent/RoleComponent` | `svc` 字段 + 5 个 default 钩子 + `getComponent(Class)` |
| 能力接口 | `core/hotbar/HotbarPresentable`、`core/hotbar/HotbarItem`、`core/hotbar/CooldownBearing`、`core/hotbar/EnergyCosting`、`core/dispatch/HotbarActionable`、`core/dispatch/CombatHook` | 编译期能力：能进热键栏（表现规格） / 有冷却 / 耗能量 / 能被施放 / 能参与攻击；**按需实现，不必靠继承获得** |
| 表现规格 | `core/hotbar/HotbarSpec` | 一个组件的七个表现字段（id / 显示名 / 描述 / 图标 / 冷却 / 能量消耗 / 种类）收成一个不可变对象，由 `HotbarSpec.of(...)` 构造 |

## `ComponentServices`：组件的唯一平台入口

`core/ports/ComponentServices` 是一个 record，**恰好 10 个成员**：

```java
record ComponentServices(Self self, EnergyPort energy, SanTEPort sante, VitalsPort vitals,
                         CooldownPort cooldowns, BuffPort buffs, FactionPort factions,
                         DamagePort damage, TimerPort timers, ComponentLookup components)
```

它由容器在**构造组件的同时**注入（`RoleInstance.createServices` 构造服务集 → `Role.createComponent` 经 `ComponentFactory.create(id, services)` 交给组件构造函数），字段是 `final`，不存在"先创建、后注入"的中间态。

| # | 成员 | 方法白名单 | 适配器 | 语义要点 |
|---|---|---|---|---|
| 1 | `self` | `player()`、`id()` | `core/SelfImpl` | 本组件依附的玩家，**每次现取、不缓存** |
| 2 | `energy` | `current()`、`tryConsume(int)`、`gain(int)` | `core/EnergyPortImpl` | 能量真值；`tryConsume` 把判断与扣减合成一步，`amount <= 0` 直接成功 |
| 3 | `sante` | `gain(int)`、`decrease(int)`、`set(int)`、`current()`、`max()` | `core/SanTEPortImpl` | SanTE 真值，所有写入都经这里 |
| 4 | `vitals` | `heal(double)` | `core/VitalsPortImpl` | 生命；不会超过当前最大生命 |
| 5 | `cooldowns` | `isReady()`、`remainingTicks()`、`start(int)`、`end()` | `core/CooldownPortImpl` | 冷却；**构造期已绑定本组件 id 与种类**，组件不再传 id |
| 6 | `buffs` | `canCastSkill()`、`canUseMainWeapon()`、`add(BuffType,int)`、`has(BuffType)`、`remainingTicks(BuffType)`，以及两个重载 `applyPotionEffect(...)` | `core/BuffPortImpl` | 闸门 + 本系统药水的**唯一施加入口**；两个重载分别对应默认标志与自定义 `ambient` / `particles` |
| 7 | `factions` | `isHostile(Player)`、`faction()`、`hasEnemyInRange(double)` | `core/FactionPortImpl` | 阵营与敌对判定；未选角色的玩家算敌人 |
| 8 | `damage` | `trueDamage(...)` 两个重载、`physicalDamage(...)` 两个重载 | `core/DamagePortImpl` | 伤害原语，带击退的重载多一个参数；**伤害来源允许为 `null`** |
| 9 | `timers` | `run(Runnable)`、`runLater(long,Runnable)`、`runRepeating(long,long,Runnable)`、`track(Task)` | `core/TimerPortImpl` | 任务**创建即登记**进本组件的资源表，`stop()` 返回后由框架兜底取消 |
| 10 | `components` | `get(Class<T>)` | `core/ComponentLookupImpl` | 组件查找；未注册返回 `null`，注册表冻结前调用抛 `IllegalStateException` |

**纪律**：

- **一个方法都不许多用**：要加端口方法，先改 `ComponentServices` 与对应接口（这是一个需要明确决策的改动，不要顺手加）。
- 适配器一律包级私有，只持有 `RoleInstance` 反向引用；**不允许 `RoleInstance` 直接实现端口接口**，否则组件可以用 `(RoleInstance) svc.energy()` 拿回聚合根。
- 组件不能读角色模板数据（`maxHP` / `baseATK` 之类）—— 端口里没有这条通道。

## 组件模型与生命周期

### 基类 `RoleComponent`

`roleComponent/RoleComponent` 里只允许出现三样东西：`svc` 字段、钩子方法、`getComponent`。任何"顺手加个 helper"都越界 —— 那属于端口或组件私有方法的职责。

**5 个 default 钩子，由容器无条件广播给注册表里的全部组件**：

| 钩子 | 语义 |
|---|---|
| `awake()` | 装配阶段：解析跨组件依赖并缓存引用。**幂等**，不得改动任何玩家可见状态 |
| `start()` | 开始生效：初始化数据、发放装备、登记定时器 |
| `stop()` | 停止生效：**与 `start()` 严格对称**；返回后框架还会兜底回收本组件登记的资源 |
| `update()` | 每刻（20 Hz）。禁止阻塞，**禁止直接写热键栏**（渲染是框架的职责） |
| `onSanTEChange(int pre, int now)` | **事件钩子**，不是每刻广播：只在 SanTE 真变化时通知（`pre == now` 不通知） |

### 三个可选的便利基类

新组件**不必**继承它们：只要 `extends RoleComponent`、再按需要实现能力接口就能登记（`Role.Builder.addComponent` 的工厂形参是 `ComponentFactory<? extends RoleComponent>`）。这三个类只是"照抄起来最短"的现成组合，它们**没有删除**，现有组件全部走这条便利路径。

| 类型 | 形态 | 结果 |
|---|---|---|
| `PassiveSkill` | `extends RoleComponent`，只保留显示名与描述 | 被动**不实现** `HotbarItem` / `HotbarActionable` ⇒ "能不能被施放"是编译期事实 |
| `ActiveComponent` | `extends RoleComponent implements HotbarItem, HotbarActionable, HotbarPresentable`：把构造参数装进一个 `HotbarSpec` 并实现 `spec()` | 提供默认 `onCast`（不做事也不进冷却）与 `onCooldownEnd`（空实现） |
| `Skill` / `MainWeapon` | 分别 `extends ActiveComponent`；`Skill` 的构造函数参数顺序是 `显示名, 描述, 冷却, 能量消耗, 图标`，`MainWeapon` 是 `显示名, 描述, 图标, 冷却` 且**能量消耗恒传 0** | 主武器因此永远不会进入"能量不足"状态 |

### 能力接口与「一个实现点」

`HotbarPresentable` 把"能进热键栏"收敛成**一个实现点**：

```java
public interface HotbarPresentable extends HotbarItem, CooldownBearing, EnergyCosting {

    /** 唯一实现点：表现规格。 */
    HotbarSpec spec();

    default String getId() { return spec().getId(); }      // 其余访问器全部是 default
}
```

- 组件只写 `spec()`（返回 `HotbarSpec.of(id, 显示名, 描述, 图标, 冷却, 能量消耗, 种类)` 建好的对象）；`getId` / `getDisplayName` / `getDescription` / `getIcon` / `getCooldownTicks` / `getEnergyCost` / `getKind` 七个访问器由接口的 `default` 方法代劳，组件**不写任何委托**。
- `CooldownBearing` / `EnergyCosting` 把"有冷却"与"耗能量"抽成可以单独实现的能力；`HotbarPresentable` 继承这两个接口，所以只写 `spec()` 的组件天然满足三者。
- `HotbarItem` 保留为**渲染器读写面**；`HotbarPresentable.asHotbarItem()` 直接返回规格视图，容器侧由 `RoleInstance.hotbarItemOf(String)` 优先走它。
- **能力可以自由组合**：例如"能被按键施放、又能参与攻击结算"的组件，今天可以只写 `extends RoleComponent implements HotbarActionable, CombatHook`（不继承 `Skill` / `MainWeapon`）。可编译的完整骨架见 `开发指南-新增角色或组件.md`。
- `HotbarActionable` / `CombatHook` 声明的是"这个组件具备哪种形态"；实际派发另有收窄：**施放入口** `RoleInstance.handleCast` 今天要求组件是主动组件（`ActiveComponent`），**攻击入口** `RoleInstance.handleAttack` 要求实现 `CombatHook`。

### 权威 kind 在注册处

`ItemKind` 有三个值：`SKILL`（技能）、`MAIN_WEAPON`（主武器）、`PASSIVE`（被动）。**权威 kind 由注册处给出** —— `Role.Builder.addComponent(..., kind)` 把它存进角色模板的装配条目，框架侧的行为分支（冷却表 / 能力闸门 / 持久化键 / 文案表）一律读 `Role.componentKindOf(String)`。

为什么不从组件里读它：**服务集先于组件构造**，而服务集里就带着 kind —— `RoleInstance.createServices(String componentId, ItemKind kind)` 在组件被创建之前构造冷却端口，`CooldownPortImpl(RoleInstance owner, String componentId, ItemKind kind)` 在构造期绑定 kind；而 `ComponentFactory.create(String id, ComponentServices services)` **只给 id 与服务集、不给 kind** ⇒ 组件在构造期无从得知权威 kind。所以组件 `spec()` 里的 kind 只作表现用途（`HotbarPresentable.getKind()` 读出的也只是 `spec()` 的那个值）。

被动（`PASSIVE`）的两处差异：不占热键栏（不进槽位表，渲染器另有显式跳过分支）；冷却端口对它是**无声语义**（恒就绪 / 剩余 0 / 不写任何表 / `end()` 恒 `false`，见 `core/CooldownPortImpl`）。

### 启停机制（只有一套）

组件启停 = **容器对全部已注册组件无条件广播** `awake()` / `start()` / `stop()` / `update()`。没有"按类型分流"，也没有任何"是否已迁到新写法"的标记。

**广播顺序 = 注册序**：`Role.Builder` 里 `addComponent` 的调用顺序（角色模板的组件表 `Role.getComponents()` 是有序表），容器只遍历它一次。**不再**按"技能 → 被动 → 主武器"分组，所以同一刻里两个组件都写同一个数值时，先后由注册顺序决定。

广播与回收的固定顺序（`core/RoleInstance`）：

| 顺序 | 动作 | 语义 |
|---|---|---|
| 1 | `component.awake()` | 解析跨组件依赖（幂等） |
| 2 | `component.start()` | 开始生效 |
| 3 | `component.stop()` | 停止生效，**在框架兜底回收之前** |
| 4 | `componentRegistry.cancelAllAndClear()` | 框架兜底取消各组件资源表里的任务 |

组件即使在 `stop()` 里自己取消了任务，第 4 步仍会清空它的资源表 —— 重复取消是幂等的，不会双触发同一段逻辑。

### 一个角色实例的装配顺序

`RoleInstance` 构造函数依次做：初始化能量与 SanTE 为满值 → 按**注册序**逐个创建全部组件（`Role.createComponent` 是唯一的组件创建点，它经 `ComponentFactory.create(id, services)` 在构造期注入服务集；权威 kind 随条目从注册处取出）→ **冻结组件注册表**（此后 `getComponent` 才合法）→ 建 `BuffManager` → 挂最大生命修饰符并回满血 → 广播 `awake()` → 广播 `start()` → 启动每刻（1 刻周期）的 ticker → **同步重绘一次热键栏**（保证选角色的瞬间图标就位）。

## 施放管道

### 触发来源

监听器把原版事件翻译成"施放 / 攻击"，再交给聚合根：

| 玩家动作 | 监听器 | 聚合根入口 | 组件收到的回调 |
|---|---|---|---|
| 手持技能物品右键 | `listener/SkillListener.onPlayerRightClickSkillItem` | `RoleInstance.castSkillRightClick` | `onCast`（`CastTrigger.RIGHT_CLICK`） |
| 手持技能物品左键 | `SkillListener.onPlayerLeftClickSkillItem` | `castSkillLeftClick` | `onCast`（`LEFT_CLICK`） |
| 手持技能物品按 `Q` | `SkillListener.onPlayerQDropSkillItem` | `castSkillQDrop` | `onCast`（`DROP`） |
| 手持主武器左键 / 右键 / `Q` | `listener/MainWeaponListener` | `castMainWeaponLeftClick` / `...RightClick` / `...QDrop` | `onCast`（对应的触发来源） |
| 手持主武器攻击玩家 | `MainWeaponListener.onAttackPlayer` | `RoleInstance.handleAttack` | `onAttack(AttackSignal)` |

这几个入口最终都汇到 `RoleInstance.runComponentPipeline`，它是**纯委派**（没有任何开关或标记）：按手持物品里的 id 找到组件，是主动组件就调 `onCast`，能参与攻击就调 `onAttack`。信号对象只带这一次的数据：`CastSignal(trigger)`、`AttackSignal(victim)`；施动者永远是 `svc().self().player()`。

### 结果语言 `CastResult`

`core/dispatch/CastResult`：

| 值 | 语义 |
|---|---|
| `SUCCEED` | 施放成功（**只表示成功**，不隐含任何框架动作） |
| `NO_COOLDOWN` | 组件自己处理过了（含"这次什么都不做"），框架不呈现任何反馈 |
| `REJECTED_DISABLED` | 被沉默 / 眩晕禁用 |
| `REJECTED_NO_ENERGY` | 能量不足 |

### 冷却由组件自己启动

框架**不**代启动冷却：组件在施放成功处显式调用 `svc().cooldowns().start(getCooldownTicks())`。声明值（构造时传入的冷却）仍是唯一真值来源，组件通常直接把它传进去。

- `start(int)` = **重启语义**：按本次调用时刻重算到期，覆盖旧值；旧段未走完则先清条目并回调 `RESTARTED`。
- `end()` = **真实语义**：在冷却中 ⇒ 清条目、回调 `ENDED_BY_COMPONENT`、刷新可见状态、返回 `true`；不在冷却中 ⇒ 返回 `false`、无副作用。
- 到期：`RoleInstance.scanCooldowns` 每刻扫描，移除条目并回调 `EXPIRED`。
- 组件的收尾钩子：`ActiveComponent.onCooldownEnd(CooldownEndReason)`，枚举值 `EXPIRED` / `ENDED_BY_COMPONENT` / `RESTARTED`。回调在条目移除之后派发，所以回调里再 `end()` 只会得到 `false`，不会递归重入。

## 渲染契约

**唯一渲染者 = `core/hotbar/HotbarRenderer`**：全插件只有 `HotbarRenderer.render()` 里那一次槽位写入会创建物品。`RoleInstance` 只提供查表与状态输入（`hotbarItemOf`、`isSkillReady`、`getCurrentEnergy`、`getBuffManager` 等）。

- 能进热键栏的组件实现 `HotbarPresentable`（它继承 `HotbarItem` / `CooldownBearing` / `EnergyCosting`）：组件只写**一个实现点** `spec()`，返回一个 `HotbarSpec`；`getId` / `getDisplayName` / `getDescription` / `getIcon` / `getCooldownTicks` / `getEnergyCost` / `getKind` 七个无参 getter 由接口的 `default` 方法委托给它，组件不必手写。容器用 `RoleInstance.hotbarItemOf(String)` 取这个读写面（优先走 `asHotbarItem()`），`HotbarItem` 本身保留。
- `HotbarRenderer.render()` 遍历角色模板的槽位表，未注册的 id 直接跳过；`kind` 一律取注册处的权威值（`Role.componentKindOf(String)`），被动（`PASSIVE`）即使落在槽位表里也会被显式跳过。
- 状态判定：`HotbarRenderer.stateOf(ready, canCast, energy, energyCost)`，顺序固定为 **冷却 → 被禁用 → 能量不足 → 就绪**。主武器 `energyCost` 恒为 0（能量也不会为负）⇒ 永不进入"能量不足"。
- 材质与文案：就绪用组件声明的图标、绿色加粗；被禁用 `BARRIER`、红色加粗 + ` DISABLED`；冷却中与能量不足都用 `STRUCTURE_VOID`，灰色加粗；**技能**冷却名追加 ` x.xs` 秒数（秒数只在这一处格式化），**主武器不追加**。
- 物品都带持久化标记：技能是 `Skill.Utils.SKILL_KEY`（`skill_id`），主武器是 `MainWeapon.Utils.MAIN_WEAPON_KEY`（`main_weapon_id`），值是组件 id。监听器据此识别物品并拦截丢弃 / 容器点击。

### 置脏与帧末重绘

刷新不是"每刻轮询比较"，而是**置脏 + 每刻末尾统一重绘**：

- **置脏来源**（框架内部调用 `HotbarRenderer.markDirty()`）：施放（`RoleInstance.handleCast`）、攻击（`handleAttack`）、能量变化（`setCurrentEnergy`）、启动冷却（`CooldownPortImpl.start`）、控制效果移除（`manager/BuffManager.removeBuff`）、冷却到期扫描（`RoleInstance.scanCooldowns`）、显式结束冷却（`RoleInstance.endCooldown`）。其中"程序化"的三条路径（冷却到期、预约刷新、显式结束）共用一个方法引用 `hotbarRenderer::markDirty`（`RoleInstance` 里的 `markHotbarDirty`）。
- **预约刷新**：启动冷却时同时预约"剩余时长后再置脏一次"（`runLater(markHotbarDirty, remaining)`），保证冷却结束时图标立刻恢复。
- **帧末重绘**：`RoleInstance.triggerUpdate` 的顺序是 —— 广播组件 `update()` → `scanCooldowns()` → **判脏**（`isDirty()`）→ `render()` → `clearDirty()`。三段顺序不可交换。
- **入口条件**：`isDirty() || hasCoolingSkill()`。`hasCoolingSkill()` 只数技能，作用是让"冷却中每刻至少刷一次"，技能名上的秒数才会逐刻递减；空闲刻一次物品写入都不会发生。
- `clearDirty()` 的**唯一消费者是帧末重绘**：组件、端口、渲染器内部都不得调用，否则会吞掉本次可见更新。
- 组件侧没有任何置脏通道（也没有 `HotbarPort`）：组件只声明图标 / 显示名 / 描述，状态变化由框架在五个触点自动置脏。

## 资源回收与清除角色

`core/dispatch/ComponentRegistry` 负责组件集合、每组件资源表（组件 → 任务列表）与查找：

- `register` 只允许在 `freeze()` 之前；`get(Class)` / `getById(String)` 在冻结前调用会抛 `IllegalStateException`，把"过早查询"变成响亮的错误；
- `track(component, task)` 登记任务；`cancelAll(component)` / `cancelAllAndClear()` 在 `stop()` 返回后兜底取消。

`RoleInstance.clear()` 的顺序：广播 `stop()` → 兜底取消全部登记任务 → 取消每刻 ticker → 清空热键栏（0–8 号位中带技能 / 主武器标记的物品）→ 移除最大生命修饰符 → **只移除记账过的药水效果** → 清空控制效果 → 清空两张冷却表。

触发清除的入口：`/role clear`、死亡、掉线、换角色（`RoleManager.selectRole` 先清旧角色）、插件卸载（`RoleManager.clearAllPlayersRole`）。

## 平台层与对外接口

`platform/` 是领域层与组件层**唯一**接触服务端 API 的地方（取代插件主类单例）：

| 类型 | 形态 | 职责 |
|---|---|---|
| `platform/RolesContext` | record `(Plugin plugin, Logger logger, Scheduler scheduler, KeyFactory keys, FactionLookup factions)` | 平台能力五元组；由主类在 `onEnable` 构造并注入 `RoleManager` → `RoleInstance` |
| `platform/Scheduler` | `run` / `runLater` / `runRepeating` | 调度端口 |
| `platform/BukkitSchedulerAdapter` | 唯一实现 | 包装 Paper 提供的 `GlobalRegionScheduler` 的 `run` / `runDelayed` / `runAtFixedRate`；`initialDelay <= 0` 归一为 1 |
| `platform/Task` | `cancel()` / `isCancelled()` | 调度句柄（不同调度 API 的返回类型不统一，这里统一包装） |
| `platform/KeyFactory` | 接口 + `Registry` 静态桥 | `NamespacedKey` 的唯一来源；四个公开常量（技能键、主武器键、最后伤害者键、眩晕减速修饰符键）需要在类初始化期取值，所以保留了这层静态桥；未安装时抛 `IllegalStateException` |
| `platform/FactionLookup` | 接口 + 主类里的匿名实现 | 按玩家查阵营；未选角色的玩家 → `UNKNOWN` |

**服务端基线是 Paper**：调度统一走 `GlobalRegionScheduler`，本插件不做 Folia 适配，也不预置 Folia 分支。

**对外接口**：`api/RoleAPI` 在启用时注册进 Bukkit 服务表；实现类是 `internal/api/RoleAPIImpl`。它覆盖四类能力：

- 角色：`isValidRoleId` / `setPlayerRole` / `clearPlayerRole` / `getPlayerRoleId` / `hasRole` / `getRoleDisplayName` / `getRoleDescription` / `getRoleIcon` / `getAllRoleIds` / `getRoles`；
- 玩家数值：能量、SanTE、生命的读写与查询（`getPlayerEnergy` / `setPlayerEnergy` / `increaseEnergy` / `decreaseEnergy` / SanTE 与生命对应方法）；
- 冷却：`isSkillReady` / `getSkillCooldownTick`；
- 阵营与伤害来源：`getFaction` / `setFaction` / `resetFaction` / `areHostile` / `getLastDamagerUuid`。

`api/RoleInfo` 是只读快照 record：`(String id, Component displayName, List<Component> description, Material icon, Faction faction)`。

> 改 `RoleAPI` 的既有方法签名会破坏下游插件（`SHDFGamePlugin` 通过 `ServicesManager` 使用它）。原则是**只增不改**。

## 扩展点与硬性规则

### 扩展点

| 想做的事 | 落点 |
|---|---|
| 加技能 / 被动 / 主武器 | 新组件类（`roleComponent/<角色包>/...`）：`extends RoleComponent` 并按需实现能力接口（也可以直接用三个便利基类），再在 `Role.Builder` 里用 `addComponent` 登记；具体步骤见开发指南 |
| 加角色 | `registry/RoleLoader` 里加一条 `Definition` 与一个 `Builder` 方法 |
| 改数值 | 组件构造函数里的声明值、`RoleLoader` 里的角色数值 |
| 给下游插件用 | `api/RoleAPI`（只增不改） |
| 加命令 | `command/` 包加一个 `SubCommand` 实现并在对应分发器里注册 |

### 硬性规则

1. **`ComponentServices` 恰好 10 个成员**，加成员要显式决策；
2. **组件 id 跨类型唯一**：技能 / 被动 / 主武器共用一个命名空间，重复注册会抛异常；
3. **槽位只能是 `0..8` 且不能冲突**，非法槽位直接抛异常；不带槽位的重载（`addComponent(id, 工厂, kind)`）表示不占热键栏；
4. **角色数值必须合法**：`maxHP > 0`，`baseATK` / `maxEnergy` / `maxSanTE` ≥ 0，角色 id 非空；
5. **单个角色装配失败只影响它自己**：记 `SEVERE`、跳过该角色，其余角色照常注册；
6. **组件不许写热键栏**：不造 `ItemStack`、不请求刷新；
7. **组件不许拿插件主类单例**，也不许直接调服务端调度器，一律走 `svc()` 端口；
8. **有 `start` 必有对称的 `stop`**，`stop` 里把缓存的引用置空；
9. **玩家对象不放进长生命周期字段或长任务闭包**：存 `UUID`，或每次 `svc().self().player()` 现取；
10. **数值提成类顶部命名常量**（几何 / 特效参数除外）；
11. **不要"顺手改正" id 里的拼写**：`meiqihezi_equippments_passive`、`red_equippments_passive`、`autoRecoverSanTEPassive` 都是索引键；
12. **门面命名沿用 JavaBean 风格**：`getId()` / `getDisplayName()`，不要引入 record 风格访问器；
13. **装配只有一个入口**：`Role.Builder.addComponent`（带槽位 / 不带槽位两个重载）；`addSkill` / `addMainWeapon` / `addPassive` 是已标 `@Deprecated` 的别名，仍可用，且与新入口走**同一条内部路径**（`Role.Builder.addComponentInternal`）—— 校验、id 去重、槽位写入都只有一处实现。
