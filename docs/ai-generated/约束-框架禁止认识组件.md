# 约束 · 框架禁止认识任何组件

> **强制要求（用户立规）**：**框架禁止知道任何组件的存在。**
> 本件是上位规则 —— 凡与之冲突的既有说法（含 `组件模型.md` 的分层判据、各处 javadoc 的「框架级组件」表述）**以本件为准**。

---

## §1 规则正文

### §1.1 框架层 = 哪些路径

| 归入**框架层**（受本规则约束） | 说明 |
|---|---|
| `core/**` | 聚合根与实例容器（`Role` · `RoleInstance` · `ports/**`）|
| `roleComponent/RoleComponent.java` | 组件基类（框架侧的组件**通用面**）|
| `roleComponent/ActiveComponent.java` | 主动组件基类（框架侧的**通用**主动面）|
| `roleComponent/base/**` | 三个家族基类（`Skill` / `MainWeapon` / `PassiveSkill`）|

### §1.2 禁止形态（逐条）

框架层**一律不得**以任何形式指名任何**具体组件**：

| # | 禁止 | 例（本仓曾出现）|
|---|---|---|
| ① | **不得 `import` 具体组件** | `import …roleComponent.builtin.HotbarRenderComponent;` |
| ② | **不得写具体组件的 `.class`** | `EnergyComponent.class` · `requires(VitalsComponent.class)` |
| ③ | **不得引用具体组件的 `ID_*` 常量** | `ServiceComponents.ID_VITALS` |
| ④ | **不得实现具体组件的嵌套接口** | `implements EnergyComponent.EnergyCosting` |
| ⑤ | **不得调用具体组件的静态方法** | `ServiceComponents.vitalsApplyHealthModifier(...)` |
| ⑥ | **不得由框架构造具体组件** | `ServiceComponents.build(...)` 写在 `RoleInstance` 里 |
| ⑦ | 连**注释／`{@link}`／举例**也不得指名 | `{@link HotbarRenderComponent#buildItemOf}` |

### §1.3 允许形态（框架**只**能这样取用）

| # | 允许 | 说明 |
|---|---|---|
| ① | **id 字符串** | 框架只持有 `"vitals"` 这类**数据**；常量归属见 §2 |
| ② | **组件通用面** | `RoleComponent` 及其**组件侧**声明的薄接口 |
| ③ | **按 id 取回通用面** | `componentRegistry.getById(id)` / 容器 `resolve(id)` |
| ④ | **外部注入的数据** | 例：`Role.Builder#providedTypes(Set<Class<? extends RoleComponent>>)` 只吃**数据**、不认类型名 |

★ **接口所有权的硬规定**：框架需要的新接口**必须落在组件侧**（`roleComponent/` 下），**不得**落 `core/`。
（先例：`roleComponent/OperationProvider.java` 的「**不进 core** 的公共能力区」护栏。）

---

## §2 装配权必须外置（根治点）

**根因**：容器 `RoleInstance` 曾经**自己构造** 6 个服务组件（`ServiceComponents.build(...)`）——
它既是「装配方」又是「使用者」⇒ **必然**要认识它们。**在这个形状下，任何「把清单搬个地方」都是补丁。**

**根治**：

```
装配层（在 core 与 builtin 之上，与 registry/RoleLoader 同层）
   ├─ 构造 6 个服务组件（含顺序保证：渲染组件必须先于任何会置脏者）
   ├─ 收集「已提供类型」清单（构造了哪 6 件 ⇒ 清单就是哪 6 类）
   └─ 作为【数据】注入 ↓
容器 RoleInstance（框架层）
   ├─ registerServiceComponents(注入进来的 List<RoleComponent>)
   └─ 此后只按 id 字符串取用通用面 ✓
```

★ **副作用（正向）**：`FRAMEWORK_PROVIDED_TYPES` 由**装配动作派生**，不再另行声明 —— 消掉一处「框架写死组件类清单」。

## §3 达标判据（可执行）

```
框架层四处，模式（大小写敏感、含 import 与注释）：
  ① 具体组件族：builtin\.|HotbarRenderComponent|EnergyComponent|SanTEComponent|
                VitalsComponent|BuffComponent|TimerComponent|ServiceComponents
  ② 阵营例外：FactionComponent

判据 = 命中数 = 白名单内的例外数，其余必须 0。
```

**白名单（仅此一处组件，见 §4 的裁决记录）**

| 允许 | 位置 | 允许的形态 |
|---|---|---|
| `FactionComponent` | `core/RoleInstance.java` | `import` · `getById(FactionComponent.ID)` · `instanceof FactionComponent` · 承载它们的 javadoc/注释 |
| `FactionComponent` | `core/**` 其余件（`Role.java` · `RoleInfoImpl.java` · `core/ports/RoleInfoPort.java`） | ★ **仅"说明性提及"**：注释 / `{@code}` 里指向新落点；**不得** import、不得 `.class`、不得引用 `ID` 常量、不得构造或调用 |

★ **例外范围之外，§1.2 的七条禁止形态逐条适用**（含"连注释也不得指名"）：
`roleComponent/ActiveComponent.java` · `roleComponent/RoleComponent.java` · `roleComponent/base/**`
对**任何**具体组件（含 `FactionComponent`）都必须 **0 命中**。

| 位置 | 基线（2026 记录）| ① 具体组件族（现算）| ② 阵营例外（现算）|
|---|---|---|---|
| `core/RoleInstance.java` | **29** | **1**（= 例外那一行 `import`）| **10**（例外全部落在这里）|
| `core/**` 其余件 | — | **3**（`Role.java` 的三行注释，**既存**）| **7**（`Role` 4 + `RoleInfoImpl` 1 + `RoleInfoPort` 2，全是说明性提及）|
| `roleComponent/RoleComponent.java` | **5** | **6**（**既存**：javadoc 举例）| **0** |
| `roleComponent/ActiveComponent.java` | **11** | **7**（**既存**：栏位登记仍指名渲染组件）| **0** |
| `roleComponent/base/{Skill,MainWeapon,PassiveSkill}.java` | **4 / 4 / 2** | **4 / 4 / 1**（**既存**）| **0 / 0 / 0** |

★ **判据（改判）**：

1. **阵营例外**：命中数 = 白名单内的位置与形态所允许的行数；该模式在**白名单之外必须 0**
   （现算：`core` **17** 行 = `RoleInstance` **10** + `Role` **4** + `RoleInfoImpl` **1** + `RoleInfoPort` **2**；
   `roleComponent/base/**` 与两个基类 **0**）。
2. **具体组件族**：`core/RoleInstance.java` 的 **1** 行 = 例外本身（那一行 `import`）；
   其余各格是**既存**命中（渲染组件的栏位登记与 javadoc 举例），与阵营无关、不在本次范围
   ⇒ 本次只承诺**一格都不新增**（对照上一提交的同一命令输出即可）。
3. **例外内部仍适用 §1.2 的形态限制**：不得写具体组件的 `.class`（`{@code}`/注释里的
   说明性写法不算），不得构造它，不得调用它的静态方法。

★ **上表数字是"取数时刻"口径**：`core/RoleInstance.java` 的行数历史上漂过三次
（1134 → 1019 → 995 → 现值），例外行数会随之变。判据不是"数字不许变"，而是：
**① 白名单之外恒为 0；② 例外只出现在白名单的位置与形态里**。数字变了就必须重新核对白名单
（不许"顺手扩大"）。

复算命令（逐行读盘、大小写敏感、含注释）：

```powershell
$M = "src\main\java\com\shadowHunterRolesPlugin"
$family    = 'builtin\.|HotbarRenderComponent|EnergyComponent|SanTEComponent|VitalsComponent|BuffComponent|TimerComponent|ServiceComponents'
$exception = 'FactionComponent'
# 逐文件计数（含 import 与注释）
function Show-Counts([string]$root, [string]$pattern) {
  Get-ChildItem -Recurse -File $root -Filter *.java | ForEach-Object {
    $f = $_; $n = 0
    foreach ($x in [IO.File]::ReadAllLines($_.FullName)) { if ($x -cmatch $pattern) { $n++ } }
    "{0,-40} {1}" -f $f.Name, $n
  }
}
# ① 具体组件族 —— 期望：core\RoleInstance.java = 1（例外那一行 import），core 其余件 = 0
Show-Counts "$M\core" $family
# ① 具体组件族 —— 期望：RoleComponent.java / ActiveComponent.java / base 三件全 0
#    ★ 本命令会把 roleComponent 下的组件文件一起数出来；组件之间互认是正常的，
#      框架层只有 RoleComponent.java / ActiveComponent.java 两行 + base/ 三件要看
Show-Counts "$M\roleComponent" $family
Show-Counts "$M\roleComponent\base" $family
# ② 阵营例外 —— 期望：只落在 core（RoleInstance 的 import + 转发两处 + 私有取用口 + 其 javadoc），
#    ActiveComponent / RoleComponent / base/** 全 0
Show-Counts "$M\core" $exception
Show-Counts "$M\roleComponent\base" $exception
# ③ 例外内部仍不得写"具体组件的 .class"（§1.2 ② 在例外上依然生效）
#    期望：只有注释 / {@code} 里的说明性写法（现算 3 行），代码行 0
Get-ChildItem -Recurse -File "$M\core" -Filter *.java | ForEach-Object {
  $f=$_; $i=0
  foreach($x in [IO.File]::ReadAllLines($_.FullName)){ $i++
    if($x -cmatch 'FactionComponent\.class'){ "$($f.Name):$i  $($x.Trim())" } }
}
```

## §4 与既有文件的关系

| 既有说法 | 与本件的关系 |
|---|---|
| `组件模型.md` §2④「框架不认识具体家族」 | ★ **本件是其上位规则**：不只家族，**任何具体组件**都不认识 |
| `Role` 的 `providedTypes`（数据注入）| **符合**本件 §1.3④ —— 它是**修复的样例**，应推广到其余各处 |
| `OperationProvider`「不进 `core/` 的公共能力区」| ★ 与本件 §1.3 的接口所有权规定**同源**，本件把它升为通则 |
| 旧的「框架级组件」提法 | ✗ **作废** —— 该提法曾导致「框架可当特例碰聚合根」的真实误判，并造出 `core → frameworkLevel` 的反向依赖 |
| **阵营组件（2026 增补）** | ★ **明列例外**：用户裁定「阵营真值必须住组件、旧接口与容器字段全删」。因此 `core/RoleInstance` 允许**按 id + 类型**取回 `FactionComponent` 的通用面（`getById(ID)` + `instanceof`），`core` 允许引用它的 `ID` 常量与类名。**例外范围仅此一处**，其余具体组件仍适用 §1.2 全部禁止形态；新增同类例外必须先取得用户裁定并在此表登记 |

## §5 本会话的教训（为什么此前是补丁）

1. **把清单搬个地方 ≠ 消除认识** —— 曾把白名单从 `Role` 搬到 `ServiceComponents`，方向反而是**新增** `core → frameworkLevel` 的 import。
2. **「重命名」不解决层级** —— 把 `frameworkLevel/` 改名 `builtin/` 消除了误导性名称，但**装配权仍在容器**里。
3. **真正的根治只有一条**：**把装配权移出框架层**，框架退化为「id + 通用面」。

## §6 本轮续报：认识面从「框架层」收窄到「**基类**」

★ **基类也是框架层**，判据一样严：
> **把基类单独拿出来读，能不能看出工程里有哪些具体组件？** 能看出就是违规。

### §6.1 已删除的六个"基类通用视图"（每个都只服务**一个**具体组件）

| 已删（原在 `RoleComponent` 上） | 现在归谁 |
|---|---|
| `requestRepaint()` | 渲染组件（`HotbarRenderComponent#markDirty`）|
| `readCurrentEnergy()` / `writeCurrentEnergy(int)` | 能量组件（`current()` / `set(int)`）|
| `readCurrentSanTE()` / `writeCurrentSanTE(int)` | SanTE 组件（同上；**原生产者 0** ⇒ 直删）|
| `heal(double)` | 生命组件（**原消费者 0**）|

★ 同批删除 `EnergyComponent.EnergyCosting`（一个方法、一个实现者、**零类型消费者** ⇒ 空转类型）；
`getEnergyCost()` **保留**（11 处真实消费者）。

★ **允许留在基类的只有两种**：① 生命周期钩子（`awake/start/stop/update`）；
② **参数是"另一个组件"的匿名入口**（`findComponent(Class<T>)` —— 类型由调用方给出，基类不认识具体类型）。

### §6.2 栏位（slot）的**持有者位移**（与"框架不认识组件"同源的一步）

```
旧：栏位住在【基类描述符】RoleComponent.Specification ⇒ 框架读它
新：栏位住在 HotbarSpecification（数据） + 渲染组件的 slotByComponent（运行期落位）
    ：组件在 ActiveComponent.awake() 里【登记】自己的栏位
```
⇒ 基类描述符**只剩一个可选读口** `slotOrNull()`；`hasSlot` / `slot` / `assignSlot` / `requiresSlot` 全删
（`setSlot` 本就只在 `HotbarSpecification` 上，保留 ✓）。

### §6.3 ★★ 一条因事故而立的新硬约定

```
ActiveComponent.awake() 是 final —— 子类只能覆写 onAwake()
```
**事故**：`CangluBlueIceRevolverSkill` 覆写 `awake()` 且未调 `super.awake()`
⇒ 栏位登记没执行 ⇒ **热键栏里没有该物品，且没有任何报错**（渲染计划只是"查不到栏位"就跳过）。
`final` 把"漏调"从**静默失效**变成**编译错误** ✓

### §6.4 两处栏位判据是**故意的**（互为补集，不合并）

| ① 装配期 `core/Role.java:328` | ② 登记期 `HotbarRenderComponent#registerSlot` |
|---|---|
| 拦"模板写错"（那时还没有实例）| 拦"运行期登记错"（含**不经装配器**的动态添加）|

★ **但两处共用同一套异常类型与文案**（冻结主句 `Slot N is already occupied by 'X'.` 一字未动，
登记期只**追加**一个分句点名"谁被拒"——因为 `awake()` 广播里调用方不知道是谁）。

★ 给**写组件的人**读的操作细节见 `组件模型.md` **§6**。
