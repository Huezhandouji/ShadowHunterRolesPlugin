# 0002 · 默认画法落在组件基类，而不是装配期描述符

- **状态**：已采纳（当前有效）
- **对象**：热键栏物品的**默认画法**（三态材质、名称与后缀、状态行、分隔线、识别键）放在哪里

## 背景

物品的外观**取决于运行期状态**：冷却剩余多少秒、是否被闸门挡住（沉默 / 眩晕）、能量够不够。这些状态在装配期都不存在——装配期只有"这个组件声明了什么"。

同时，装配期已经有了一个承担声明职责的对象（组件自带的**描述符**：图标 / 显示名 / 描述 / 冷却 / 耗能 / 是否占栏位），它在装配时被冻结成不可变快照，用来做校验与栏位绑定。把画法放哪一边，是个必须一次说清的选择。

## 决策

**默认画法落在组件基类**（`Skill` / `MainWeapon` 的 `buildItem()`），组件可以覆写、也可以 `super` 叠加；**描述符只做声明**，不产出物品。

## 被放弃的替代方案

**替代方案（画法进描述符）**：把默认画法写成描述符的方法，让"声明 + 产出"集中在同一个对象里。

放弃它的理由：**画物品要读运行期状态（冷却剩余 / 闸门 / 能量），而描述符是装配期对象**——它在组件实例化**之前**被创建、被冻结，手上既没有 `svc()`（组件的服务入口），也拿不到容器状态。要让它画物品，只能走两条路，两条都更坏：

- 装配后再把运行期状态"注入"描述符 ⇒ 描述符不再是不可变快照，"冻结"这条约束失去意义；
- 把状态读口塞进描述符 ⇒ 描述符变成半运行期对象，装配期校验要读的东西和运行期画物品要读的东西混在一起。

## 后果（含代价）

- **描述符不能独立产出物品**：想预览或校验"这个组件会长什么样"，必须先构造出组件实例；离线（没有服务端运行时）无法演示产出结果，这类验证只能放在服务端上做。
- **基类变重**：三个便利基类因此承担了表现逻辑；不继承它们、只实现能力接口的组件必须自己写画法。
- **表现相关代码分两处**：数据（图标 / 名字 / 描述 / 冷却 / 耗能）在描述符里，画法在基类里——读代码时要同时看两处才能知道"最终长什么样"。

## 门槛自证

- **难以回退**：改成描述符产出，等于要求描述符能读运行期状态——要动它的构造时机、冻结语义与所有使用点，并重新验证装配期校验链路。
- **缺上下文会令人困惑**：既然已经有描述符集中放表现数据，"为什么画法不跟它放一起"是读者一定会问的问题；不解释就会以为是随手放的。
- **是真实取舍**：确实评估过"声明 + 产出集中在一个对象"这条路（它在阅读上更顺），是因为运行期状态这一条硬性限制才选了分离。
