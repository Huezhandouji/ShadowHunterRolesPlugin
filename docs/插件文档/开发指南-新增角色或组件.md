# 开发指南：新增角色 / 技能 / 被动 / 主武器

这份文档写给**要往插件里加内容的开发者**。读完你能照着现有约定写出一个能编译、能装配、能在游戏里验证的技能 / 被动 / 主武器，或者新增一整条角色；也能按仓库的规范加一条命令。

前置阅读：`架构与组件模型.md`（组件基类与钩子、端口白名单、施放与冷却契约、渲染契约）。

> 四条最要紧的事：
> 1. 主动组件**只有一条**施放路径 —— 实现 `onCast(CastSignal)`，返回 `CastResult`；
> 2. **冷却由组件自己启动**（在施放成功处调 `svc().cooldowns().start(...)`），框架不会代启动；
> 3. **组件不参与渲染**：只声明图标 / 显示名 / 描述，物品由统一渲染器写；
> 4. **装配只有一个入口**：`Role.Builder.addComponent`（带槽位 / 不带槽位两个重载）。组件只需 `extends RoleComponent` 并按需实现能力接口；`Skill` / `MainWeapon` / `PassiveSkill` 是**可选的便利基类**（见「组件不必继承三个基类」）。

## 开发环境与常用命令

```powershell
cd ShadowHunterRoles
$env:GRADLE_USER_HOME = "$PWD\.gradle-work"       # 可选：把 Gradle 缓存放在仓库内

.\gradlew build -x copyPluginJar --console=plain  # 编译（-x 跳过自动拷到调试服）
.\gradlew runServer                               # 起本地 Paper 1.21.11 调试服
```

- 构建成功的标志是 `BUILD SUCCESSFUL`，产物在 `build/libs/ShadowHunterRolesPlugin-1.0.0.jar`。
- 调试服目录是 `run/`（`run/logs/latest.log`、`run/plugins/`）。
- 想每次构建自动把 jar 拷进服务端，在 `gradle.properties` 里把 `pluginCopyPath` 指向目标 `plugins` 目录（`build.gradle.kts` 的 `copyPluginJar` 只在配置了该属性时才复制）。
- 起服成功的标志是控制台出现 `ShadowHunter Character System enabled.`。

## 新增一个技能

### 文件放哪里

```
src/main/java/com/shadowHunterRolesPlugin/roleComponent/<角色包>/skill/<名字>Skill.java
```

现有包：`roleComponent/meiqiHezi/skill/`、`roleComponent/red/`。**跨组件依赖只允许在同一角色包内**（用 `getComponent(X.class)`），跨角色引用属于设计错误。

### 骨架

```java
package com.shadowHunterRolesPlugin.roleComponent.meiqiHezi.skill;

import com.shadowHunterRolesPlugin.core.Skill;
import com.shadowHunterRolesPlugin.core.dispatch.CastResult;
import com.shadowHunterRolesPlugin.core.dispatch.CastSignal;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import net.kyori.adventure.text.Component;
import org.bukkit.Material;
import org.bukkit.entity.Player;

/** 示例技能：3 格内敌人吃 6 点物理伤害，自己回 2 点生命。 */
public class MeiqiheziSampleSkill extends Skill {

    private static final int COOLDOWN_TICKS = 100;   // 5 秒，与构造器实参保持一致
    private static final int ENERGY_COST = 10;
    private static final double RADIUS = 3;
    private static final double DAMAGE = 6;
    private static final double HEAL = 2;

    /** 由容器经 ComponentFactory.create(id, services) 调用；id 在装配处声明（见「新增一个角色」）。 */
    public MeiqiheziSampleSkill(String id, ComponentServices services) {
        super(id, services,
              Component.text("示例技能"),                  // 显示名
              Component.text("3 格内敌人受伤，自身回血"),   // 描述
              COOLDOWN_TICKS, ENERGY_COST, Material.PAPER);
    }

    @Override
    public CastResult onCast(CastSignal signal) {
        if (!svc().buffs().canCastSkill()) return CastResult.NO_COOLDOWN;        // 沉默 / 眩晕：不启冷却
        if (!svc().energy().tryConsume(ENERGY_COST)) return CastResult.REJECTED_NO_ENERGY;

        Player caster = svc().self().player();                                   // 每次现取，不存字段
        for (Player victim : caster.getLocation().getNearbyPlayers(RADIUS)) {
            if (!svc().factions().isHostile(victim)) continue;                   // 未选角色的玩家也算敌人
            svc().damage().physicalDamage(victim, caster, DAMAGE);               // 真实伤害用 trueDamage(...)
        }
        svc().vitals().heal(HEAL);
        svc().cooldowns().start(getCooldownTicks());                             // 冷却由组件自启
        return CastResult.SUCCEED;                                               // 只表示"施放成功"
    }
}
```

### 要点

- **构造参数顺序**：`super(id, services, 显示名, 描述, 冷却刻数, 能量消耗, 图标)`；`id` 与 `services` 由容器注入，组件内部不再硬编码 id。
- **基类是可选的**：这份骨架用 `Skill`，因为它是"能施放 + 能显示"的最短写法；框架真正要求的只有 `extends RoleComponent`（见「组件不必继承三个基类」）。`Skill` 内部把构造参数装进一个 `HotbarSpec` 并实现 `spec()`，七个表现访问器由接口的 `default` 方法提供，所以你不必手写 getter。
- **端口白名单**见 `架构与组件模型.md` 的「ComponentServices」一节；不要用白名单以外的方法，也不要 import 插件主类或平台层。
- **冷却**：施放成功处调 `svc().cooldowns().start(getCooldownTicks())`。`start` 是重启语义（覆盖旧值、不叠加）；`end()` 可主动结束冷却并在冷却中返回 `true`；到期由框架每刻扫描处理。想收尾自己的状态就覆写 `onCooldownEnd(CooldownEndReason reason)`（枚举值 `EXPIRED` / `ENDED_BY_COMPONENT` / `RESTARTED`）。
- **判定顺序**通常写成：闸门（`canCastSkill`）→ 能量（`tryConsume`）→ 做事 → 启动冷却 → 返回 `SUCCEED`。任何"没做事"的分支都返回 `NO_COOLDOWN`。
- **触发来源**：`CastSignal.trigger()` 是 `RIGHT_CLICK` / `LEFT_CLICK` / `DROP` 之一。只响应某一种的话，开头判断后返回 `NO_COOLDOWN`。
- **加药水必须走 `svc().buffs().applyPotionEffect(...)`**：它带默认标志；如果要保真 `ambient` / `particles`，用 5 参重载。直接 `player.addPotionEffect(...)` 会绕过记账，清角色时不会回收（现有代码里只有"施加给别人"的效果是直接加的）。
- **热量键**：技能物品用 `Skill.Utils.SKILL_KEY` 标记，不需要自己造物品。

### 延时与周期任务

- 用 `svc().timers()`：`run(Runnable)` / `runLater(delayTicks, Runnable)` / `runRepeating(initialDelay, period, Runnable)`。任务**创建即登记**进本组件的资源表（`core/ports/TimerPort`）。
- 取消：在自己的 `stop()` 里 `task.cancel()`（样板 `MeiqiheziCircleSlashSkill` 的 `castTask`）。框架在 `stop()` 返回后还会兜底取消资源表，重复取消是幂等的。
- 任务体内只需保留**与玩家状态相关**的守卫（如 `caster.isDead() || !caster.isOnline()`）。
- **不要**直接 `Bukkit.getScheduler()`；调度只在 `platform/BukkitSchedulerAdapter` 里包装。

### 不要覆写渲染

组件侧**没有**可覆写的渲染方法：没有 `createIconItem`，也没有带参的 `getDisplayName`。新组件只做两件事：

1. 在构造函数里声明 `getIcon()`（图标）与 `getDisplayName()`（显示名）以及描述；
2. 状态变化时**不要自己写物品** —— 框架在施放 / 攻击 / 冷却启动 / 能量变化 / 控制效果移除这些触点自动置脏，并在每刻末尾统一重绘（`core/hotbar/HotbarRenderer`）。

材质、名字颜色、后缀、描述行序与持久化标记全部由渲染器统一生成。

## 新增一个被动

文件放在 `roleComponent/<角色包>/<名字>Passive.java`（现有被动分布在 `roleComponent/` 根、`roleComponent/red/`、`roleComponent/meiqiHezi/passive/` 三处，按角色归属放置）。

```java
package com.shadowHunterRolesPlugin.roleComponent.red;

import com.shadowHunterRolesPlugin.core.PassiveSkill;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import net.kyori.adventure.text.Component;

/** 示例被动：开始生效时初始化，每刻做点小事，停止时对称回收。 */
public class RedSamplePassive extends PassiveSkill {

    /** 由容器经 ComponentFactory.create(id, services) 调用（id 在装配处声明，见「新增一个角色」）。 */
    public RedSamplePassive(String id, ComponentServices services) {
        super(id, services, Component.text("示例被动"), Component.text("被动描述"));
    }

    @Override
    public void start() {
        // 初始化数据 / 发放装备 / 登记定时器。被动"开始生效"的唯一时机。
    }

    @Override
    public void stop() {
        // 与 start 严格对称：start 里创建的资源在这里全部回收或清空。
    }

    @Override
    public void update() {
        // 每刻（20 Hz）。不要阻塞；读写状态走 svc() 端口。
    }
}
```

要点：

- 基类是 `PassiveSkill extends RoleComponent`；被动**不实现** `HotbarItem` / `HotbarActionable`，所以它天然不能被抓到手里施放，也不会出现在热键栏里。`PassiveSkill` 是可选的便利基类：只 `extends RoleComponent` 也能写被动（见「组件不必继承三个基类」）。
- 生命周期钩子就是基类的 default 方法（`awake()` / `start()` / `stop()` / `update()`），按需覆写，不需要额外接口。
- `awake()` 只在"需要解析跨组件依赖并缓存引用"时覆写（用 `getComponent(X.class)`）。它必须幂等，且不得改动任何玩家可见状态。
- 想在 SanTE 变化时做事：覆写 `onSanTEChange(int pre, int now)`（`pre == now` 不通知；用 `svc().self().player()` 取玩家）。样板：`roleComponent/DefaultSanTEZeroPunishment`。
- **有 `start` 必有对称的 `stop`** —— 装备类被动只发不收，会让玩家脱不下装备。

## 新增一个主武器

文件放在 `roleComponent/<角色包>/mainWeapon/<名字>MainWeapon.java`。

```java
package com.shadowHunterRolesPlugin.roleComponent.red;

import com.shadowHunterRolesPlugin.core.MainWeapon;
import com.shadowHunterRolesPlugin.core.dispatch.AttackSignal;
import com.shadowHunterRolesPlugin.core.dispatch.CastResult;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import net.kyori.adventure.text.Component;
import org.bukkit.Material;
import org.bukkit.entity.Player;

/** 示例主武器：攻击造成 8 点物理伤害并击退。 */
public class RedSampleMainWeapon extends MainWeapon {

    private static final int COOLDOWN_TICKS = 100;   // 5 秒

    /** 由容器经 ComponentFactory.create(id, services) 调用（id 在装配处声明，见「新增一个角色」）。 */
    public RedSampleMainWeapon(String id, ComponentServices services) {
        // 注意参数顺序：图标在冷却之前（与 Skill 相反，这个顺序是固定的）；能量消耗恒为 0
        super(id, services, Component.text("示例之刃"),
              Component.text("攻击造成物理伤害"), Material.IRON_SWORD, COOLDOWN_TICKS);
    }

    @Override
    public CastResult onAttack(AttackSignal signal) {
        Player attacker = svc().self().player();                     // 攻击者永远是自己
        Player victim = signal.victim();
        svc().damage().physicalDamage(victim, attacker, 8, 1);        // 4 参 = 伤害 + 击退
        svc().cooldowns().start(getCooldownTicks());                  // 冷却由组件自启
        return CastResult.SUCCEED;
    }
}
```

要点：

- **主武器只受眩晕限制**（不受沉默）：闸门是 `svc().buffs().canUseMainWeapon()`。
- `MainWeapon` 是**可选的便利基类**（`extends ActiveComponent`，另实现 `CombatHook`，能量消耗恒传 0）；只 `extends RoleComponent implements HotbarActionable, CombatHook` 也能写，见「组件不必继承三个基类」。
- 攻击路径：`MainWeaponListener.onAttackPlayer` 取消原版伤害 → `RoleInstance.handleAttack` → `onAttack(AttackSignal)`。左键 / 右键 / `Q` 三个入口同样走 `onCast(CastSignal)`，与技能是同一条管道。
- **主武器没有能量消耗**：`MainWeapon` 构造函数恒把能量消耗传 0，因此它的图标永远不会有"能量不足"状态。写新武器时也保持这一点。
- 攻击玩家会按声明值启动冷却（现有两个武器都在 `onAttack` 里无条件启动），这是当前的既定行为。

## 组件不必继承三个基类（能力按需组合）

统一装配入口带来的一条自由：组件**只要 `extends RoleComponent`，再按需要实现能力接口**，就可以登记进角色。

| 能力接口 | 位置 | 提供什么 |
|---|---|---|
| `HotbarPresentable` | `core/hotbar/` | 能进热键栏：只写**一个实现点** `spec()`（返回 `HotbarSpec.of(id, 显示名, 描述, 图标, 冷却, 能量消耗, 种类)` 建好的对象）；`getId` / `getDisplayName` / `getDescription` / `getIcon` / `getCooldownTicks` / `getEnergyCost` / `getKind` 全由接口的 `default` 方法代劳 |
| `CooldownBearing` | `core/hotbar/` | 有冷却：`getCooldownTicks()`（`0` = 不进冷却） |
| `EnergyCosting` | `core/hotbar/` | 耗能量：`getEnergyCost()`（`0` = 不耗能） |
| `HotbarActionable` | `core/dispatch/` | 能被按键施放：`onCast(CastSignal)` |
| `CombatHook` | `core/dispatch/` | 能参与攻击结算：`onAttack(AttackSignal)` |
| `HotbarItem` | `core/hotbar/` | 渲染器的读写面（七个无参 getter）；`HotbarPresentable.asHotbarItem()` 返回它，`RoleInstance.hotbarItemOf(String)` 优先走这一条。通常不必单独实现 |

`Skill` / `MainWeapon` / `PassiveSkill` **没有被删除**：它们是"能力组合已经配好"的便利基类；不想用继承时按上表挑能力即可。

### 不继承基类的组合

三个旧装配方法的工厂形参是**窄类型**（`ComponentFactory<Skill>` / `ComponentFactory<PassiveSkill>` / `ComponentFactory<MainWeapon>`），所以一个不属于这三支的 `RoleComponent` 子类过去没有登记位置。统一入口把它放宽成 `ComponentFactory<? extends RoleComponent>` ⇒ 这类组合现在可以写、也可以登记。例如**既能被按键施放、又能参与攻击结算**的组件（不想继承 `MainWeapon`，以免顺带带上主武器的渲染分支与"能量消耗恒 0"）：

```java
package com.shadowHunterRolesPlugin.roleComponent.myRole;

import com.shadowHunterRolesPlugin.core.dispatch.AttackSignal;
import com.shadowHunterRolesPlugin.core.dispatch.CastResult;
import com.shadowHunterRolesPlugin.core.dispatch.CastSignal;
import com.shadowHunterRolesPlugin.core.dispatch.CombatHook;
import com.shadowHunterRolesPlugin.core.dispatch.HotbarActionable;
import com.shadowHunterRolesPlugin.core.ports.ComponentServices;
import com.shadowHunterRolesPlugin.roleComponent.RoleComponent;

/** 既能被按键触发、又能参与攻击结算的组件：不继承任何便利基类。 */
public class MyHybridComponent extends RoleComponent implements HotbarActionable, CombatHook {

    public MyHybridComponent(String id, ComponentServices services) {
        super(id, services);
    }

    @Override
    public CastResult onCast(CastSignal signal) {
        svc().vitals().heal(1);                    // 施放：给自己回 1 点
        return CastResult.NO_COOLDOWN;             // 没启动冷却 ⇒ 框架不动冷却
    }

    @Override
    public CastResult onAttack(AttackSignal signal) {
        svc().damage().physicalDamage(signal.victim(), svc().self().player(), 2);
        svc().cooldowns().start(40);               // 攻击：自己启动 2 秒冷却
        return CastResult.SUCCEED;
    }
}
```

登记它同样只用统一入口（这里用无槽位重载，表示不占热键栏）：

```java
                .addComponent(ID_MY_HYBRID, MyHybridComponent::new, ItemKind.SKILL)
```

写这类组件前先知道两件事：

- **权威 kind 在注册处，不在组件里**：`addComponent` 的 `kind` 实参决定冷却表、能力闸门、物品标记与渲染文案；`spec()` 里的 kind 只作表现用途。理由是服务集**先于**组件构造 —— `RoleInstance.createServices(String, ItemKind)` 先造出冷却端口（`CooldownPortImpl` 在构造期绑定 kind），而 `ComponentFactory.create(String, ComponentServices)` 只给 id 与服务集、不给 kind ⇒ 组件在构造期无从得知权威 kind（见 `架构与组件模型.md` 的「权威 kind 在注册处」）。
- **两条管道入口今天另有收窄**：`RoleInstance.handleCast`（按键施放）要求组件是主动组件 `ActiveComponent`，`RoleInstance.handleAttack`（攻击）要求实现 `CombatHook`。所以只 `extends RoleComponent implements HotbarActionable` 的组件今天**能写、能编译、能登记**，但按键不会派发到它；要被按键施放，让它继承 `ActiveComponent`（或直接用 `Skill`）。

## 新增一个角色

角色是**代码定义的**：唯一装配点是 `registry/RoleLoader`，没有 `roles.yml` 之类的数据文件（数据驱动目前没有实现）。

### 步骤

1. 写好该角色用到的组件类（见「新增一个技能」「新增一个被动」「新增一个主武器」）；
2. 在 `RoleLoader` 顶部把该角色要用的组件 id 声明成 `private static final String ID_*` 常量（现有 14 个 id 常量、16 条装配调用，可对照着写）；
3. 加一个 `private static Role.Builder <id>Builder()`，照 `meiqiheziBuilder()` 或 `redBuilder()` 的样子写；
4. 在 `defaultDefinitions()` 的 `List.of(...)` 里加一条 `new Definition("<id>", RoleLoader::<id>Builder)`；
5. 构建 → 起服 → 进游戏 `/role set <id>` 验证（见「提交前的检查与游戏内验证」）。

### 抄一份最小模板

```java
    private static Role.Builder sampleBuilder() {
        return new Role.Builder("sample")                                  // id（必填，非空）
                .displayName(Component.text("Sample"))
                .description(List.of(
                        Component.text("第一行描述"),
                        Component.text("第二行描述")
                ))
                .maxHP(40)            // > 0，否则抛 IllegalArgumentException
                .baseATK(10)          // >= 0
                .maxEnergy(100)       // >= 0
                .maxSanTE(100)        // >= 0
                .faction(Faction.HUNTER)                                                          // 传 null → UNKNOWN
                .addComponent(ID_SAMPLE_MAIN_WEAPON, RedSampleMainWeapon::new, 0, ItemKind.MAIN_WEAPON)  // 槽位 0
                .addComponent(ID_SAMPLE_SKILL_1, MeiqiheziSampleSkill::new, 1, ItemKind.SKILL)           // 槽位 1..3
                .addComponent(/* … */, 2, ItemKind.SKILL)
                .addComponent(/* … */, 3, ItemKind.SKILL)
                .addComponent(ID_DEFAULT_SAN_TE_ZERO, DefaultSanTEZeroPunishment::new, ItemKind.PASSIVE)
                .addComponent(ID_AUTO_RECOVER_SANTE, AutoRecoverSanTEHealthPassive::new, ItemKind.PASSIVE)
                .addComponent(ID_SAMPLE_PASSIVE, RedSamplePassive::new, ItemKind.PASSIVE)
                .icon(Material.PAPER);                                         // 供下游读取
    }
```

**两个重载**（`core/Role.java` 的 `Role.Builder`）：

| 重载 | 形态 | 用途 |
|---|---|---|
| `addComponent(id, 工厂, 槽位, kind)` | 四参 | 占热键栏：`槽位` 只能是 `0..8` 且同一角色内不能冲突；`kind` 是权威 kind |
| `addComponent(id, 工厂, kind)` | 三参 | **不占热键栏**（被动与"不上热键栏的组件"用这个）：不写槽位表，渲染器遍历槽位表时天然看不到它 |

`kind` 的取值来自 `com.shadowHunterRolesPlugin.core.hotbar.ItemKind`：`SKILL`（技能）、`MAIN_WEAPON`（主武器）、`PASSIVE`（被动）。模板里用到了它，所以要在 `RoleLoader.java` 顶部的 import 区加一行 `import com.shadowHunterRolesPlugin.core.hotbar.ItemKind;`。

### 三个旧装配方法（仍在，但已标"建议改用新入口"）

`addSkill` / `addMainWeapon` / `addPassive` **都还在、还能用**，签名与语义没有变化：它们与新入口完全等价，只是把权威 kind 替你补上。三者都已标 `@Deprecated`（源码见 `core/Role.java` 的 `Role.Builder`），而且三个旧方法与两个新重载都只调用**同一条内部路径** `Role.Builder.addComponentInternal` —— 校验、id 去重、槽位写入只有一处实现，所以两条写法不会有行为差异。

| 旧写法 | 等价的统一入口 | 权威 kind | 槽位 |
|---|---|---|---|
| `addSkill(id, 工厂, 槽位)` | `addComponent(id, 工厂, 槽位, ItemKind.SKILL)` | `SKILL` | 必填 |
| `addMainWeapon(id, 工厂, 槽位)` | `addComponent(id, 工厂, 槽位, ItemKind.MAIN_WEAPON)` | `MAIN_WEAPON` | 必填 |
| `addPassive(id, 工厂)` | `addComponent(id, 工厂, ItemKind.PASSIVE)` | `PASSIVE` | 无 |

`registry/RoleLoader` 里现有的两条角色清单**仍在用旧写法**（照旧工作）；新写的代码建议直接用 `addComponent`。另外旧别名的工厂形参是窄类型（`ComponentFactory<Skill>` 等），统一入口放宽到 `ComponentFactory<? extends RoleComponent>` —— 只 `extends RoleComponent` 的组件只能走新入口。

### 硬规则（违反会在装配期抛异常，该角色不会被注册）

| 规则 | 事实 |
|---|---|
| 组件 id **跨类型唯一** | 技能 / 被动 / 武器共用一个命名空间，重复注册抛 `IllegalArgumentException` |
| 槽位只能是 `0..8`，且不能冲突 | 非法槽位与冲突都抛异常（不会"告警后覆盖"） |
| 角色 id 非空 | `new Role.Builder(id)` 里校验 |
| 数值必须合法 | `maxHP > 0`；`baseATK` / `maxEnergy` / `maxSanTE` ≥ 0 |
| 装配失败按角色隔离 | 单个角色装配抛异常 → 记 `SEVERE`、跳过该角色，其余照常注册；不会让异常冒泡拖垮整个插件 |
| 派发顺序 = 注册顺序 | 组件的**注册顺序**就是派发顺序：`addComponent`（或三个旧别名）的调用顺序，逐刻广播与 `onSanTEChange` 事件都按它走；**不再**按"技能 → 被动 → 主武器"分组 |

### 组件构造器会被执行多次吗

不会。`addComponent`（以及三个旧别名）只登记 `(id, 工厂, 权威 kind, 槽位?)`，组件实例是在**角色实例化时**由 `Role.createComponent(id, services)`（全仓唯一的组件创建点）经 `ComponentFactory.create(id, services)` 创建的。因此：

- 校验（id 非空、跨类型唯一、槽位 0..8 且不冲突）在注册时就完成；
- 但**组件构造函数必须是纯的**：不要在构造里改玩家状态、发起任务或写静态状态 —— 要"开始生效"就写在 `start()` 里。

## 命令编写规范

### 现有 `/role` 保持传统实现

`/role` 仍走 `plugin.yml` 的 `commands: role:`（含 `aliases: [r]`）+ 主类 `getCommand("role").setExecutor(new RoleCommand(...))`。它**不迁移**到 Brigadier：迁移会改变 Tab 补全与用法文案等玩家可见行为，却没有功能收益。

### 新增子命令：一个子命令一个类

`command/` 包用统一接口 `command/SubCommand`：

- `getName()`：子命令名（`/role` 后的第一个参数，不区分大小写）；
- `getUsage()`：用法说明（用于调试类命令的用法提示）；
- `execute(CommandSender, String[])`：收到的 `args` 里**子命令名已被剥离**；
- `onTabComplete(CommandSender, String[])`：补全，默认返回空；
- `SubCommand.filter(候选集合, 前缀)`：共享的前缀过滤（大小写归一），不要每个类抄一份。

分发器只负责路由：`RoleCommand` 把第一级参数路由到子命令，`DebugCommand` 把调试话题路由到二级子命令。两层都遵循「只消费自己那一级参数，把剩余 `String[]` 交给下一层」。

当前结构：

```
/role                      plugin.yml + 主类 setExecutor（传统注册）
 └─ RoleCommand            纯分发器：非玩家拒绝 / 无参数静默 / 未知子命令统一报错 / Tab 补全
     ├─ set    → SetRoleCommand
     ├─ clear  → ClearRoleCommand
     ├─ energy → EnergyCommand
     ├─ help   → HelpCommand
     └─ debug  → DebugCommand          ← op 门控在这里（先于任何参数判断）
          ├─ cooldown → DebugCooldownCommand
          └─ sched    → DebugSchedCommand
```

- **门控只写一处**：调试树的门控在 `DebugCommand.execute` 开头（`player.isOp()`），叶子命令不再各自判 op。非 op 玩家无论带不带话题、话题是否认识，都得到同一句拒绝文案；Tab 补全也走同一道门，因此不会向普通玩家暴露调试话题。
- **命令代码不写日志**（`command/` 包里没有 `getLogger`）；所有反馈都用 Adventure `Component` 直接回给发送者。调试命令是唯一例外：它把关键行**同时**以 `[command-debug] ` 前缀写进服务端日志，便于离线排查。
- **报错文案要固定**：已命中的分支返回 `true`；参数个数不匹配时的行为（静默还是提示）要与相邻命令保持一致 —— 现有命令里有几处刻意保持的"静默返回"，改动前先看 `README.md` 里「命令的边界行为」的清单。

### 将来新增顶层命令：Brigadier

```java
this.getLifecycleManager().registerEventHandler(LifecycleEvents.COMMANDS, commands ->
    commands.registrar().register(<命令树>, "<描述>", List.of("<别名>")));
```

- 注册只走 `LifecycleEvents.COMMANDS`；**不要**把同一个命令名同时写进 `plugin.yml` 的 `commands:`（会重复注册）；
- 命令级权限用 `requires(source -> source.getSender().hasPermission("<节点>"))`，并且该权限节点要在 `plugin.yml` 的 `permissions:` 里声明；
- 执行体里不要把异常抛回主线程：捕获 → 给发送者一条可读消息 → 记日志；
- 玩家可见文案一律用 Adventure `Component`，不要用旧的颜色常量或字符串拼接。

## 组件与角色的注册

组件**不需要**注册到别处：角色模板保存的是 `(id, 工厂, 权威 kind, 槽位?)`，实例化时由 `RoleInstance.initComponents` 按**注册序**逐条取出 → `Role.createComponent(id, services)`（全仓唯一的组件创建点）→ `ComponentFactory.create(id, services)` 在构造期注入服务集 → 登记进组件注册表，并按**具体类型**归位到技能 / 主武器 / 被动三张视图表（不按 kind 猜测，所以 `Skill`、`MainWeapon`、`PassiveSkill` 的窄类型访问器只对继承它们的组件有效）。

也就是说：新增组件只需写类 + 在 `RoleLoader` 的 Builder 里登记，没有清单文件要改。

## 提交前的检查与游戏内验证

| # | 检查 | 怎么做 |
|---|---|---|
| 1 | 编译 | `.\gradlew build -x copyPluginJar --console=plain`，看 `BUILD SUCCESSFUL` |
| 2 | 装配无异常 | 起服看控制台；出现 `Role 'xxx' failed assembly validation and was NOT registered` 就是「新增一个角色」里那张硬规则校验拦下了 |
| 3 | 其它角色没被带崩 | 起服应看到 `ShadowHunter Character System enabled.` |
| 4 | 能被选中 | 进游戏 `/role set <id>`，应回显 `Your role has been set: <id>` |
| 5 | 热键栏正确 | 0 号位主武器、1–3 号位技能；图标 / 名字取自组件声明值；四态（就绪 / 冷却中 / 被禁用 / 能量不足）与描述行由渲染器统一生成；冷却中的技能名带 ` x.xs` 且逐刻递减 |
| 6 | 施放正确 | 左键 / 右键 / `Q` 各试一次；冷却按声明值启动 |
| 7 | 回收干净 | `/role clear` 或死亡后：最大生命恢复原值、**本系统加的**药水效果消失、热键栏里的技能 / 武器物品被清掉、任务停止 |
| 8 | 跨组件依赖 | 用 `getComponent(Xxx.class)`，只在同一角色包内使用 |

观测手段：

- 组件抛异常会被隔离，并在日志里打一条 `SEVERE`（同一组件只报一次，恢复后再报一次 `INFO`）——见 `core/RoleInstance.runComponentUpdate`；
- 调试命令可以现场看冷却状态：`/role debug cooldown status <槽位|组件id>`、`/role debug cooldown end/restart ...`、`/role debug sched [all]`；
- 调试命令的关键输出也会带 `[command-debug] ` 前缀进 `logs/latest.log`。

## 目前不支持的能力

以下都在本插件里**没有实现**，写代码时不要假设它们存在：

| 事项 | 现状 |
|---|---|
| 数据驱动角色配置（`roles.yml` 之类） | 没有。角色只能在 `RoleLoader` 里用代码装配 |
| 可注册的控制效果类型 | 没有。`BuffType` 是固定枚举（`STUN` / `SILENCE` / `IMMUNE`），能力闸门也写死在 `BuffManager.canCastSkill` / `canUseMainWeapon` |
| 可注册的阵营与关系策略 | 没有。`Faction` 是固定枚举（`SHADOW` / `HUNTER` / `UNKNOWN`），敌对规则写死在 `RoleInstance.isHostileTo` |
| 声明式组件依赖校验（缺依赖时提前报错） | 没有。取不到组件时 `getComponent` 返回 `null`，需要自己判空 |
| 组件读取角色模板数据（`maxHP` / `baseATK`） | 端口里没有这条通道；要用得先加一个新端口成员 |
| 游戏内改数值 | 没有配置文件，改数值必须改代码并重新构建 |
| Folia 适配 | 不做。服务端基线是 Paper |

## 禁忌清单

1. **不 import 插件主类**、不调 `ShadowHunterRolesPlugin.getInstance()`（组件与领域层都不该依赖它）；
2. **不直接 `Bukkit.getScheduler()`**、不写裸的 `BukkitRunnable` 作为唯一调度手段 —— 走 `svc().timers()`；
3. **有 `start` 必有对称的 `stop`**；`stop` 里把缓存的组件引用置空；
4. **`Player` 不存进长生命周期字段或长任务闭包** —— 存 `UUID`，或每次 `svc().self().player()` 现取；
5. **数值提成类顶部命名常量**（几何 / 特效参数除外）；
6. **组件不碰热键栏**：不造 `ItemStack`、不请求刷新；
7. **不要"顺手改正" id 里的拼写**：`meiqihezi_equippments_passive`、`red_equippments_passive`、`autoRecoverSanTEPassive` 都是索引键，改名等于换一个组件；
8. **不要改 `RoleAPI` 既有方法的签名或返回类型**：只增不改，破坏性变更会连带影响下游插件；
9. **`ComponentServices` 成员数固定为 10**：要加端口成员必须先做设计决策；
10. **新代码不要再用 `addSkill` / `addMainWeapon` / `addPassive`**：它们已标 `@Deprecated`，保留只是为了不破坏现有清单；新写法是 `addComponent`（含槽位 / 不含槽位两个重载）；
11. **文档只描述插件本身**：写进本目录的内容应当是使用者或开发者需要知道的插件行为与用法。
