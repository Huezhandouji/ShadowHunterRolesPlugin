### 4.1 ★ 命名纪律：`builtin/` 不是「框架级」（本轮改名确立）

- **旧名的问题**：`frameworkLevel`（框架级）这个**层级名**曾导致一次**真实误判** —— 有人据此认为
  「框架级组件可作为特例去碰聚合根 `Role`」，并因此制造了一条 `core → frameworkLevel` 的**反向依赖** ✗。
- **改名后的语义**：`builtin/` = 「**提前写好的内建组件**」（随框架一起发布），与 `custom/` 的
  **角色内容组件** **无层级之别** —— 两者都是 `RoleComponent` 的普通实现、都按角色实例装配、
  都只能经自己的服务集取用 ✓。
- ★★ **纪律（写死）**：**不得因为「名字带框架」就把内建组件当特例去碰聚合根 `Role`**；
  它们不持有、也不得直改聚合根。`ServiceComponents.FRAMEWORK_PROVIDED_TYPES` 的**字段名保留**

- **判据**：`Test-Path …/roleComponent/frameworkLevel` = **False**；全 `src`（含 `src/test`）内旧包名字串命中 = **0** ✓。

## 6. ★ 基类与描述符的硬约定（**每条都对应一次实测事故**）

> 这一节是**契约**，不是建议。写新组件前先读它。

### 6.1 `RoleComponent` 基类**不得出现任何具体组件的语言**

判据 = 「**把基类单独拿出来读，能不能看出工程里有哪些具体组件**」——能看出就是违规。

已按此删除的六个"框架通用视图"（**它们都在基类上，却只服务一个具体组件**）：

| 已删除 | 现在的归属 | 消费者的新写法 |
|---|---|---|
| `requestRepaint()` | 渲染组件 | 取到 `HotbarRenderComponent` 后调 `markDirty()` |
| `readCurrentEnergy()` | 能量组件 | `EnergyComponent#current()` |
| `writeCurrentEnergy(int)` | 能量组件 | `EnergyComponent#set(int)` |
| `readCurrentSanTE()` | SanTE 组件 | `SanTEComponent#current()`（原基类那份**生产者 0**，直删）|
| `writeCurrentSanTE(int)` | SanTE 组件 | `SanTEComponent#set(int)`（同上）|
| `heal(double)` | 生命组件 | `VitalsComponent#heal(double)`（原基类那份**消费者 0**）|

★ **允许留在基类的两种形态**（都不是"具体组件的语言"）：
1. **生命周期钩子**：`awake()` / `start()` / `stop()` / `update()`；
2. **参数是"另一个组件"的匿名入口**：`findComponent(Class<T>)` / `getComponent(Class<T>)` ——
   类型由**调用方**给出，基类不认识任何具体类型 ✓。

★ 同批删除：`EnergyComponent.EnergyCosting`（**多此一举** —— 只有一个方法、实现者只有 `ActiveComponent`、**零类型消费者**）；`getEnergyCost()` 本身**保留**（11 处真实消费者）。

### 6.2 ★★ `ActiveComponent.awake()` 是 **`final`**，子类只能覆写 `onAwake()`

```java
// ActiveComponent
@Override public final void awake() {   // 子类【不能】覆写
    HotbarRenderComponent render = findComponent(HotbarRenderComponent.class);
    if (render != null) render.registerSlot(this, specification().slotOrNull());
    onAwake();                          // 子类钩子，在登记【之后】调用
}
protected void onAwake() { }
```

**为什么必须 `final`**（实测事故）：`CangluBlueIceRevolverSkill` 曾覆写 `awake()` 且**未调 `super.awake()`**
⇒ 栏位登记没执行 ⇒ **热键栏里没有那把左轮，而且没有任何报错**（渲染计划只是"查不到栏位"就跳过）。
`final` 把这条路**从编译期堵死** —— 想漏也漏不了。

### 6.3 栏位（slot）的归属与仲裁

```
持有者 ①：描述符 —— HotbarSpecification.slot（数据；setSlot 只能 0..8、冻结后禁改）
持有者 ②：渲染组件 —— slotByComponent（Map<组件 id, 栏位>；★ 运行期落位读它）
```

- **登记**：组件在 `awake()` 里登记（见 6.2）；`slot == null` ⇒ **撤销登记** = 不占热键栏。
- **仲裁**：同栏位被两个组件占用 ⇒ 抛异常；同组件重复登记同栏位 ⇒ 幂等。
- **落位**：`renderPlan()` 读登记表（**不再读描述符**）；`componentIdAtSlot(...)` 亦读登记表
  ⇒ 反查与落位**同源**，不可能脱节。
- ★ **`componentIdAtSlot` 已从静态改为实例方法**（登记表是实例状态）。

### 6.4 ★ 两处栏位判据是**故意的**，且**用同一套说法**

| | ① 装配期 `core/Role.java:328` | ② 登记期 `HotbarRenderComponent#registerSlot` |
|---|---|---|
| 时机 | 模板构建（`Role.Builder.addComponent`）| 实例装配（`awake()`）|
| 读什么 | 描述符**快照** | 描述符读口 |
| 越界 | `IllegalArgumentException("Slot must be between 0 and 8, got: N")` | ★ **逐字相同** |
| 冲突 | `IllegalArgumentException("Slot N is already occupied by 'X'.")` | ★ **同类型 + 同主句**，仅**追加**分句点名"谁被拒" |

★ **为什么两处都留**（不是纯重复）：① 拦"模板写错"（那时没有实例）；② 拦"运行期登记错"，
且 **① 覆盖不到动态添加**（`ComponentLookup#add/insertAt` 不经装配器）、**② 覆盖不到模板构建期**。
两者互为补集 ✓。冻结主句**一字未动** ⇒ 既有逐字断言不受影响。

### 6.5 两种"敌对"判定：**非对称**，方向由形参顺序表达（★ 2026 语义变更）

|---|---|---|
| `isHostileTo(UUID target)` | **我**是否与 target 敌对（**target = 目标方**）| `FactionLookup#isHostile(Faction, UUID)` |
| `isHostile(UUID first, UUID second)` | **first 是否视 second 为敌人**（**first = 发起方，second = 目标方**）| `FactionLookup#isHostile(UUID, UUID)` |

★ **区分点 = 参数个数**。两处的 `Player` 支都已 `@Deprecated`（**保留、纯委托**，
`victim.getUniqueId()` → UUID 版 ⇒ 语义在编译期就等价）。

★ **两法不再同值**（旧口径下 `isHostile(a,b) == isHostile(b,a)` 是硬约束，现已作废）：
"在场"那一维**只读目标方**，因此合成判定非对称。
`FactionRelationTest` 锁的仍是**阵营维度**的对称性（那一维未变），
**合成层**的对称性由 `HostilityTest#noLongerSymmetric` 明确断言为"不对称"。

**判敌口径（三条规则，同阵营优先）** —— 真值 = `platform/Hostility.java`（纯静态、可离线测）：

| # | 规则 | 落点 |
|---|---|---|
| ① | **同阵营 ⇒ 任何情况下非敌对**（最高优先级）| `FactionRelation` |
| ② | **对方是创造 / 旁观 ⇒ 非敌对** | `Hostility#isHostileTo` 首行 |
| ③ | **其余 ⇒ 敌对**（含"任一方没有角色"）| `FactionRelation` |

★ **发起方自己是否在场不参与判定**（旧口径"己方不在场 ⇒ 一律不敌对"那道闸门已从
`RoleInfoImpl#isHostileTo` 删除）。现实现里 `Hostility#isHostileTo` **根本没有 selfInPlay 形参** ——
这不是遗漏，是"己方在场不参与"的类型化表达。

### 6.6 ★★ 家族描述符必须**泛型化**，否则 `requires(具体组件.class)` **永不满足**

```java
// 三个家族基类（现状）
public abstract static class Specification<S extends Skill>        extends HotbarSpecification<S> { … }
public abstract static class Specification<M extends MainWeapon>   extends HotbarSpecification<M> { … }
public abstract static class Specification<P extends PassiveSkill> extends RoleComponent.Specification<P> { … }

// 具体组件的嵌套描述符 —— ★ 必须把"自己"传上来
public static final class Specification extends Skill.Specification<MySkill> {
    @Override public MySkill create(String id, ComponentServices services) { … }   // ★ 协变返回【具体类型】
}
```

**为什么**：`providedType()` 的落点 `Specification#deriveProvidedType()` 沿 `getClass()` 链找
**第一个** `...Specification<X>` 的泛型实参。

- 家族基类若写死 `<Skill>` ⇒ 具体组件的推导结果是 **`Skill.class`（族级）**
  ⇒ 别的组件写 `requires(某具体技能.class)` **永远不满足**（装配期报「缺必需依赖」）；
- 泛型化 + **协变返回**之后，推导结果 = **具体组件类** ✓

★ **实测事故**：`CangluTraumaMainWeapon` 声明 `requires(CangluHysteriaPassive.class)`，
而后者的 `providedType()` 推导成 `PassiveSkill.class`
⇒ 角色 `canglu` **整个装配失败、不进注册表**（日志：`requires missing component type '…CangluHysteriaPassive'`）。
★ 内建组件没这问题 —— 它们的 `Specification` 直接继承 `RoleComponent.Specification<EnergyComponent>`
这类**具体**实参。

★ **新写组件的检查项**：`extends Xxx.Specification<`**你自己的类名**`>`，
且 `create(...)` 的返回类型是**你自己的类**（不是家族基类）。
