# 架构与组件模型

> **本目录只放架构文档。** 组件写法与玩法数值等不由本目录负责。
> 
> **对应时点**：制品代 `261B7E6D…`（归档登记 16）；源码基线 = 提交 `f93831a` 及其后的工作树改动。


这份文档写给**准备改这个插件的开发者**。读完它你能回答：一个角色从"模板"到"玩家身上的实例"经过哪些对象；一个技能被触发时经过哪条链路；组件能碰什么、不能碰什么；热键栏是谁在什么时候写的；清除角色时框架会回收哪些东西。

> 只用「文件 + 符号」定位代码，不写行号。
> 组件层的写法（怎么写一个新组件）不在本文覆盖范围 —— 本文只负责架构。

## 总览

```
装配期（插件启用，一次）
  ShadowHunterRolesPlugin.onEnable
    ├─ saveDefaultConfig()                            数据目录里没有 config.yml 时写一份内置默认
    ├─ ConfigurationManager.install(new ConfigurationManager(plugin)) 配置的唯一读盘入口
    ├─ KeyFactory.Registry.install(keys)              名字空间唯一来源
    ├─ new RolesContext(plugin, logger, scheduler, keys, factions)
    ├─ new RoleRegistry()                            角色模板容器（纯容器）
    ├─ new RoleLoader(getLogger()).loadInto(registry) 逐条装配角色模板（每条登记一个描述符）
    ├─ new RoleManager(rolesContext, roleRegistry)
    ├─ getCommand("role").setExecutor(new RoleCommand(...))
    ├─ registerEvents(5 个 listener)
    └─ ServicesManager.register(RoleAPI.class, RoleAPIImpl)

运行期
  角色模板层   Role（数据 + 组件装配条目（kind + 栏位 + 工厂）+ 派生栏位视图）  core/Role
       ▼       RoleRegistry（纯容器，无静态状态）      registry/RoleRegistry
       ▼       RoleLoader（显式装配，按角色隔离失败）  registry/RoleLoader

  实例层       RoleManager（UUID → RoleInstance）     manager/RoleManager
       ▼       RoleInstance（聚合根）
       │         ├─ ComponentRegistry（组件集合 + 每组件资源表 + 查找）
       │         ├─ HotbarRenderer（唯一渲染者）
       │         ├─ BuffManager（控制效果计时 + 闸门）
       │         └─ 10 个端口适配器 → ComponentServices
       ▼
  组件层       RoleComponent（基类：svc + 5 个钩子 + getComponent）
                 │           + 按需实现的能力接口（能进热键栏 / 能被施放 / 能参与攻击 / …）
                 │           + 装配期描述符 RoleComponent.Specification（怎么造它 + 占不占栏位）
                 ├─ PassiveSkill   → 被动组件   （可选便利基类；描述符无栏位）
                 └─ ActiveComponent ─┬─ Skill      → 技能组件   （可选便利基类；描述符带栏位）
                                     └─ MainWeapon → 主武器组件（可选便利基类；描述符带栏位）

  装配入口     Role.Builder.addComponent（三种写法：描述符 / 工厂+栏位+kind / 工厂+kind）
```

| 层 | 关键类型 | 职责 |
|---|---|---|
| 模板 | `core/Role` | 存 id / 显示名 / 描述 / `maxHP` / `baseATK` / `maxEnergy` / `maxSanTE` / 阵营 / 图标 / 组件装配条目；栏位归属在条目里（**随组件走**）；`getSlotMap()` 是构造期**派生**的视图、`componentIdAtSlot(int)` 按栏位取 id；`createInstance` 造实例 |
| 容器 | `registry/RoleRegistry` | 纯容器：实例字段 `LinkedHashMap`，只有 `register` / `get` / `contains` / `ids` / `all` / `size` / `isEmpty`，没有静态块、没有静态 Map |
| 装配 | `registry/RoleLoader` | 两条 `Definition`；逐条 `build()` + `register()`；每个组件以**描述符**登记（`new <组件>.Specification().setSlot(n)`）；单个角色失败只跳过它并记 `SEVERE` |
| 持有 | `manager/RoleManager` | `Map<UUID, RoleInstance>`；`selectRole` / `clearRole` / `hasRole` / `getRoleInstance` / `areHostile` / `clearAllPlayersRole` |
| 聚合根 | `core/RoleInstance` | 真值持有（能量 / SanTE / 生命 / 阵营 / 冷却 / 控制效果）+ 组件集合 + 每刻广播 + 渲染置脏与帧末重绘 + 资源回收 |
| 组件基类 | `roleComponent/RoleComponent` | `svc` 字段 + 5 个 default 钩子 + `getComponent(Class)` + 嵌套的**装配期描述符** `Specification<T>`（含不可变快照 `Snapshot`） |
| 能力接口 | `core/hotbar/HotbarPresentable`、`core/hotbar/HotbarItem`、`core/hotbar/CooldownBearing`、`core/hotbar/EnergyCosting`、`core/hotbar/CooldownAware`、`core/dispatch/HotbarActionable`、`core/dispatch/CombatHook` | 编译期能力：能进热键栏（表现规格 + 基础物品） / 有冷却 / 耗能量 / 关心冷却结束 / 能被施放 / 能参与攻击；**按需实现，不必靠继承获得** |
| 表现规格 | `core/hotbar/HotbarSpecification` | **表现规格 + 带栏位描述符合一**：一个组件的表现字段（显示名 / 描述 / 图标 / 冷却 / 能量消耗 / 种类）收成一个不可变对象，同时承担"怎么造这个组件"与"栏位"（`setSlot`）；旧短名 `HotbarSpec` 保留为 `@Deprecated` 别名 |
| 配置 | `config/ConfigurationManager`、`config/ConfigKey` | 配置的**唯一读盘入口**：类型化取值 + 缺失/非法安全回落 + 越界夹取 + TTL 与文件戳失效；键的路径/默认值/域/说明集中在 `ConfigKey` |

## `ComponentServices`：组件的唯一平台入口

`core/ports/ComponentServices` 是一个 record，**恰好 10 个成员**：

```java
record ComponentServices(Self self, EnergyPort energy, SanTEPort sante, VitalsPort vitals,
                         CooldownPort cooldowns, BuffPort buffs, FactionPort factions,
                         DamagePort damage, TimerPort timers, ComponentLookup components)
```

它由容器在**构造组件的同时**注入（`RoleInstance.createServices` 构造服务集 → `Role.createComponent` 经 `ComponentFactory.create(id, services)` 交给组件构造函数），字段是 `final`，不存在"先创建、后注入"的中间态。

| # | 成员 | 方法白名单 | 适配器 | 语义要点 |
|---|---|---|---|---|
| 1 | `self` | `player()`、`id()` | `core/SelfImpl` | 本组件依附的玩家，**每次现取、不缓存** |
| 2 | `energy` | `current()`、`tryConsume(int)`、`gain(int)` | `core/EnergyPortImpl` | 能量真值；`tryConsume` 把判断与扣减合成一步，`amount <= 0` 直接成功 |
| 3 | `sante` | `gain(int)`、`decrease(int)`、`set(int)`、`current()`、`max()` | `core/SanTEPortImpl` | SanTE 真值，所有写入都经这里 |
| 4 | `vitals` | `heal(double)` | `core/VitalsPortImpl` | 生命；不会超过当前最大生命 |
| 5 | `cooldowns` | `isReady()`、`remainingTicks()`、`start(int)`、`end()` | `core/CooldownPortImpl` | 冷却；**构造期已绑定本组件 id 与种类**，组件不再传 id |
| 6 | `buffs` | `canCastSkill()`、`canUseMainWeapon()`、`add(BuffType,int)`、`has(BuffType)`、`remainingTicks(BuffType)`，以及两个重载 `applyPotionEffect(...)` | `core/BuffPortImpl` | 闸门 + 本系统药水的**唯一施加入口**；两个重载分别对应默认标志与自定义 `ambient` / `particles` |
| 7 | `factions` | `isHostile(Player)`、`faction()`、`hasEnemyInRange(double)` | `core/FactionPortImpl` | 阵营与敌对判定；未选角色的玩家算敌人 |
| 8 | `damage` | `trueDamage(...)` 两个重载、`physicalDamage(...)` 两个重载 | `core/DamagePortImpl` | 伤害原语，带击退的重载多一个参数；**伤害来源允许为 `null`** |
| 9 | `timers` | `run(Runnable)`、`runLater(long,Runnable)`、`runRepeating(long,long,Runnable)`、`track(Task)` | `core/TimerPortImpl` | 任务**创建即登记**进本组件的资源表，`stop()` 返回后由框架兜底取消 |
| 10 | `components` | `get(Class<T>)` | `core/ComponentLookupImpl` | 组件查找；未注册返回 `null`，注册表冻结前调用抛 `IllegalStateException` |

**纪律**：

- **一个方法都不许多用**：要加端口方法，先改 `ComponentServices` 与对应接口（这是一个需要明确决策的改动，不要顺手加）。
- 适配器一律包级私有，只持有 `RoleInstance` 反向引用；**不允许 `RoleInstance` 直接实现端口接口**，否则组件可以用 `(RoleInstance) svc.energy()` 拿回聚合根。
- 组件不能读角色模板数据（`maxHP` / `baseATK` 之类）—— 端口里没有这条通道。

## 组件模型与生命周期

### 基类 `RoleComponent`

`roleComponent/RoleComponent` 里只允许出现三样东西：`svc` 字段、钩子方法、`getComponent`。任何"顺手加个 helper"都越界 —— 那属于端口或组件私有方法的职责。

**5 个 default 钩子，由容器无条件广播给注册表里的全部组件**：

| 钩子 | 语义 |
|---|---|
| `awake()` | 装配阶段：解析跨组件依赖并缓存引用。**幂等**，不得改动任何玩家可见状态 |
| `start()` | 开始生效：初始化数据、发放装备、登记定时器 |
| `stop()` | 停止生效：**与 `start()` 严格对称**；返回后框架还会兜底回收本组件登记的资源 |
| `update()` | 每刻（20 Hz）。禁止阻塞，**禁止直接写热键栏**（渲染是框架的职责） |
| `onSanTEChange(int pre, int now)` | **事件钩子**，不是每刻广播：只在 SanTE 真变化时通知（`pre == now` 不通知） |

### 三个可选的便利基类

新组件**不必**继承它们：只要 `extends RoleComponent`、再按需要实现能力接口就能登记（`Role.Builder.addComponent` 的工厂形参是 `ComponentFactory<? extends RoleComponent>`）。这三个类只是"照抄起来最短"的现成组合，它们**没有删除**，现有组件全部走这条便利路径。

| 类型 | 形态 | 结果 |
|---|---|---|
| `PassiveSkill` | `extends RoleComponent`，只保留显示名与描述 | 被动**不实现** `HotbarItem` / `HotbarActionable` ⇒ "能不能被施放"是编译期事实 |
| `ActiveComponent` | `extends RoleComponent implements HotbarItem, HotbarActionable, HotbarPresentable, CooldownAware`：把构造参数装进一个 `HotbarSpecification` 并实现 `specification()` | 提供默认 `onCast`（不做事也不进冷却）；`onCooldownEnd` 的默认空实现来自能力接口 `CooldownAware` |
| `Skill` / `MainWeapon` | 分别 `extends ActiveComponent`；两者的**装配期描述符**是各自的嵌套 `Specification`（带栏位） | 主武器描述符恒传能量消耗 0 ⇒ 永远不会进入"能量不足"状态 |

三个基类的**描述符**见「装配期描述符与栏位」一节（`PassiveSkill` 的描述符不带栏位，`Skill` / `MainWeapon` 的带栏位）。

### 能力接口与「一个实现点」

`HotbarPresentable` 把"能进热键栏"收敛成**一个实现点**：

```java
public interface HotbarPresentable extends HotbarItem, CooldownBearing, EnergyCosting {

    /** 唯一实现点：表现规格（组件自己的描述符）。 */
    HotbarSpecification<?> specification();

    default String getId() { return specification().getId(); }      // 其余访问器全部是 default

    /** 基础物品：委托给同一处；状态装饰仍由框架施加。 */
    default ItemStack baseItem(String id) { return specification().baseItem(id); }
}
```

- 组件只写 `specification()` —— 返回**自己的描述符**（组件自带的嵌套 `Specification`，表现字段在它的构造函数里给默认值；id 属于注册处，由装配入口 `bindId` 绑进描述符）；`getId` / `getDisplayName` / `getDescription` / `getIcon` / `getCooldownTicks` / `getEnergyCost` / `getKind` 七个访问器由接口的 `default` 方法代劳，组件**不写任何委托**。旧短名 `spec()` 保留为 `@Deprecated` 别名（同一个值，没有第二套实现）。
- `CooldownBearing` / `EnergyCosting` 把"有冷却"与"耗能量"抽成可以单独实现的能力；`HotbarPresentable` 继承这两个接口，所以只写 `specification()` 的组件天然满足三者。
- `HotbarItem` 是**渲染器读写面**（七个表现 getter + `baseItem(String)`）；`HotbarPresentable.asHotbarItem()` 直接返回描述符视图，容器侧由 `RoleInstance.hotbarItemOf(String)` 优先走它。
- **能力可以自由组合**：例如"能被按键施放、又能参与攻击结算、还想在冷却结束时收尾自己"的组件，今天可以只写 `extends RoleComponent implements HotbarActionable, CombatHook, CooldownAware`（不继承 `Skill` / `MainWeapon`）。（该组合的完整可编译骨架见组件源码。）
- 派发点判的都是**能力接口**，不是继承关系：**施放入口** `RoleInstance.handleCast` 判 `HotbarActionable`，**攻击入口** `RoleInstance.handleAttack` 判 `CombatHook`，**冷却结束回调** `RoleInstance.dispatchCooldownEnd` 判 `CooldownAware` ⇒「不必继承、按需实现能力」在派发面同样成立（`ActiveComponent` 已实现这三个接口，所以继承 `Skill` / `MainWeapon` 的组件行为不变）。

### 权威 kind 在注册处

`ItemKind` 有三个值：`SKILL`（技能）、`MAIN_WEAPON`（主武器）、`PASSIVE`（被动）。**权威 kind 来自装配期描述符、落在注册处的装配条目里**：`Role.Builder.addComponent(String, Specification<?>)` 从描述符取 `kind()` 存进 `Role.ComponentEntry`，框架侧的行为分支（冷却表 / 能力闸门 / 持久化键 / 文案表）一律读 `Role.componentKindOf(String)` 或条目里的 kind。

为什么不在**组件实例**上读它：**服务集先于组件构造**，而服务集里就带着 kind —— `RoleInstance.createServices(String componentId, ItemKind kind)` 在组件被创建之前构造冷却端口，`CooldownPortImpl(RoleInstance owner, String componentId, ItemKind kind)` 在构造期绑定 kind；而 `ComponentFactory.create(String id, ComponentServices services)` **只给 id 与服务集、不给 kind** ⇒ 组件实例在构造期无从得知权威 kind。描述符能读到 kind（`Specification.kind()`），但它是**装配期的声明**、不是组件实例的字段；组件侧 `specification().getKind()` 读到的只是表现值。

被动（`PASSIVE`）的两处差异：不占栏位（描述符类型上就没有 `setSlot`；条目没有栏位值；渲染器另有显式跳过分支）；冷却端口对它是**无声语义**（恒就绪 / 剩余 0 / 不写任何表 / `end()` 恒 `false`，见 `core/CooldownPortImpl`）。

### 启停机制（只有一套）

组件启停 = **容器对全部已注册组件无条件广播** `awake()` / `start()` / `stop()` / `update()`。没有"按类型分流"，也没有任何"是否已迁到新写法"的标记。

**广播顺序 = 注册序**：`Role.Builder` 里 `addComponent` 的调用顺序（角色模板的组件表 `Role.getComponents()` 是有序表），容器只遍历它一次。**不再**按"技能 → 被动 → 主武器"分组，所以同一刻里两个组件都写同一个数值时，先后由注册顺序决定。

广播与回收的固定顺序（`core/RoleInstance`）：

| 顺序 | 动作 | 语义 |
|---|---|---|
| 1 | `component.awake()` | 解析跨组件依赖（幂等） |
| 2 | `component.start()` | 开始生效 |
| 3 | `component.stop()` | 停止生效，**在框架兜底回收之前** |
| 4 | `componentRegistry.cancelAllAndClear()` | 框架兜底取消各组件资源表里的任务 |

组件即使在 `stop()` 里自己取消了任务，第 4 步仍会清空它的资源表 —— 重复取消是幂等的，不会双触发同一段逻辑。

### 一个角色实例的装配顺序

`RoleInstance` 构造函数依次做：初始化能量与 SanTE 为满值 → 按**注册序**逐个创建全部组件（`Role.createComponent` 是唯一的组件创建点，它经 `ComponentFactory.create(id, services)` 在构造期注入服务集；权威 kind 随条目从注册处取出）→ **冻结组件注册表**（此后 `getComponent` 才合法）→ 建 `BuffManager` → 挂最大生命修饰符并回满血 → 广播 `awake()` → 广播 `start()` → 启动每刻（1 刻周期）的 ticker → **同步重绘一次热键栏**（保证选角色的瞬间图标就位）。

## 装配期描述符与栏位

组件的"怎么造"与"占不占热键栏"不再是**工厂 + 数值哨兵**，而是一个**有类型的声明**：`roleComponent/RoleComponent.Specification<T>`。

| 描述符成员 | 语义 |
|---|---|
| `kind()` | 权威种类；**在 `create(id, services)` 之前即可读**（服务集在组件被构造**之前**就要它） |
| `hasSlot()` / `slot()` | 占不占栏位；**"不占栏位"是栏位的缺失**（内部用可空 `Integer` 表达），未设栏位时 `slot()` **抛异常**，不回落 `-1` |
| `bindId(String)` / `boundId()` | 装配期绑定**注册 id**（与栏位同属"必须由装配器设置"的参数）；绑定到另一个 id、或已冻结后再绑都抛异常 |
| `freeze()` | 装配期冻结：产出**不可变快照** `Specification.Snapshot`（`kind` + 栏位 + 工厂），此后描述符自身也拒绝再改 |
| `create(String, ComponentServices)` | 抽象创建：由**具体描述符**决定造哪个组件类 |

**规则进类型**（栏位由描述符的**类型**表达，不靠装配点自觉）：

| 描述符 | 类型面 | 结果 |
|---|---|---|
| `core/hotbar/HotbarSpecification<T>` | `extends RoleComponent.Specification<T> implements HotbarItem`，有 `setSlot(int)`，`requiresSlot()` = `true` | **带栏位**那一支：装配期未设栏位 ⇒ `freeze()` 抛异常；它的默认 `create(...)` 是 fail-fast（抛 `UnsupportedOperationException`），裸描述符造不出语义不明的组件 |
| `Skill.Specification` / `MainWeapon.Specification` | 分别 `extends HotbarSpecification<Skill>` / `HotbarSpecification<MainWeapon>`；构造函数给出各自的默认表现值（主武器恒传能量消耗 0），`create(...)` 保留**抽象** | 具体组件必须声明自己的嵌套描述符并实现 `create` ⇒ 漏写是**编译错误**，不是运行期惊喜 |
| `PassiveSkill.Specification` | `extends RoleComponent.Specification<PassiveSkill>`（**继承根类型**） | **没有** `setSlot`、也没有表现面 ⇒「被动不占热键栏」成为**编译期事实** |

**装配与栏位的落点**（`core/Role`）：

- `Role.Builder.addComponent(String, Specification<?>)`：吃一个描述符，先 `bindId(id)` 再 `freeze()`；条目只留 `(kind, 栏位, 工厂)` ⇒ 角色模板**不持有描述符对象**，同一份描述符实例被两个角色共享也互不影响。
- 另外两个重载 `addComponent(id, 工厂, 栏位, kind)` / `addComponent(id, 工厂, kind)`，以及三个已标 `@Deprecated` 的别名（`addSkill` / `addMainWeapon` / `addPassive`），都映射到**同一条内部路径** `Role.Builder.addComponentInternal`；栏位在内部用可空 `Integer` 表示（`null` = 不占栏位）——**`-1` 哨兵已删除**。
- **栏位随组件走**：`Role` 不再维护栏位归属，装配条目 `Role.ComponentEntry` 自带 `hasSlot()` / `getSlot()`（无栏位时 `getSlot()` 抛异常）。`Role.getSlotMap()` 是构造期**一次性派生**的视图（签名与语义不变），另有 `Role.componentIdAtSlot(int)` 按栏位取 id；重复栏位的校验改为**扫组件表**（异常类型与文案不变）。
- `registry/RoleLoader` 的登记形态随之变成 `addComponent(id, new <组件>.Specification().setSlot(n))`；**登记顺序 = 注册序**（派发序与渲染序都看它）。

## 施放管道

### 触发来源

监听器把原版事件翻译成"施放 / 攻击"，再交给聚合根：

| 玩家动作 | 监听器 | 聚合根入口 | 组件收到的回调 |
|---|---|---|---|
| 手持技能物品右键 | `listener/SkillListener.onPlayerRightClickSkillItem` | `RoleInstance.castSkillRightClick` | `onCast`（`CastTrigger.RIGHT_CLICK`） |
| 手持技能物品左键 | `SkillListener.onPlayerLeftClickSkillItem` | `castSkillLeftClick` | `onCast`（`LEFT_CLICK`） |
| 手持技能物品按 `Q` | `SkillListener.onPlayerQDropSkillItem` | `castSkillQDrop` | `onCast`（`DROP`） |
| 手持主武器左键 / 右键 / `Q` | `listener/MainWeaponListener` | `castMainWeaponLeftClick` / `...RightClick` / `...QDrop` | `onCast`（对应的触发来源） |
| 手持主武器攻击玩家 | `MainWeaponListener.onAttackPlayer` | `RoleInstance.handleAttack` | `onAttack(AttackSignal)` |

这几个入口最终都汇到 `RoleInstance.runComponentPipeline`，它是**纯委派**（没有任何开关或标记）：按手持物品里的 id 找到组件，实现 `HotbarActionable` 就调 `onCast`，实现 `CombatHook` 就调 `onAttack`。信号对象只带这一次的数据：`CastSignal(trigger)`、`AttackSignal(victim)`；施动者永远是 `svc().self().player()`。

### 结果语言 `CastResult`

`core/dispatch/CastResult`：

| 值 | 语义 |
|---|---|
| `SUCCEED` | 施放成功（**只表示成功**，不隐含任何框架动作） |
| `NO_COOLDOWN` | 组件自己处理过了（含"这次什么都不做"），框架不呈现任何反馈 |
| `REJECTED_DISABLED` | 被沉默 / 眩晕禁用 |
| `REJECTED_NO_ENERGY` | 能量不足 |

### 冷却由组件自己启动

框架**不**代启动冷却：组件在施放成功处显式调用 `svc().cooldowns().start(getCooldownTicks())`。声明值（构造时传入的冷却）仍是唯一真值来源，组件通常直接把它传进去。

- `start(int)` = **重启语义**：按本次调用时刻重算到期，覆盖旧值；旧段未走完则先清条目并回调 `RESTARTED`。
- `end()` = **真实语义**：在冷却中 ⇒ 清条目、回调 `ENDED_BY_COMPONENT`、刷新可见状态、返回 `true`；不在冷却中 ⇒ 返回 `false`、无副作用。
- 到期：`RoleInstance.scanCooldowns` 每刻扫描，移除条目并回调 `EXPIRED`。
- 组件的收尾钩子：`CooldownAware.onCooldownEnd(CooldownAware.CooldownEndReason)` —— 钩子与枚举都挂在能力接口 `core/hotbar/CooldownAware` 上（默认空实现），枚举值 `EXPIRED` / `ENDED_BY_COMPONENT` / `RESTARTED`。派发点 `RoleInstance.dispatchCooldownEnd` 判的就是这个接口：`ActiveComponent` 已 `implements CooldownAware` ⇒ 继承 `Skill` / `MainWeapon` 的组件照旧收到回调；只 `extends RoleComponent` 的组件要自己 `implements CooldownAware`。回调在条目移除之后派发，所以回调里再 `end()` 只会得到 `false`，不会递归重入。

## 渲染契约

**唯一渲染者 = `core/hotbar/HotbarRenderer`**：全插件只有 `HotbarRenderer.render()` 里那一次槽位写入会创建物品（全仓 `setItem(` 共 3 处 = 本渲染器的这一次 + 清栏的两处）。`RoleInstance` 只提供查表与状态输入（`hotbarItemOf`、`isSkillReady`、`getCurrentEnergy`、`getBuffManager` 等）。

- 能进热键栏的组件实现 `HotbarPresentable`（它继承 `HotbarItem` / `CooldownBearing` / `EnergyCosting`）：组件只写**一个实现点** `specification()`，返回自己的 `HotbarSpecification`；`getId` / `getDisplayName` / `getDescription` / `getIcon` / `getCooldownTicks` / `getEnergyCost` / `getKind` 七个无参 getter 与 `baseItem(String)` 都由接口的 `default` 方法委托给它，组件不必手写。容器用 `RoleInstance.hotbarItemOf(String)` 取这个读写面（优先走 `asHotbarItem()`），`HotbarItem` 本身保留。
- `HotbarRenderer.render()` **按注册序遍历 `Role.getComponents()`**（有序表 = 装配调用序）：不带栏位的条目跳过，带栏位者取**条目里的栏位值**落位。栏位归属随组件自己的描述符走 ⇒ 渲染器不再读 `Role.getSlotMap()`（那张表是派生视图）；每个栏位至多被写一次（装配期已禁止重复栏位）⇒ 落位结果与旧实现逐格相同，且「注册序 = 渲染序」在代码上直接可见。`kind` 一律取条目里的权威值，被动（`PASSIVE`）即使带栏位也被显式跳过。
- **基础物品由组件提供，状态装饰仍归框架**：`HotbarItem.baseItem(String id)`（默认实现在 `HotbarSpecification`：图标 + 显示名 + 单行描述；**不写持久化标记、不定状态**）给出物品底稿；`HotbarRenderer.buildIcon(id, item, kind)` 在它之上施加**状态装饰** —— 三态材质覆盖（就绪态沿用基础物品的材质）、名称颜色与加粗、冷却秒数或 `DISABLED` / `ENERGY LACK` 后缀、状态行 lore、分隔线、两个持久化键。组件覆写 `baseItem` 只影响底稿，**碰不到这些冻结面**；`id` 由渲染器显式传入（描述符自带的 id 由装配入口绑定，见 `RoleComponent.Specification.bindId`）。
- 状态判定：`HotbarRenderer.stateOf(ready, canCast, energy, energyCost)`，顺序固定为 **冷却 → 被禁用 → 能量不足 → 就绪**。主武器 `energyCost` 恒为 0（能量也不会为负）⇒ 永不进入"能量不足"。
- 材质与文案：就绪用**基础物品**的材质、绿色加粗；被禁用 `BARRIER`、红色加粗 + ` DISABLED`；冷却中与能量不足都用 `STRUCTURE_VOID`，灰色加粗；**技能**冷却名追加 ` x.xs` 秒数（秒数只在这一处格式化），**主武器不追加**。
- 物品都带持久化标记：技能是 `Skill.Utils.SKILL_KEY`（`skill_id`），主武器是 `MainWeapon.Utils.MAIN_WEAPON_KEY`（`main_weapon_id`），值是组件 id。监听器据此识别物品并拦截丢弃 / 容器点击。

### 置脏与帧末重绘

刷新不是"每刻轮询比较"，而是**置脏 + 每刻末尾统一重绘**：

- **置脏来源**（框架内部调用 `HotbarRenderer.markDirty()`）：施放（`RoleInstance.handleCast`）、攻击（`handleAttack`）、能量变化（`setCurrentEnergy`）、启动冷却（`CooldownPortImpl.start`）、控制效果移除（`manager/BuffManager.removeBuff`）、冷却到期扫描（`RoleInstance.scanCooldowns`）、显式结束冷却（`RoleInstance.endCooldown`）。其中"程序化"的三条路径（冷却到期、预约刷新、显式结束）共用一个方法引用 `hotbarRenderer::markDirty`（`RoleInstance` 里的 `markHotbarDirty`）。
- **预约刷新**：启动冷却时同时预约"剩余时长后再置脏一次"（`runLater(markHotbarDirty, remaining)`），保证冷却结束时图标立刻恢复。
- **帧末重绘**：`RoleInstance.triggerUpdate` 的顺序是 —— 广播组件 `update()` → `scanCooldowns()` → **判脏**（`isDirty()`）→ `render()` → `clearDirty()`。三段顺序不可交换。
- **入口条件**：`isDirty() || hasCoolingSkill()`。`hasCoolingSkill()` 只数技能，作用是让"冷却中每刻至少刷一次"，技能名上的秒数才会逐刻递减；空闲刻一次物品写入都不会发生。
- `clearDirty()` 的**唯一消费者是帧末重绘**：组件、端口、渲染器内部都不得调用，否则会吞掉本次可见更新。
- 组件侧没有任何置脏通道（也没有 `HotbarPort`）：组件只声明图标 / 显示名 / 描述，状态变化由框架在五个触点自动置脏。

## 资源回收与清除角色

`core/dispatch/ComponentRegistry` 负责组件集合、每组件资源表（组件 → 任务列表）与查找：

- `register` 只允许在 `freeze()` 之前；`get(Class)` / `getById(String)` 在冻结前调用会抛 `IllegalStateException`，把"过早查询"变成响亮的错误；
- `track(component, task)` 登记任务；`cancelAll(component)` / `cancelAllAndClear()` 在 `stop()` 返回后兜底取消。

`RoleInstance.clear()` 的顺序：广播 `stop()` → 兜底取消全部登记任务 → 取消每刻 ticker → 清空热键栏（0–8 号位中带技能 / 主武器标记的物品）→ 移除最大生命修饰符 → **只移除记账过的药水效果** → 清空控制效果 → 清空两张冷却表。

触发清除的入口：`/role clear`、死亡、掉线、换角色（`RoleManager.selectRole` 先清旧角色）、插件卸载（`RoleManager.clearAllPlayersRole`）。

## 平台层与对外接口

`platform/` 是领域层与组件层**唯一**接触服务端 API 的地方（取代插件主类单例）：

| 类型 | 形态 | 职责 |
|---|---|---|
| `platform/RolesContext` | record `(Plugin plugin, Logger logger, Scheduler scheduler, KeyFactory keys, FactionLookup factions)` | 平台能力五元组；由主类在 `onEnable` 构造并注入 `RoleManager` → `RoleInstance` |
| `platform/Scheduler` | `run` / `runLater` / `runRepeating` | 调度端口 |
| `platform/BukkitSchedulerAdapter` | 唯一实现 | 包装 Paper 提供的 `GlobalRegionScheduler` 的 `run` / `runDelayed` / `runAtFixedRate`；`initialDelay <= 0` 归一为 1 |
| `platform/Task` | `cancel()` / `isCancelled()` | 调度句柄（不同调度 API 的返回类型不统一，这里统一包装） |
| `platform/KeyFactory` | 接口 + `Registry` 静态桥 | `NamespacedKey` 的唯一来源；四个公开常量（技能键、主武器键、最后伤害者键、眩晕减速修饰符键）需要在类初始化期取值，所以保留了这层静态桥；未安装时抛 `IllegalStateException` |
| `platform/FactionLookup` | 接口 + 主类里的匿名实现 | 按玩家查阵营；未选角色的玩家 → `UNKNOWN` |

**服务端基线是 Paper**：调度统一走 `GlobalRegionScheduler`，本插件不做 Folia 适配，也不预置 Folia 分支。

### 配置

配置子系统提供**唯一的读盘入口**（`config/ConfigurationManager` + `config/ConfigKey`）：

- **默认配置落盘**：主类 `onEnable` 先 `saveDefaultConfig()`（数据目录里没有 `config.yml` 时从 jar 内置默认值写一份；内置件是 `src/main/resources/config.yml`），随后 `ConfigurationManager.install(new ConfigurationManager(plugin))` 安装全局实例（静态桥，写法与 `KeyFactory.Registry` 同族；未安装时 `installed()` 返回 `null`）。
- **键的定义集中在一处**：路径 / 默认值 / 域 / 说明都在 `ConfigKey`（`ConfigKey.integer` / `ConfigKey.text` / `ConfigKey.bool` 三个工厂 + 解析结果 `ConfigKey.Resolution`）。现有键 `ConfigurationManager.COMMAND_PERMISSION_LEVEL`（路径 `command-permission-level`，默认 3，域 0-4）。
- **取值规则**：`ConfigurationManager.get(ConfigKey)` 是**永不抛异常**的类型化取值 —— 缺失 / 类型不符 / 非整数 / 文件读不动 ⇒ 回落默认值；数值越界 ⇒ 夹取到 `[min, max]`。
- **唯一的读盘入口**：文件存在时读数据目录那份（`YamlConfiguration.loadConfiguration(file)`），不存在时回落 `plugin.getConfig()`（jar 内置默认值）⇒ 调用方不再各自去读配置。
- **生效时效**：`ConfigurationManager.TTL_MILLIS` = 5000 ms + **文件戳（mtime×31+长度）变更即失效** ⇒ 改完配置文件**最迟一个 TTL** 内生效，**无需重启或 reload**。
- **可观测**：首次读到某键、以及因文件变更而重读导致取值变化时，各打一行含新旧值的 INFO（前缀 `[config]`）⇒ 运行期取到的是原始行。
- 消费方：`command/CommandAccess` 把"指令所需权限等级"的判定**委托**给 `ConfigurationManager.get(ConfigurationManager.COMMAND_PERMISSION_LEVEL)`（等级来源与拒绝文案见该类）。

**对外接口**：`api/RoleAPI` 在启用时注册进 Bukkit 服务表；实现类是 `internal/api/RoleAPIImpl`。它覆盖四类能力：

- 角色：`isValidRoleId` / `setPlayerRole` / `clearPlayerRole` / `getPlayerRoleId` / `hasRole` / `getRoleDisplayName` / `getRoleDescription` / `getRoleIcon` / `getAllRoleIds` / `getRoles`；
- 玩家数值：能量、SanTE、生命的读写与查询（`getPlayerEnergy` / `setPlayerEnergy` / `increaseEnergy` / `decreaseEnergy` / SanTE 与生命对应方法）。SanTE 的"没有角色"有两种表达：旧方法返回常量 `RoleAPI.NO_ROLE_SAN_TE_SENTINEL`（= -78），新增的 `getPlayerSanTEOptional(Player)` / `getPlayerSanTEOptional(UUID)` 返回**空 `OptionalInt`**；
- 冷却：`isSkillReady` / `getSkillCooldownTick`；
- 阵营与伤害来源：`getFaction` / `setFaction` / `resetFaction` / `areHostile` / `getLastDamagerUuid`。

`api/RoleInfo` 是只读快照 record：`(String id, Component displayName, List<Component> description, Material icon, Faction faction)`。

> 改 `RoleAPI` 的既有方法签名会破坏下游插件（`SHDFGamePlugin` 通过 `ServicesManager` 使用它）。原则是**只增不改**。

## 扩展点与硬性规则

### 扩展点

| 想做的事 | 落点 |
|---|---|
| 加技能 / 被动 / 主武器 | 新组件类（`roleComponent/<角色包>/...`）：`extends RoleComponent` 并按需实现能力接口（也可以直接用三个便利基类）+ 声明自己的嵌套**描述符**；在 `Role.Builder` 里用 `addComponent` 登记（带栏位的写法：`addComponent(id, new <组件>.Specification().setSlot(n))`） |
| 加角色 | `registry/RoleLoader` 里加一条 `Definition` 与一个 `Builder` 方法 |
| 改数值 | 组件自带描述符里的默认表现值、`RoleLoader` 里的角色数值、配置键（`config/ConfigKey`） |
| 给下游插件用 | `api/RoleAPI`（只增不改） |
| 加命令 | `command/` 包加一个 `SubCommand` 实现并在对应分发器里注册 |

### 硬性规则

1. **`ComponentServices` 恰好 10 个成员**，加成员要显式决策；
2. **组件 id 跨类型唯一**：技能 / 被动 / 主武器共用一个命名空间，重复注册会抛异常；
3. **栏位由描述符的类型表达**：带栏位的描述符（`HotbarSpecification` 一支）**必须**在装配期设过栏位（`setSlot`，`0..8`）—— 未设栏位、重复设成别的位置、冻结后再设、越界都抛异常；不带栏位的描述符（`PassiveSkill.Specification`）**没有** `setSlot` ⇒ 天然不占热键栏。**没有 `-1` 哨兵**：无栏位时 `slot()` 抛异常；
4. **角色数值必须合法**：`maxHP > 0`，`baseATK` / `maxEnergy` / `maxSanTE` ≥ 0，角色 id 非空；
5. **单个角色装配失败只影响它自己**：记 `SEVERE`、跳过该角色，其余角色照常注册；
6. **组件不许写热键栏**：组件只提供**基础物品**（`HotbarItem.baseItem`，不写持久化标记、不定状态）；三态材质、名称装饰、后缀、状态行 lore、分隔线与持久化键都归框架，组件不得请求刷新；
7. **组件不许拿插件主类单例**，也不许直接调服务端调度器，一律走 `svc()` 端口；
8. **有 `start` 必有对称的 `stop`**，`stop` 里把缓存的引用置空；
9. **玩家对象不放进长生命周期字段或长任务闭包**：存 `UUID`，或每次 `svc().self().player()` 现取；
10. **数值提成类顶部命名常量**（几何 / 特效参数除外）；
11. **不要"顺手改正" id 里的拼写**：`meiqihezi_equippments_passive`、`red_equippments_passive`、`autoRecoverSanTEPassive` 都是索引键；
12. **门面命名沿用 JavaBean 风格**：`getId()` / `getDisplayName()`，不要引入 record 风格访问器；
13. **装配只有一个内部路径**：`Role.Builder.addComponent` 三种写法（描述符 / 工厂+栏位+kind / 工厂+kind）与三个已标 `@Deprecated` 的别名（`addSkill` / `addMainWeapon` / `addPassive`）全部映射到 `Role.Builder.addComponentInternal` —— 校验、id 去重、栏位写入只有一处实现；描述符写法额外做 `bindId(id)` + `freeze()`。
