## 2. 目标语义（把用户要求翻成可判定条款）

| 语义 | 条款 |
|---|---|
| **S1 组件自管理** | 冷却的**启动**由**组件**发起（技能/主武器在施放成功处调用），框架**不再代劳** |
| **S2 开始冷却＝重复开启按新的来** | `start(ticks)`：以**本次调用时刻**为基准重算到期 tick ⇒ **覆盖旧值**（旧冷却被顶替，**不叠加、不取最大**）；若旧冷却**尚未到期**，必须让组件**可感知**（回调见 S4） |
| **S3 结束冷却＝真实语义** | `end()`：**仅当该组件处于冷却中**才生效；**清除条目**（**关闭 O-21**）＋ 触发回调 ＋ 需要一次可见刷新 |
| **S4 冷却中结束冷却可被处理** | 组件能收到"**我的冷却结束了**"的通知，并区分**原因**（自然到期 / 被显式结束 / 被重启顶替），从而收尾自己的状态（如前摇任务、连击计数） |
| **S5 查询** | 组件可查 `isReady()` / `remainingTicks()`（已有）——语义不变 ✓ |
| **S6 清理** | 角色销毁 ⇒ 冷却表清空（**已有** `:725/:726` ✓）；**销毁不回调**（组件同时在销毁，交由 `stop()` 负责） |

## 3. 关键设计决策（**需你拍板**）

### D1 框架是否继续自动启动冷却？
- **推荐 A：停止自动启动，改由组件显式 `start(getCooldownTicks())`** ✓
  - **等价性论证**：调用点（施放成功处）、调用值（同一 `getCooldownTicks()`）**完全一致** ⇒ **可观察行为不变** ✓；唯一差异 = **发起者**（框架→组件）。
  - 收益：与"组件自管理"的需求一致 ✓、消除"谁是真值"的隐性双轨 ✓。
- **否决 B：保留自动启动 + 组件可调整** ✗ —— 会造成**双真值/双路径**，与我们刚清理掉的迁移期架构同型 ✗。
- **影响**：`RoleInstance:184` / `:203` 两处调用**删除**；**约 12 个**返回 `SUCCEED` 的组件逐个补显式 `start` ✓（逐条给等价性对照 ✓）。

### D2 到期检测与清除由谁负责？
- **推荐：容器侧"冷却注册表"（单一扫描）** ✓
  - 到期 ⇒ **移除条目** ＋ 触发回调 ＋ 一次可见刷新；
  - `start` **不再排** `runLater`（F6/F7）✗ ⇒ 消除任务累积 ✓；
  - 顺带**关闭 O-21**（条目永不清除 ✗）✓。
- **扫描位置**：优先**复用既有每 tick 路径**（`triggerUpdate` → 组件 `update()` 之前/之后 ✓），**不新建独立 ticker** ✗（与 **t17** 划界 ✓）。

### D3 ⚠️ **可见刷新怎么换？（本规划最重要的顺序结论）**
- 现状：冷却到点靠 `runLater(this::updateHotbar, remaining)`（F6/F7）✓ 保证**到点那一刻刷一次** ✓。
- 若本项就把它换成 `markDirty()` ✗ ⇒ **可见刷新会丢** ✗✗ —— 因为 `HotbarRenderer` 目前是**骨架、无帧末 flush**（阶段 4 已登记的 **F1** ✓），`markDirty()` 今天**没有可见效果** ✗。
- ⇒ **结论：分两步** ✓
  1. **本项（第一步）**：只做 **API/语义**（`end()` 真实语义、回调、重启语义、注册表清除）＋ **保留**现有 `runLater(updateHotbar)` 刷新机制 ✓ ⇒ **零可见差异** ✓。
  2. **4.4 接管后（第二步）**：把刷新从 `runLater(updateHotbar)` 换成 `markDirty()` ✓（与 4.4 预案的接线清单合并 ✓）。
- ⇒ **本项与 4.4 的推荐顺序**：**先本项、后 4.4** ✓（本项不动渲染；4.4 一次性把刷新源收敛到 `markDirty` ✓）。

### D4 回调形状（满足 S4）
- 在 **`ActiveComponent`** 增加可选覆写钩子 ✓（被动不需要）：
  ```java
  public void onCooldownEnd(CooldownEndReason reason) { }   // 默认空实现
  public enum CooldownEndReason { EXPIRED, ENDED_BY_COMPONENT, RESTARTED }
  ```
- **语义**：`EXPIRED`＝自然到期 ✓；`ENDED_BY_COMPONENT`＝组件/外部显式 `end()` ✓（**正是"冷却中结束冷却"的情形** ✓）；`RESTARTED`＝在冷却中再次 `start` 顶替 ✓。
- **重入约束**（必须写死）：回调内**允许**再 `start`（例如"到点立刻接下一段"✓），但**禁止**在回调里同步递归触发自身回调 ⇒ 派发时**先移除条目再回调** ✓（保证不会因回调再次 `end()` 而重入）。

### D5 `CastResult` 的语义收敛（文档同步项）
- D1-A 之后：`SUCCEED` 仅表示"**施放成功**"（**不再**触发框架启动冷却 ✓）；`NO_COOLDOWN` 仍是"组件已自行处理、框架不呈现反馈" ✓。
- ⚠️ 必须同步活文档 ✗：任何"返回 `SUCCEED` 即由框架按声明值启动冷却"的表述都要改 ✓（否则属 **F1 同类"文档驱动的回归"** ✗）。

### D6 两张表是否合并？
- **建议：本项保持两张表** ✓（合并进单一冷却命名空间是**阶段 5** 的原计划 ✓）；本项只在两表上实现同一套语义 ✓。

## 4. API 草案（**签名级，不写实现**）

```java
public interface CooldownPort {
    boolean isReady();                 // 不变
    int     remainingTicks();          // 不变
    void    start(int ticks);          // S2：以本次时刻重算到期；重复开启=覆盖旧值；旧值未到期 ⇒ 回调 RESTARTED
    boolean end();                     // S3：在冷却中 ⇒ 清条目 + 回调 ENDED_BY_COMPONENT + 返回 true；否则 false（幂等、不报错）
}
```
- `boolean end()` 的返回值**供组件判断"我确实结束了一段冷却"** ✓（也可不用 ✓）。
- `ComponentServices` 白名单**不变**（`cooldowns()` 已在 10 成员内 ✓）。

**容器侧（实现说明，非代码）**：新增"冷却注册表"持有 `componentId → cooldownEndTick`（技能/武器各一张或按 kind 分派 ✓），提供 `start/end/isReady/remaining` 与 **tick 扫描**；`ActiveComponent` 增加 `onCooldownEnd(...)` 派发 ✓。

2. **零可见差异**（第一步）：`Mode B` 三行 + 正序集合差 **只看 `C`** ✓；数值/字符串**多重集**（路径无关值口径）：**无新增**（本项不引入新字面量：`enum` 名与回调名是标识符 ✓）✓；**刷新仍由 `runLater(updateHotbar)` 承担** ✓。

4. **运行期四态**（需真人）：冷却中 `end()` 后**立刻可再放** ✓；重启顶替后秒数**从新值重新倒数** ✓；到点后**物品恢复可放态** ✓；组件回调确实被调用（可用临时日志或既有表现间接观察 ✓）。

## 7. 风险（分级）

| 级 | 风险 | 处置 |
|---|---|---|
| **blocker** | 把刷新换成 `markDirty()` 而 4.4 未接管 ⇒ **可见刷新丢失** | **D3 分两步** ✓（第一步保留 `runLater(updateHotbar)`） |
