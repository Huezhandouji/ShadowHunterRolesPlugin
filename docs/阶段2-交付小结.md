## 3. `RoleManager` 去单例 + `areHostile` 迁移（2.5 / 2.3）

- **2.5 去掉静态单例**：`RoleManager` 的 `private static RoleManager instance` / `getInstance()` 全部删除，构造器改为 `public RoleManager(RolesContext context)`；主类在 `onEnable` 构造并持有（`ShadowHunterRolesPlugin.java:40`）。原调用点 `ShadowHunterRolesPlugin.java:25` 随之消失。
- **2.3 core 里的 `RoleManager.getInstance()` 归零**：`RoleInstance` 的 5 处（`:533,544,545,553,554`）分两路处理：
  - `isHostileTo(Player)`（`:533` → 新 `:507`）改走 **`platform.factions().isHostile(getFaction(), other)`** ✓ 与指南 2.3 一致；
  - 两个 **静态** `areHostile(Player,Player)` / `areHostile(UUID,UUID)`（`:542-558`）**移到 `RoleManager`**（新 `:73-88`），由 `RoleAPIImpl.areHostile(...)`（`:357`/`:361`）调用，实现体逐字保留（`getRoleInstance` + 任一为 null → true + `isHostileTo(ins2)`）。
- **与 2.3 字面表述的偏差（主动申报）**：`areHostile` 走的是 `RoleManager` 而不是 `FactionLookup`。理由：`FactionLookup` 的契约只收 `Player`，而 `areHostile(UUID,UUID)` 是**按 UUID 查实例**的公开重载（`RoleAPI` 对外暴露）；改走 `FactionLookup` 必须先 `Bukkit.getPlayer(uuid)`，在"离线即销毁"（§10 裁决 12）下虽然等价，但会**丢掉一条语义分支的显式表达**。移动实现到数据所有者（`RoleManager` 持有 `playerRoleMap`）既让 core 不再依赖单例，又逐字保留语义；`RoleAPI` 接口**未动**（只改了 `RoleAPIImpl` 的实现体）。
- **`SkillUtil.hasEnemyInRange` 语义并入 FactionLookup（2.3 的另一半）**：签名由 `(Faction selfFaction, Location, double)` 改为 **`(RoleInstance self, Location, double)`**，内部 `self.rolesContext().factions().isHostile(selfFaction, p)`。两处调用点（`AutoRecoverEnergyPassive.java:20`、`AutoRecoverSanTEHealthPassive.java:20`）改为传 `instance`。**语义等价**：原实现"对方无角色 → true；否则 `other.isHostileTo(selfFaction)`"，新实现由 `FactionLookup.isHostile` 覆盖同一真值表（自身 UNKNOWN → 恒 true；对方 UNKNOWN → true；都已知 → 阵营不同即 true）。

**为什么需要 `KeyFactory.Registry`（静态桥）**：这四个常量是 `static final`，值必须在**类初始化**时确定；而 `KeyFactory` 的实例在 `onEnable` 才存在。`Registry` 只暴露 `of(String)`，由主类在 `onEnable` 的**第一段**（`ShadowHunterRolesPlugin.java:37`）安装，**早于**任何可能触发这些常量初始化的代码路径（`RoleManager` 构造、`RoleRegistry` 静态注册、监听器注册）。若未安装即访问，会得到明确的 `IllegalStateException("KeyFactory is not installed yet (onEnable did not finish).")` 而不是 NPE。这是本阶段唯一的静态状态，且**只服务这四个常量**（`SKILL_KEY` 阶段 4.4 前不得删除，指南 2.4 原话）。

### 8.1 `retired` 消失后的覆盖论证（T11-L1，评审留痕）

**触发路径（谁在 disable 时承担取消）** —— 行号以 **t9 代码提交 `6421eda` 的树**为准（`git show 6421eda:<path>` 实测）：
```
ShadowHunterRolesPlugin.onDisable()            (:81；:84 调用 clearAllPlayersRole)
  → roleManager.clearAllPlayersRole()          (RoleManager.java:96-101；:98 循环 instance.clear()，:100 再清 map)
    → 每个实例 instance.clear()                 (RoleInstance.java:706-…)
      → 先 triggerLifecycleStop()               (RoleInstance.java:709；方法体 :565-589，逆序：武器 :568 → 被动 → 技能 :581)
        → 组件 stop()                           (RoleInstance.java:571-580 的逆序遍历)

```
**覆盖结论**：`retired` 的职责（插件 disable 时取消该周期任务）**已被组件自身的 `stop()` 完整承接**，路径上无缺口窗口；此外还有一层服务端兜底 —— 插件禁用时 Bukkit/Paper 会取消**该 plugin 名下**的全部任务，因此即便某个实例不在 `playerRoleMap` 里（`clear()` 未被调用），该任务也不会跨插件生命周期存活。`retired` 的原始用途是 **Folia 的实体/区域失效兜底**，而本插件唯一运行环境是普通 Paper（§3.3 注 ②）—— 平台端口在 Paper 上不产生"区域失效"这一事件源，故不需要该回调。
**残余风险（如实）**：若将来真的启用 Folia 分支（§3.3 注 ② 明确"现在不实现"），`Scheduler` 的 Folia 实现需要自行决定是否提供 `retired` 语义；这一条留给未来的 Folia 适配器，**不影响当前 Paper 运行环境的等价性**。
