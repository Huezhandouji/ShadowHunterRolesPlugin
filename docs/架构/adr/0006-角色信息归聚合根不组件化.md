# 0006 · 角色信息归聚合根，不组件化

- **状态**：已采纳（当前有效）
- **对象**：角色的**展示信息**（显示名 / 描述 / 图标）的归属

## 背景

角色信息（显示名、描述、图标）是**每个角色一份**的静态数据：它由角色模板声明，不随玩家、不随会话、不随 tick 变化。同一份信息被多处读取——对外接口、命令、面板、以及任何需要"这个角色叫什么、长什么样"的地方。

与之相对，组件是**按角色实例实例化**的：一个玩家拿到某个角色时，框架会为这次实例创建一套组件对象。这条"按实例创建"的性质，决定了哪些东西适合做成组件、哪些不适合。

此前曾评估过把角色信息做成一个**框架级组件**（承载显示名 / 描述 / 图标），以便让"角色必须提供这些信息"这件事能被装配期检查看见。

## 决策

**角色信息不做成组件，归聚合根（角色模板）**：显示名 / 描述 / 图标仍由角色模板持有，读取方直接向模板取；需要"必须存在"的保证时，用装配期校验保证模板字段完整，而不是用组件承载它。

**理由**：组件按角色实例实例化 ⇒ 把**全局一份**的静态信息做成组件，会让同一份数据**在每个实例上重复一份**：内存上重复、初始化时重复、校验时也要在每个实例上再查一遍。而这些信息的生命周期与"玩家是否在线、是否持有该角色"完全无关。

这条判断与**阵营关系表保持静态、不随实例复制**的既有裁决**同源**：凡是"全局一份 / 模板级"的数据，都不应该被拖进按实例创建的对象里。

## 被放弃的替代方案

**替代方案（做成框架级组件）**：新增一个框架级组件承载角色信息，使"角色必须提供展示信息"能由依赖系统检查。

放弃它，有三处实打实的代价：

1. **每实例一份**：同一份静态信息随实例重复创建——与它的生命周期不符；
2. **需要引入"框架必然提供的服务类型"白名单**：组件是按实例装配的，而依赖检查看到的是**模板**；要让模板侧检查看见一个"框架必然会提供"的组件，就必须额外维护一张白名单，否则会把框架自己的服务误报成"缺依赖"；
3. **实例侧还要硬检查一次**：模板侧通过了，也不代表实例侧真的装配上了——于是同一件事要在两处各查一遍。

## 后果（含代价）

- **"必须提供展示信息"的保证落在模板校验上**：错误在装配期就暴露（该角色不注册），而不是等到某个玩家拿到角色时才发现；
- **读取路径多一跳**：读取方经模板取，而不是经"某个组件的实例"取；好处是不需要在没有玩家的场景下构造实例；
- **对外接口只增不改**：既有读取入口保持原样，新增替代入口按"只增不改"处理；
- **代价**：如果将来出现"某个角色的展示信息需要按玩家/按状态变化"的需求，它**不能**直接塞进模板——那时应当为**可变的那部分**单独设计（组件或其它按实例对象），而把**不变的那部分**留在模板。

## 判定边界（可复述的规则）

> **每实例一份 ⇒ 该做成组件**；**全局 / 模板级静态 ⇒ 归聚合根**。

| 类别 | 判定问法 | 本仓的例子 |
|---|---|---|
| **该做成组件** | 这份数据/行为是否**随玩家实例**产生、随实例消亡？ | 能量、SanTE、生命、buff 记账、计时资源、阵营**当前值** —— 每个实例各一份 |
| **归聚合根** | 这份数据是否**全局一份 / 模板级**、与"谁持有"无关？ | 角色的显示名 / 描述 / 图标；角色的数值上限声明；**阵营关系表**（静态关系，不随实例复制） |
| **边界情形** | 同一概念既有"模板级声明"又有"实例级当前值"？ | 则**拆开**：声明留模板，当前值进组件（阵营即此例：关系表静态、当前值按实例） |

## 门槛自证

- **难以回退**：一旦按组件落地，所有读取方都会依赖"经组件取"的路径，并且要为每个实例维护一份副本；改回模板级要动读取路径与实例装配，并重新核对"必须存在"的检查点。
- **缺上下文会令人困惑**：读者会看到框架里大量"按实例一份"的组件（能量、阵营……），自然会问"为什么角色信息不也做成组件"——不解释就会以为是遗漏。
- **是真实取舍**：确实评估过"做成框架级组件"这条路（它换来"必须存在"能被依赖检查看见），是因为"全局一份的数据不该按实例复制"才选了模板级。
