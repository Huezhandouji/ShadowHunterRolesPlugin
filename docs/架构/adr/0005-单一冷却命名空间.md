# 0005 · 单一冷却命名空间

- **状态**：已采纳（当前有效）
- **对象**：冷却的存储结构——两张表（技能 / 主武器）还是**一张表**

## 背景

技能与主武器是两类东西，曾经各有一张冷却表，按"组件属于哪一类"选用哪张表。这一对表的代价是：冷却的**所有**读口与写口都要多带一个"属于哪一类"的参数，而这个参数本身又必须在组件被构造之前就确定（服务集先于组件构造）——于是它反过来成了装配期的必填项，并渗进端口、容器与命令面。

## 决策

**冷却只保留一个命名空间**：一张表，键是组件 id。启动冷却的入口返回"**是否真的写了表**"（这个返回值承担原来"被动没有冷却"的语义：不写表、不派发、不请求刷新）。

## 被放弃的替代方案

**替代方案（保留两张表）**：按类别分表，读起来更直观（"技能冷却"与"武器冷却"两栏清清楚楚）。

放弃它的理由：分表把"类别"变成冷却的必填参数，而这个参数在删除类别枚举之后无处安放；更实际的代价是**误用无法被发现**——拿一个主武器的 id 去问"技能冷却好了吗"，在分表下会得到"没有记录 ⇒ 视为就绪"，这是一个会撒谎的答案。

## 后果（含代价）

- **可能出现跨类误用的语义变化**：同一个 id 在合并前可能因为问错了表而恒得"就绪"，合并后会得到**真实**的冷却状态。这属于"把原本会撒谎的答案改准"，但它确实是一次可见读数变化，任何依赖旧行为的外部调用都会不同。
- **按类别筛选不再免费**：想知道"技能侧是否在冷却"要结合组件自身的能力面判断，不能再靠"表名"。
- **一个返回值承担语义**：入口的布尔返回值不是装饰，而是"被动不写表"这条语义的落点——改它等于改语义。

## 门槛自证

- **难以回退**：改回两张表要把"类别"参数重新加回端口、容器、命令面与所有调用点，并重新核对"哪张表"的分派；期间任何漏改都会表现为冷却不生效或读错表。
- **缺上下文会令人困惑**：合并后只有一个入口、且它返回一个布尔值，读者会问"为什么启动冷却还要返回东西"；不解释就会把这个返回值当成可忽略的调试信息。
- **是真实取舍**：两张表在可读性上确有优势，是明确评估过之后才合并的。
