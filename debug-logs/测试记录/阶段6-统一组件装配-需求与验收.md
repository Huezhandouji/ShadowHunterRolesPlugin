## §5 `addComponent` 签名与旧方法别名（A6）

### §5.1 两个重载（**写死**）

```java
// 占热键栏（有槽位）：权威 kind 由注册处给出
public Builder addComponent(String id, ComponentFactory<? extends RoleComponent> factory, int slot, ItemKind kind)

// 不占热键栏（无槽位）
public Builder addComponent(String id, ComponentFactory<? extends RoleComponent> factory, ItemKind kind)
```
- **无槽位 = 不占热键栏**（不进 `slotMap`；渲染器遍历 `slotMap` ⇒ 天然不会被渲染 —— 见 C-08 的现状出处 `HotbarRenderer.render()` 只遍历 `slotMap`）。
- **工厂形参类型放宽到 `ComponentFactory<? extends RoleComponent>`**（今天三条都是窄类型：`ComponentFactory<Skill>` / `ComponentFactory<PassiveSkill>` / `ComponentFactory<MainWeapon>` —— 这正是"必须继承"的类型学根源）。

### §5.2 旧三方法 = **弃用别名**，与 `addComponent` **走同一条内部路径**

- `addSkill(String, ComponentFactory<Skill>, int)` → 内部 `addComponent(id, factory, slot, ItemKind.SKILL)`
- `addMainWeapon(String, ComponentFactory<MainWeapon>, int)` → 内部 `addComponent(id, factory, slot, ItemKind.MAIN_WEAPON)`
- `addPassive(String, ComponentFactory<PassiveSkill>)` → 内部 `addComponent(id, factory, ItemKind.PASSIVE)`
- **保留**（不删）+ 标注 `@Deprecated`（javadoc 指向 `addComponent`）；**14 个现有组件的 `RoleLoader` 装配行可以不改**（用户裁定：现有组件零改动）。
- **单一内部路径判据（C-03）**：三个旧方法与新入口最终都调用**同一个私有实现**（`private Builder addComponentInternal(...)` 或直接同体）；判据 = 「三个 `add*` 方法体内**只有一条** `addComponentInternal(` 调用，且 `addComponent` 两个重载体内**也只有**这一条」。

### §5.3 数据结构（**派发顺序的载体**，A4 的前置）

- `Role.Builder` 内新增**唯一有序组件表** `LinkedHashMap<String, ComponentEntry>`（`ComponentEntry = (factory, kind, slot?)`），**声明顺序 = `add*` 调用顺序**；`slotMap` 语义不变（仅"槽位 → id"）。
- **三个既有 id 视图保留**：`Role.getSkillIds()` / `getPassiveSkillIds()` / `getMainWeaponIds()`（现算出处 = `core/Role.java:278-286`，三处 `return <xxx>Factories.keySet();`，载体是 `LinkedHashMap`（`:112-114`）⇒ **组内保持声明序**）⇒ 目标形态 = **按 kind 过滤的有序视图**；另新增 `Role.getComponents()`（权威有序表）与 `Role.componentKindOf(String id)`。
- **`RoleInstance.initComponents()` 只遍历 `getComponents()` 一次**（判据 C-05）。

## §6 权威 kind 的位置与理由（A7）

**结论（写死）**：**权威 `kind` 在注册处（`Role` 模板 / `Role.Builder.addComponent` 的入参）**；组件 `spec().kind()` **仅作表现用途**，**不得**参与任何行为分支（渲染器/闸门/PDC/冷却表/listener 一律读注册 kind）。

**理由（服务集先于组件构造 ⇒ 组件不可能持有权威 kind）**：
1. `RoleInstance.createServices(String componentId, ItemKind kind)`（`core/RoleInstance.java:158`）**先**构造服务集，调用点 `:225`（技能 `ItemKind.SKILL`）/ `:234`（被动 `ItemKind.SKILL` ← 见 C-12 清理项）/ `:243`（主武器 `ItemKind.MAIN_WEAPON`）；
2. `CooldownPortImpl` 在**构造期**就把 kind 绑定为字段（`core/CooldownPortImpl.java:23-27` 的 `CooldownPortImpl(RoleInstance owner, String componentId, ItemKind kind)`）⇒ 冷却端口的行为在组件**被构造之前**已经由注册处决定；
3. 组件拿到的工厂签名是 `T create(String id, ComponentServices services)`（`roleComponent/ComponentFactory.java:24`，`@FunctionalInterface`）—— **只有 id 与服务集，没有 kind** ⇒ 组件**无法**从框架侧得知权威 kind；今天它之所以"知道"，是因为**基类构造函数**把常量写死（`Skill:29` 传 `ItemKind.SKILL` / `MainWeapon:32` 传 `ItemKind.MAIN_WEAPON`）⇒ 统一入口后这条通道消失，必须由注册处持有。

**一致性判据（C-04）**：组件自述 kind 与注册 kind **不一致时不得改变行为**；判据 = 渲染器/闸门/PDC 的行为分支里**读取组件自述 kind 的调用点 = 0**（唯一允许出现的位置 = 日志或自检）。

### §7.4 **`red` 的 update 次序对调 —— 反例（决定性）**

**两条写入的现算事实**：
- `RedDeeplySorrowSkill.update():64`：`svc().sante().decrease(10);`（条件：`running == true` 且 20 刻节拍到 `:55-60`）；
- `RedBleedPassive.update():159`：`svc().sante().gain(BLEED_SANTE_RECOVER);`，`BLEED_SANTE_RECOVER = 4`（`:39`）、节拍 = `BLEED_SETTLE_INTERVAL_TICKS = 20`（`:45`）⇒ **两者都是 20 刻节拍**；
- `SanTEPortImpl` 三个写方法都直接落到容器（`SanTEPortImpl.java:15/20/25`），而 `RoleInstance.setCurrentSanTE` **每次写入都 clamp 到 `[0, max]` 并立即派发**（`:554-562` 的 `dispatchSanTEChange(pre, now)` ⇒ `broadcastSanTEChange` 按注册表顺序广播到**全部**组件）。
⇒ **同一 tick 内两次写入的先后，会改变 clamp 的落点**（先扣后加 vs 先加后扣）。

**反例（SanTE 初值 = 9，maxSanTE = 100，同 tick 双写）**：

| 序 | 计算 | 是否归零 | 归零惩罚（STUN 100 tick + 真伤 + 标题，`DefaultSanTEZeroPunishment:48-56`） | `deeplySorrow.running` | tick 末 SanTE |
|---|---|---|---|---|---|
| **现状**（deeplySorrow → bleed） | 9 −10 ⇒ clamp **0** ⇒ 派发 `(9,0)`；再 0 +4 ⇒ 4 | **是** | **触发** ✅ | 置 `false`（`:75-78`） | **4** |
| **纯注册序**（bleed → deeplySorrow） | 9 +4 ⇒ 13 ⇒ 派发 `(9,13)`；再 13 −10 ⇒ 3 | **否** | **不触发** ❌ | 保持 `true` | **3** |

**同一状态、同一 tick，一个触发整套归零惩罚（眩晕 + 真伤 + 标题）、一个不触发** ⇒ 玩家可见的**强差异**。
**仅数值也已有差异**（无需惩罚）：初值 100 ⇒ 现状 `100−10+4 = 94`；新序 `clamp(100+4)−10 = 90`。
**可达性**：两次结算同为 20 刻节拍，相位由「黯然销魂的施放时刻」与「组件创建时刻」决定 ⇒ **玩家可控**；本卡**不声称**每次都会撞上同 tick，只要求实施批按"**已申报的行为变化**"处理并按 §10 取证。

### §7.5 **结论写死（A5）**

> **本批派发顺序声明 = 「已申报的行为变化」（非等价）**，依据 = 判据 **C-05**（派发序改为纯注册序）+ **C-11**（`update` 次序的自检）+ 本节 **§7.4 的反例**；影响面 = **`red` 角色的 SanTE 结算次序**（`RedBleedPassive.update()` 的 `gain(+4)` 与 `RedDeeplySorrowSkill.update()` 的 `decrease(−10)` 在同一 tick 的先后），可观察后果 = ① tick 末 SanTE 值（如 4 vs 3、94 vs 90）② **归零惩罚是否触发**（STUN + 真伤 + 标题）③ `RedDeeplySorrowSkill.running` 是否被置 false（连带其冷却重启）。**`meiqihezi` 侧逐阶段等价；`awake/start/stop/onSanTEChange` 四个阶段的"相对次序"等价。**

## §8 「不必继承」的判据与例子（A8）

**冻结要求**：新组件只需 `extends RoleComponent`（或实现 `RoleComponent` 的等价契约）+ **按需实现能力接口**（`HotbarActionable` / `CombatHook` / `CooldownBearing` / `EnergyCosting` / `HotbarPresentable`），**不必**继承 `Skill` / `MainWeapon` / `PassiveSkill`；登记一律走 `addComponent`。

**今天写不出、之后能写出的例子（两条，均可核对）**：

1. **「有图标、有冷却，但**不被按键触发**的组件」** —— 今天**类型上不可能**：能被渲染的前提是成为 `HotbarItem`，而今天唯一提供图标/冷却的基类是 `ActiveComponent`，它**同时实现** `HotbarItem` 与 `HotbarActionable`（`javap` 实测：`public abstract class ActiveComponent extends RoleComponent implements HotbarItem, HotbarActionable`）⇒ 今天"能显示"就必然"可施放"。
   - **判据（C-13a）**：`git -C ShadowHunterRoles grep -n -F 'implements HotbarItem, HotbarActionable' -- src/main/java` 现算 = **1 行**（`ActiveComponent`）；实施后新增的能力接口应允许 `HotbarPresentable` + `CooldownBearing` **不带** `HotbarActionable`。
2. **「同时是技能形态与攻击形态」的组件** —— 今天的绕道 = `extends MainWeapon implements HotbarActionable`：类型上可行，但会**连带**继承主武器的四条通道（闸门 = `canUseMainWeapon`、PDC = `main_weapon_id`、冷却 = 主武器表、**文案不带秒数**）⇒ 开发者**无法**只挑能力。
   - **判据（C-13b）**：`git -C ShadowHunterRoles grep -c -F 'implements CombatHook' -- src/main/java` 现算 = **1**（仅 `MainWeapon`）；`Skill` 与 `PassiveSkill` **都不**实现它 ⇒ 今天的组合自由度 = 0。
3. **今天的登记入口是窄类型（类型学证据）**：`addSkill(String, ComponentFactory<Skill>, int)` / `addPassive(String, ComponentFactory<PassiveSkill>)` / `addMainWeapon(String, ComponentFactory<MainWeapon>, int)`（`Role.java:183/203/219`）⇒ 一个只 `extends RoleComponent` 的类**没有任何入口**可登记。
