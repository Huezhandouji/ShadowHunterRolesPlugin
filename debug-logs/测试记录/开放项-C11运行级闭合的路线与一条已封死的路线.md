## 一、⚠️ 已封死的路线：「把机器人放到粒子半径外」/「绕开粒子」

**结论：在现有源码下没有可行构造。** 三条依据：

**1. 崩点粒子与 C-11 必需的写入在同一个 tick、同一条分支**

`src/main/java/com/shadowHunterRolesPlugin/roleComponent/red/RedBleedPassive.java`：

- 周期结算路径：`:155 player.spawnParticle(Particle.DUST, victim.getLocation()…)` → 紧接 `:159 svc().sante().gain(BLEED_SANTE_RECOVER)`（= **`+4`**，C-11 相位的必需写入）；
- 另一条结算路径：`:244 svc().sante().gain(…)` → `:246 victim.spawnParticle(Particle.DUST, …)`。

⇒ **只要 C-11 的相位成立（`+4` 真的发生），同一 tick 必然有 DUST 包发出。** 两条路径只是**收件人不同**（前者发给红方施放者，后者发给受害者）。

**2. 「放到半径外」不成立**

上述两处用的是 **`Player#spawnParticle`** ⇒ **按玩家定向发送，不受 32 格半径约束**，收件人必然收到。
而 `World#spawnParticle` 那几处（`roleComponent/DefaultSanTEZeroPunishment.java:88/89/124` = `TOTEM_OF_UNDYING` / `SCULK_SOUL`）虽是半径发送，但**惩罚点就在施放者身上** ⇒ 施放者也必然收到。

**3. ⇒ 客户端必须同时容忍三类包**

`DUST` + `TOTEM_OF_UNDYING` + `SCULK_SOUL`。**「绕开粒子」在现有源码下无解**，除非改产品代码 —— 而那要付**新制品代次 + 一整套取证**，**不该为一张取证卡去动产品代码**。

## 三、⚠️ 仍待查的第一环（**已排除一条假设，留下一条新假设**）

`t25` 的实测事实之一是：三次武器攻击**已被服务端接受**（槽 0 主武器图标转 `structure_void` = 进入冷却态），但 **`RedBleedPassive.playerBleedRecord` 始终为空** ⇒ **流血账本未建立** ⇒ 相位链**第一环即断**。

**❌ 已排除的假设（曾被写进本件，现予推翻）**：「受害者必须是**敌对且已有角色**的玩家」。
**推翻依据（可复算）**：账本闸门 `RedBleedPassive.canReceiveBleed(Player)`（`RedBleedPassive.java:111`）只判四件事 ——
`victim != null` · `victim.isOnline()` · `!victim.isDead()` · `victim.getHealth() > 0d` —— **不含任何阵营/角色/敌对判定**。
另：`RedBleedPassive.applyStacks(UUID, int)`（`:76`）内部也**无前置条件**；`MainWeaponListener` 内**无**阵营/敌对相关符号。

**✅ 现行假设（未验证，勿当结论）**：真凶更可能是紧邻闸门的那一行 ——
`RedSanctifiedBladeMainWeapon.java:44-46`：
```java
RedBleedPassive bleed = getComponent(RedBleedPassive.class);
if (bleed != null && RedBleedPassive.canReceiveBleed(victim)) {
    bleed.applyStacks(victim.getUniqueId(), BLEED_STACKS_PER_HIT);
}
```
源码自身的注释即写明：**「拿不到账本时只跳过流血、继续结算普攻伤害（不能直接 return）」** ⇒ **`bleed == null` 是一条被设计过的正常分支**。
而 `t25` 观察到的特征（**攻击被接受、主武器照常进冷却态、只有账本没写**）**与该分支完全吻合** ⇒ 指向 **`getComponent(RedBleedPassive.class)` 返回了 `null`**。

**下一步验证（静态即可，便宜）**：读 `RoleComponent`/`RoleInstance` 的 `getComponent(Class)` 实现，核"按运行时类查找"与"组件实际注册键"是否一致（例如是否存在按 id 注册、按类查找的错配）。
**修法方向（若假设成立）**：属**探针侧/调用侧**可绕（例如改由 `requestResolve` 入口驱动），**成本远低于**客户端解析层。

### 5.3 方向判定（对**被惩罚方**= 红）

- **「是否触发」**：不变（由注册序决定）。
- **「触发后的强度/延长性」**：修复后**削弱** —— 时长与真伤跳数不再被重入刷新放大，且"回满 max"按时兑现（对红方是**有利**项）。
- **「惩罚期间的压制」**：修复后**加强** —— SanTE 被每跳钉 0（旧实现可残留 +4）。
- ⇒ **净判读**：**「触发与否」不变；一旦触发，修复使惩罚有界、不可延长，并在 ≈4 s 后把 SanTE 回满 ⇒ 对红方整体偏有利**；同时惩罚期间的 SanTE 压制更硬（局部加强）。两件事必须**分列**，不得合成一句"加强/削弱"。

- 旧结论：「**约 1 秒延迟、略加强红**」——其模型把 `inSanTEPunishment` 当作**纯写不读的死状态**、把重入当作"只把惩罚**延迟**约 1 秒"。
